# Завершение проверки местных ролей после миграции 090

Миграция 090 отделяет глобальные назначения администратора и исследователя от местной роли участника дерева. В текущей базе `archive_memberships_role_check` может оставаться `NOT VALID`: сервер исправляет старые `admin` и `researcher` в `relative` только при открытии каждого архива. Это руководство описывает отдельную операторскую процедуру для всех архивов. Она не назначает глобальные роли и не открывает членство в чужом дереве.

Используйте только проверенный каталог релиза с этим CLI и отдельную PostgreSQL-роль `SUPERUSER` или `BYPASSRLS`, у которой есть права изменить таблицу. Рабочая роль Drevo специально не подходит: на `archive_memberships` включена принудительная RLS, поэтому её чтение не может служить глобальной инвентаризацией. Перед рабочим запуском проверьте процедуру на одноразовой восстановленной копии, состояние резервной копии и место для WAL. Пароль передавайте штатным защищённым способом PostgreSQL; не добавляйте его в команду, журнал или отчёт.

В каталоге закреплённого релиза, с уже настроенными `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER` и доступом к паролю:

```sh
node --experimental-strip-types ops/postgres/finalize-global-staff-roles.ts inventory
node --experimental-strip-types ops/postgres/finalize-global-staff-roles.ts apply
node --experimental-strip-types ops/postgres/finalize-global-staff-roles.ts inventory
node --experimental-strip-types ops/postgres/finalize-global-staff-roles.ts validate
```

`inventory` — только чтение: выдаёт общие числа членств, старых `admin`, `researcher`, неизвестных ролей и признак `validated`, без имён, ID архивов и участников. `apply` меняет **только** `role` старых двух значений на `relative` короткими транзакциями, не более 500 строк в порции и 100 порций за вызов. В каждой порции он берёт тот же advisory lock, что и стартовая миграция 090, до блокировки строк. Удерживаемые другой транзакцией строки пропускаются; если остался хоть один старый участник, результат `complete:false` и код выхода 2 означают, что запуск нужно повторить после устранения конкуренции. Не считать пустую порцию доказательством завершения. Неизвестная роль останавливает запись до первого изменения; её причину нужно исследовать отдельно, не преобразовывать автоматически.

`validate` вызывается отдельно: под тем же advisory lock повторно проверяет структуру, действующий триггер и отсутствие несовместимых строк, затем выполняет `VALIDATE CONSTRAINT` с пределами ожидания блокировки и времени SQL. Повторный запуск после успешной проверки безопасен. Согласно [документации PostgreSQL](https://www.postgresql.org/docs/current/sql-altertable.html), этот шаг берёт `SHARE UPDATE EXCLUSIVE`; не объединяйте его с длительным backfill в одной транзакции. Ошибки CLI показывают только безопасную причину или SQLSTATE, а не текст ошибки PostgreSQL с данными строки. Прерванный запуск можно повторить; уже зафиксированные порции сохранятся, незавершённая порция откатится.

Операция не меняет `archive_owners`, `approved`, `person_id`, `tree_access`, тариф, глобальные назначения и историю. `runtime_users.role` по-прежнему представляет владельца как `admin` для совместимости старого клиента; это не новое глобальное право. Проверка 090 сама по себе не закрывает общий аудит межархивной изоляции.
