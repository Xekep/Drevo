## CODE15-01 Ответ каталога источников уходит после отзыва доступа

Категория: авторизация и конкурентный доступ. Severity: HIGH. Priority: P1.
Confidence: HIGH для воспроизведения SQLite; PostgreSQL использует тот же
HTTP-контроллер, но отдельное воспроизведение ещё требуется. Сложность: M.

Где: `src/server/source-catalog-http.ts:46`, ветви GET списка и отдельного
источника; `src/server/source-catalog-store.ts`, методы `page` и `get`.

Контроллер проверяет `auth.isAdmin(req)` до чтения каталога. После асинхронного
получения данных он сразу возвращает JSON, не проверяя действующий сеанс,
роль или членство повторно и не связывая доставку с блокировками прав.
Пользователь с ранее действовавшим доступом может получить один подготовленный
ответ после его отзыва. Новые запросы при этом уже запрещены.

Воспроизведение:

1. Запустить отдельный архив с `PUBLIC_ORIGIN=http://localhost`, создать
   одобренного администратора с действующей cookie-сессией.
2. Создать через POST `/api/sources` источник с уникальным текстом описания.
3. Отправить GET `/api/sources`; приостановить возврат результата `.all()`
   запроса `SELECT data,version FROM source_catalog`, уже прочитав строки.
4. Другим соединением снять `approved` пользователя, затем отпустить результат.
5. Повторить для GET `/api/sources/:id`, приостанавливая `.get()`.

Измерено в обоих случаях: выполнявшийся GET вернул `200` и уникальное закрытое
описание; следующий GET вернул `403`. Это не доступ произвольного гостя:
для начала запроса нужны действующие административные права.

Исправление: использовать существующий подход защищённой доставки из
`archive-query-http.ts`: после подготовки данных повторно проверить сессию и
актуальные права; в PostgreSQL удерживать совместимые блокировки сеанса,
членства и архива до ограниченной по времени отправки. Простая повторная
проверка без блокировки оставляет новое окно гонки. Проверить отзыв сеанса,
членства, одобрения и роли, список и прямой ID, а также медленного клиента.

## CODE15-02 Дневной лимит токенов не резервирует незавершённые запросы

Категория: ограничение расходов и конкурентный доступ. Severity: MEDIUM.
Priority: P2. Confidence: HIGH. Сложность: L.

Где: `src/server/ai-usage.ts:120` — проверка фактического расхода;
`begin` записывает нулевые токены; `admit` сериализует проверку и начало;
`finish` записывает расход после выполнения. Вызов —
`src/server/ai-research-http.ts`, приём запроса и завершение работы модели.

Лимиты числа запросов резервируются корректно, включая повторную атомарную
проверку в `admit`. Токены учитываются по завершённым запросам. Пока несколько
диалогов работают, каждый видит расход незавершённых соседей как нулевой;
один длительный запрос также может превысить оставшийся дневной бюджет.
Следующий запрос блокируется, но уже понесённый расход остаётся сверх лимита.

Воспроизведение без вызова модели:

1. Создать `aiUsageStore` на тестовом SQLite со штатной схемой.
2. Задать `requestsPerMinute=0`, `dailyRequests=0`, `dailyTokens=100`.
3. Дважды вызвать `usage.admit` для одного пользователя до завершения первого.
4. Для каждого вызова выполнить `finish` с 60 входными и 60 выходными токенами.
5. Прочитать summary и попробовать третий `admit`.

Измерено: два запроса приняты, итог 240 токенов при лимите 100, третий запрос
отклонён. Это воспроизведение учёта, а не измеренный счёт внешнего провайдера.

Исправление: явно определить лимит как мягкий порог либо реализовать жёсткий
бюджет. Для жёсткого бюджета нужен атомарный резерв на выполняющийся запрос,
оценка входа и предел выхода, повторная проверка перед каждым платным вызовом
агента/vision/Code Interpreter, сверка с фактическим usage и освобождение
остатка при ошибке, остановке и падении процесса. Резерв должен работать
между backend-процессами и разными древами одного аккаунта. Само по себе
перемещение текущей проверки внутрь транзакции проблему не решает: это уже
сделано, но резерв токенов отсутствует.

## Подтверждённые ограничения и защиты

- `postgres-connections.ts` ограничивает пул десятью соединениями и разделяет
  допуск транзакций и файловых задач. `store-database.ts` использует
  `pg_try_advisory_lock` и освобождает соединения между попытками захвата;
  прежнее замечание о безусловном исчерпании пула ожидающими блокировками
  по этому пути не подтверждается.
- `archive-read-cache.ts` имеет общий бюджет и лимит одного снимка. Это
  ограничение сохранённых JSON/индексов, а не гарантия верхнего RSS процесса:
  распарсенные копии ответов и текущая работа расходуют память отдельно.
- Вход в ИИ повторно проверяет права после сохранения файлов и атомарно
  допускает сообщение вместе с записью usage. Начальная проверка `usage.check`
  не является единственной защитой от гонки числа запросов.
- Изменение источников проверяет актуального автора и версии в транзакциях;
  CODE15-01 относится к чтению и доставке, а не к отсутствию всех проверок прав.
