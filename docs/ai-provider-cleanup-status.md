# Состояние очистки диалогов ИИ

В разделе «Платформа → Yandex AI» доступен раскрываемый блок «Очистка диалогов у провайдера». Он загружает очередь при открытии, показывает общие счётчики платформы и выдаёт по 20 незавершённых заданий. Фильтры — все незавершённые либо задания, требующие действий. Обновление возвращает к первой странице. Это операционная информация для администратора платформы; владелец или администратор отдельного древа её не получает.

`GET /api/admin/ai/cleanup` возвращает только локальный ID задания, состояние, число попыток, время обновления и следующей проверки, безопасную категорию ошибки, допустимый HTTP-код и признак допустимости ручного повтора. Ответ не содержит удалённые ID, архивы, пользователей, диалоги, исходные credentials, ciphertext, токены lease или произвольный текст ошибки провайдера. `Cache-Control: no-store`; курсор привязан к фильтру и проверяется до SQL. Постраничный запрос ограничен 21 строкой, включая признак следующей страницы, и использует индекс порядка `(updated_at, id)` без OFFSET. Временная смена состояния или времени задания может изменить состав следующих страниц; кнопка обновления начинает новый просмотр текущей очереди.

В PostgreSQL перед выдачей заново проверяются сеанс, одобренное членство и системный допуск. Строки прав удерживаются до ограниченного по времени завершения записи HTTP-ответа; одновременно изменяющиеся права дают конфликт, отозванные — отказ без очереди. SQL ограничен двумя секундами, передача ответа — четырьмя. Счётчики считаются для всех незавершённых заданий одним снимком с текущей страницей; при росте очереди их расчёт требует чтения большего числа записей. В SQLite явно показывается отсутствие долговечной очереди.

Для `blocked` с причиной `provider_auth_401/403` или допустимым `provider_rejected_4xx` администратор может нажать «Повторить». `POST /api/admin/ai/cleanup/:id/retry` проверяет origin, действующий сеанс, членство и платформенный допуск, затем атомарно переводит только всё ещё заблокированное задание в `pending` с задержкой 45 секунд. Повторный запрос не сдвигает срок и не создаёт вторую запись аудита. Повреждённый snapshot, неизвестная причина, временный ответ и 404 не допускают ручного повтора. Зашифрованное исходное подключение, его версия и число сетевых попыток не меняются; новый API-ключ в настройках на прежнее задание не влияет. Ответ `202` означает только постановку в очередь: сетевой DELETE выполняет существующий worker позже и вне SQL-транзакции. Интерфейс не утверждает, что удаление уже произошло.

В журнал текущего архива записывается только обезличенное действие «Повтор очистки поставлен в очередь» с автором, без удалённого ID, другого архива, текста ошибки или credentials. Этот журнал следует жизненному циклу текущего архива и не является отдельным вечным общеплатформенным журналом. Повреждённый snapshot требует проверки ключа и системного восстановления; кнопка не заменяет credentials вручную.

Успешное удаление Conversation у Yandex не доказывает удаления его элементов. Поэтому список не выдаёт такую гарантию. Прежние ID без достоверного исходного подключения и окно падения до долговечной регистрации ID сохраняют ограничения [основного контракта](ai-provider-cleanup.md).

Проверки: HTTP на отдельной PostgreSQL БД с настоящим архивным пулом, безопасная проекция ошибок, пагинация при одинаковых timestamps, оба индексных плана без общей сортировки, владелец древа без системного допуска, отзыв допуска и сеанса после начальной аутентификации. Для ручного повтора дополнительно проверяются причины отказа, origin/JSON, отзыв сеанса/членства/допуска, два одновременных POST, неизменность snapshot и 45-секундный срок, аудит ровно один раз. SQLite показывает отсутствие долговечной очереди; браузерные desktop/mobile проверки покрывают кнопку, ответы 409/503 и сохранение несохранённого черновика общих настроек. Реальный провайдер и рабочие диалоги в тестах не используются.
