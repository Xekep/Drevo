# Состояние очистки диалогов ИИ

В разделе «Платформа → Yandex AI» доступен раскрываемый блок «Очистка диалогов у провайдера». Он загружает очередь при открытии, показывает общие счётчики платформы и выдаёт по 20 незавершённых заданий. Фильтры — все незавершённые либо задания, требующие действий. Обновление возвращает к первой странице. Это операционная информация для администратора платформы; владелец или администратор отдельного древа её не получает.

`GET /api/platform/ai/cleanup` работает из корневого `/admin` с действующим сеансом и глобальным правом администратора, даже если администратор не состоит ни в одном древе. Прежний `GET /api/admin/ai/cleanup` остаётся для архивного интерфейса и дополнительно требует одобренного членства. Оба возвращают только локальный ID задания, состояние, число попыток, время обновления и следующей проверки, безопасную категорию ошибки, допустимый HTTP-код и признак допустимости ручного повтора. Ответ не содержит удалённые ID, архивы, пользователей, диалоги, исходные credentials, ciphertext, токены lease или произвольный текст ошибки провайдера. `Cache-Control: no-store`; курсор привязан к фильтру и проверяется до SQL. Постраничный запрос ограничен 21 строкой, включая признак следующей страницы, и использует индекс порядка `(updated_at, id)` без OFFSET. Временная смена состояния или времени задания может изменить состав следующих страниц; кнопка обновления начинает новый просмотр текущей очереди.

В PostgreSQL новый маршрут перед выдачей заново проверяет сеанс и глобальное право; архивный маршрут также проверяет одобренное членство. Строки прав удерживаются до ограниченного по времени завершения записи HTTP-ответа; одновременно изменяющиеся права дают конфликт, отозванные — отказ без очереди. SQL ограничен двумя секундами, передача ответа — четырьмя. Счётчики считаются для всех незавершённых заданий одним снимком с текущей страницей; при росте очереди их расчёт требует чтения большего числа записей. В SQLite явно показывается отсутствие долговечной очереди.

Для `blocked` с причиной `provider_auth_401/403` или допустимым `provider_rejected_4xx` администратор может нажать «Повторить». Новый `POST /api/platform/ai/cleanup/:id/retry` проверяет origin, действующий сеанс и глобальное право без членства; прежний `POST /api/admin/ai/cleanup/:id/retry` также требует одобренного членства. Оба атомарно переводят только всё ещё заблокированное задание в `pending` с задержкой 45 секунд. Повторный запрос не сдвигает срок и не создаёт вторую запись аудита. Повреждённый snapshot, неизвестная причина, временный ответ и 404 не допускают ручного повтора. Зашифрованное исходное подключение, его версия и число сетевых попыток не меняются; новый API-ключ в настройках на прежнее задание не влияет. Оба маршрута отправляют ответ о конкретном задании после COMMIT и ещё раз проверяют сеанс и свои права перед выдачей; при отзыве в этом промежутке не выдаются даже признаки 404/409. Поставленное в очередь задание при этом не откатывается. Ответ `202` означает только постановку в очередь: сетевой DELETE выполняет существующий worker позже и вне SQL-транзакции. Интерфейс не утверждает, что удаление уже произошло.

Новый маршрут записывает действие в платформенный аудит с автором и локальным непрозрачным UUID задания, без данных провайдера или архива. Прежний архивный маршрут сохраняет обезличенное действие «Повтор очистки поставлен в очередь» в журнале текущего архива; этот журнал следует жизненному циклу архива. Повреждённый snapshot требует проверки ключа и системного восстановления; кнопка не заменяет credentials вручную.

Успешное удаление Conversation у Yandex не доказывает удаления его элементов. Поэтому список не выдаёт такую гарантию. Прежние ID без достоверного исходного подключения и окно падения до долговечной регистрации ID сохраняют ограничения [основного контракта](ai-provider-cleanup.md).

Проверки: HTTP на отдельной PostgreSQL БД с настоящим архивным пулом, безопасная проекция ошибок, пагинация при одинаковых timestamps, оба индексных плана без общей сортировки, владелец древа без системного допуска, отзыв допуска и сеанса после начальной аутентификации. Для ручного повтора дополнительно проверяются причины отказа, origin/JSON, отзыв сеанса/членства/допуска, два одновременных POST, неизменность snapshot и 45-секундный срок, аудит ровно один раз. SQLite показывает отсутствие долговечной очереди; браузерные desktop/mobile проверки покрывают кнопку, ответы 409/503 и сохранение несохранённого черновика общих настроек. Реальный провайдер и рабочие диалоги в тестах не используются.
