# Граница доступа к системным копиям и восстановлению — 2026-10-05

Аудит выполнен по `1030ef7a62ec90997fcd8f0d067fa8a959efe9d8` для PostgreSQL и пяти HTTP-маршрутов ниже; затем добавлены отдельные синтетические проверки отсутствовавших порядков отзыва. Это не новая гарантия для SQLite, внешнего хранилища или всех операций с копиями. На исходной базе PostgreSQL job `111660288727` run `37278328427` сообщил `SUCCESS`; новые тесты требуют точного Linux CI после интеграции. Квоты и тарифы не являются заменой проверке сеанса, членства, владения и платформенного права.

Запрос к выбранному `/a/{archiveId}/api/...` сначала проходит `archiveRoutePool` с `directory.contains(accountId, archiveId)` (`src/server/index.ts:272–299`, `src/server/archive-route-pool.ts:37–91`). Он запускается в runtime именно этого `archiveId`; `backupCoordinator`, `restoreHttp` и `databaseBackupHttp` получают соответствующую `archive.db` (`src/server/index.ts:303–324`, `src/server/archive-http.ts:154,222`). Начальное разрешение маршрута не считается финальным: SQL ниже проверяет `db.archiveId` снова. `postgres-runtime.ts` уже проверял выбранную SQLite-копию, TAR и managed backup для `other-archive`; новый `postgres-restore-guard.ts` проверяет actual HTTP preview/apply другого архива, отдельный stage и revision, неизменность root-архива и расход stage только в выбранном архиве.

При отказе до claim create не оставляет нового `backup_job` или upload (тест с fake remote выше). При откате restore после подготовки копии восстановленных originals/attachments удаляются, revision не меняется и stage остаётся для повторной проверки (`restore.ts:1139–1167`, `postgres-restore-guard.ts`). Предварительная страховочная SQLite-копия `before-import-*` создаётся **до** финальной archive-write транзакции (`restore.ts:872–889`) и при позднем отказе может оставаться серверным recovery-артефактом; это не частично восстановленный архив и не выдача файла клиенту. Отказ preview после stage-подготовки также не обещает немедленного удаления stage: apply требует авторство/срок/свежие права, а GC чистит истёкшие stage (`restore.ts:385–405`).

Истечение `account_sessions.expires_at` — отдельное условие от удаления сеанса: конечные PG-проверки сравнивают сохранённое время с `Date.now()` (`backup-coordinator.ts:193–198`, `restore-http.ts:91–98`, `account-session-guard.ts:9–36`, `database-backup-http.ts:58–65`). Отдельного route-specific теста естественного истечения **между подготовкой и финальной проверкой** для этих пяти маршрутов нет. Пятсекундный предел выдачи preview ограничивает зависший ответ, но не заменяет проверку срока сеанса; account tier и квота также не заменяют ни одну из этих границ.

На Windows штатный локальный PostgreSQL runtime остановился на прежнем symlink assertion. Отдельная **диагностическая**, не включаемая в commit копия harness пропустила эту и следующие Windows-зависимые проверки disk reservation/кириллического поиска; новые R2-маркеры и HTTP selected preview/apply прошли на отдельной disposable БД. Диагностическую копию нельзя считать полным штатным прогоном: точный Linux CI объединённого head обязателен.

Вывод ограничен перечисленными сценариями и статическим прослеживанием остальных комбинаций. Подтверждённого пути, где завершённый отзыв допускает новый backup claim, первый байт копии или restore commit, не найдено. После точного Linux CI этот документ завершает конечную матрицу R2; он не обещает проверку всех возможных внешних хранилищ и сочетаний отказов.
