# Технический аудит Drevo — 6 октября 2026

## Executive summary

**Production readiness: 6/10.** Текущий небольшой семейный архив работает на PostgreSQL, имеет настоящую серверную изоляцию доступа, защиту совместных правок и большую автоматизированную проверку. Переход на PostgreSQL завершён; переписывать backend или менять СУБД ради устранения найденных проблем не требуется.

Главные ограничения перед расширением публичной эксплуатации: уязвимая версия Sharp, буферизация больших запросов до проверки авторизации, все резервные копии на том же сервере, несогласованный бюджет PostgreSQL-соединений и неверное владение жизненным циклом фонового ИИ-запроса. Для больших архивов существенны стоимость полного снимка, чтения источников, подготовка медиа и холодная раскладка. Обнаружены конкретные нарушения доступности. Подтверждённой критической уязвимости, обхода авторизации или повреждения текущей БД не обнаружено; это не является гарантией отсутствия таких дефектов.

**Всего: 20 основных замечаний — HIGH: 3, MEDIUM: 14, LOW: 3; CRITICAL: 0.** Замечания объединены по первопричине. Уязвимость зависимости, эксплуатационный риск, долг и измеренная проблема производительности обозначены отдельно. Исходники и production-данные во время аудита не исправлялись.

## Фактическая архитектура

```text
Browser: React 19 / Vite / React Flow / Leaflet / PDF reader / AI chat
  ├─ domain: родство, статистика, изменения, импорт/экспорт
  ├─ Worker: ELK + ограничения поколений + маршрутизация
  └─ HTTP / SSE
       ↓
Nginx: TLS, HTTP/2, gzip, раздача/проксирование
       ↓
Node.js 22: node:http, явная маршрутизация и сборка зависимостей
  ├─ аккаунты, сессии, платформенные настройки
  ├─ pool runtime отдельных архивов
  ├─ проверки роли, области чтения, авторства и revision
  ├─ прикладные сервисы / чистый domain
  └─ фоновые ИИ-задачи и периодические проверки
       ↓
PostgreSQL 18: общие аккаунты + данные архивов + RLS + JSONB/проекции
Local filesystem: оригиналы, previews, ключи, переносимые копии
Yandex AI / OAuth / почтовый провайдер / географические сервисы
systemd timers: pgBackRest/WAL, медиа-копии, health, restore-check
```

Это модульный монолит, не Express/Nest и не ORM: SQL находится в конкретных store-модулях за `StoreDatabase`. PostgreSQL — production; SQLite — локальный/совместимый адаптер. Серверное состояние архива собирается по требованию. Redis и отдельной очереди брокера нет. WebSocket не используется для ИИ: ответы идут по SSE с keep-alive; долговременное состояние хранится в БД, исполняющий процесс имеет локальное состояние.

Роли платформы `admin`/`researcher`, тариф, владелец архива, местные `relative`/`reader` и область чтения — отдельные сущности. «Кровные» включает кровных родственников, их записанных партнёров одним шагом и непосредственного второго родителя кровного потомка; обход не должен продолжаться через добавленного партнёра. Публичный просмотр всего древа по ссылке отделён от согласия на публикацию людей в межархивном поиске.

Основные точки: `src/main.tsx`, `src/App.tsx`, `src/server/index.ts`, `src/server/archive-http.ts`; бизнес-правила в `src/domain`, UI в `src/components`, операции в `ops`, регрессии в `tests`. Типизированные контракты и серверная повторная валидация ограничивают доверие к браузеру. Периодические задачи реализованы Node-таймерами и systemd, а не отдельным cron-приложением.

### Что облегчает и затрудняет развитие

Новые правила родства и форматы проще добавлять через чистый domain и его тесты. Внешний ИИ не связан напрямую с SQL. Замена PostgreSQL на MySQL потребует переделки RLS, SQL, миграций и операций восстановления и не решит найденные проблемы. UI, HTTP и domain разделены, но `App` и обработчик документов объединяют слишком много разных жизненных циклов (D18). Многопроцессность проверялась на общей файловой системе; перенос на разные машины требует общего хранения и пересмотра владельца задач (D05).

Анализ статических runtime-импортов не нашёл циклов; type-only зависимости исключены. Это не доказательство отсутствия динамических связей или сложного callback-coupling.

## Реестр проблем

### [D01] Sharp содержит HIGH advisory; два пути декодируют изображение до проверки формата

Категория: Security / dependency / upload.  
Severity: HIGH.  
Priority: P1.  
Confidence: HIGH.

Где: `package.json:58`, `ops/runtime/package.json:19`, `src/server/ai-attachments.ts:78`, `src/server/discussion-attachments.ts:60`.

Что происходит: установлена версия 0.35.4. Advisory librsvg затрагивает версии до 0.35.5. Прикрепления ИИ и обсуждений вызывают `sharp(...).metadata()` раньше проверки допустимого `format`.

Почему это проблема: обычные фото/документы имеют сигнатурные проверки до декодирования, но эти два пути не дают такой же гарантии. По advisory возможен опасный сценарий обработки SVG при определённых Linux/glibc/Node-условиях. **RCE на текущем сервере не подтверждено**, вредоносные файлы не отправлялись. [GitHub advisory](https://github.com/advisories/GHSA-wq5f-xc86-pv6w).

При каких условиях проявится: доступный пользователю путь прикрепления плюс соответствующие условия уязвимого декодера.

Последствия: потенциальное нарушение безопасности процесса; риск не следует понижать из-за отсутствия PoC.

Как воспроизвести: безопасно проверить lockfile и `npm audit` отдельно для root/runtime; сопоставить порядок декодирования и фильтрации в указанных функциях.

Как исправить: обновить оба manifest/lockfile до исправленной Sharp; передавать в декодер только разрешённые сигнатуры, отключить SVG-декодирование там, где оно не требуется. Проверить обычные изображения, несовпадение заявленного MIME/сигнатуры и previews.

Сложность исправления: S.

### [D02] Nginx буферизует до 12 GB перед серверной авторизацией восстановления

Категория: Security / API abuse / infrastructure.  
Severity: HIGH.  
Priority: P1.  
Confidence: HIGH.

Где: `ops/nginx.conf:105`, `ops/nginx.conf:113`, `src/server/restore-http.ts:51`; проверена действующая конфигурация Nginx.

Что происходит: restore-preview locations разрешают `client_max_body_size 12g`, не выключают request buffering и не имеют наблюдаемого edge-ограничения одновременных таких тел. Авторизация выполняется приложением после проксирования.

Почему это проблема: default `proxy_request_buffering on` позволяет Nginx сначала принять тело запроса, включая временный файл, и только потом обратиться к backend. Правильные права приложения не защищают эту более раннюю стадию. [Nginx reference](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_request_buffering).

При каких условиях проявится: большие или несколько параллельных неавторизованных запросов. На сервере при проверке было около 14 GB свободного места на корневом разделе.

Последствия: истощение временного диска, ошибки загрузок, WAL или локальных копий. Сценарий оценён по конфигурации; нагрузочная атака не выполнялась.

Как воспроизвести: сравнить точные locations с настройкой buffering и местом временных файлов; безопасный тест стриминга проводить только в изолированном стенде с маленьким лимитом.

Как исправить: отключить buffering для этих больших upload-paths, согласовать HTTP/1.1 upstream и раннее отклонение доступа, ввести ограничение одновременных тел и отдельный бюджет временного диска. Одного уменьшения application-limit недостаточно.

Сложность исправления: S.

### [D03] Все копии и WAL находятся на том же диске и сервере

Категория: Backup / disaster recovery / production blocker.  
Severity: HIGH.  
Priority: P1.  
Confidence: HIGH.

Где: `ops/postgres/local-backup.conf.example:7`, `ops/postgres/local-media-backup.sh:1`, `docs/postgres-migration.md`; фактические `/var/lib/pgbackrest` и media-backups на том же `/dev/vda2`.

Что происходит: pgBackRest, WAL и ежедневная копия медиа работают, но внешней копии нет. Это ранее согласованный локальный этап, а не вновь возникшая регрессия.

Почему это проблема: удаление/потеря сервера или диска уничтожит и оригиналы, и эти копии. Репозиторий не восстанавливает семейные данные, медиа и ключи. `archive_timeout=0` также не задаёт верхнюю временную границу принудительного отправления WAL при малой активности. [PostgreSQL reference](https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-ARCHIVE-TIMEOUT).

При каких условиях проявится: утрата диска/хоста; для WAL — тихая БД до закрытия сегмента.

Последствия: отсутствие гарантированного RPO/RTO полного восстановления.

Как воспроизвести: только сверка mount/storage и безопасная репетиция на отдельном экземпляре; production не восстанавливать поверх себя.

Как исправить: настроить независимую зашифрованную копию БД/WAL, оригиналов и нужных ключей; выбрать допустимый archive_timeout; выполнить полное восстановление на другой машине, измерить RPO/RTO. До появления внешнего хранилища явно сохранять статус «локальный этап».

Сложность исправления: M, требуется внешнее хранилище.

### [D04] Сумма пулов превышает бюджет соединений PostgreSQL

Категория: Backend / DB / capacity.  
Severity: MEDIUM.  
Priority: P1.  
Confidence: HIGH.

Где: `src/server/store-database.ts:180`, `src/server/archive-route-pool.ts:14`, `src/server/index.ts:340`.

Что происходит: один Pool имеет `max: 10`, корневой runtime и до четырёх архивных runtime могут суммарно потребовать 50 соединений. В production `max_connections=30`, из них 3 зарезервированы: обычным процессам доступны 27, включая прочих потребителей.

Почему это проблема: текущие четыре app-соединения не означают корректность верхней границы. Пулы растут по спросу, а multi-archive нагрузка сталкивается с лимитом раньше локального `max` каждого пула.

При каких условиях проявится: параллельные чтения/записи нескольких архивов или второй backend.

Последствия: ожидание соединений до 5 секунд, отказы и рост latency. При текущей небольшой нагрузке исчерпание не наблюдалось.

Как воспроизвести: суммировать конфигурационные бюджеты; тест насыщения — на отдельном PostgreSQL с такими же лимитами.

Как исправить: конфигурируемый общий бюджет процесса и меньшие архивные пулы либо безопасно разделяемый пул с транзакционным tenant-context. Учесть второй процесс, backup и операционные подключения; не увеличивать лимит БД вслепую. Сохранить RLS и сброс контекста.

Сложность исправления: M.

### [D05] Жизненный цикл runtime связан с HTTP-соединением, а не продолжающейся ИИ-задачей

Категория: Backend / AI / lifecycle / reliability.  
Severity: MEDIUM.  
Priority: P1.  
Confidence: HIGH.

## Backend и API

Основные API ручного HTTP-router расположены в `src/server/index.ts`, `archive-http.ts`, `archive-query-http.ts`, `documents-http.ts`, `media-http.ts`, `ai-research-http.ts` и профильных auth/admin handlers. Архивные маршруты доступны через `/a/{archiveId}/api/...`; глобальные настройки и аккаунты имеют свою границу. Большие ответы, SSE и выдача медиа имеют отличный от обычного JSON жизненный цикл — поэтому референс runtime нельзя освобождать только по socket-close (D05).

| Семейство | Права/контракт | Проблема или результат |
|---|---|---|
| Snapshot / overview / people search / details | Текущая сессия, scope, revision; AJAX-страницы | D08: часть страниц начинает с полного scoped снимка |
| Changes / connections / import | Серверная валидация, допустимая роль/авторство, проверка revision | Сохранение связи одним изменением; конфликт не перезаписывает новый снимок молча |
| Documents / citations / discussions | Доступ к документу/карточке, авторство, лимиты, страницы | D09/D10: JSON-backlinks и PDF-подготовка |
| Media / preview / Range | Право на оригинал, private cache policy, guards выдачи | D07: busy preview превращается в original fallback |
| AI chats / SSE / tools / proposals | Доступ к ИИ и данным, пользовательский контекст, подтверждение | D05; прямого SQL интерфейса у модели нет |
| Invitations / members / participant preview | Владелец/разрешённая местная роль, ограниченное членство | Preview не должен назначать global role; это подтверждено существующими тестами |
| Platform configuration / users / backups | Глобальные полномочия; тариф и роль не смешиваются | Отдельно от управления своим древом |
| Sharing / discovery | Отдельное согласие/публичная проекция и отзыв | Приватный архив не автоматически индексируется межархивным поиском |

Используются осмысленные HTTP-ошибки авторизации/конфликтов и request ID. Основные изменения защищены revision; это лучше безусловного retry POST. Идемпотентность повтора зависит от конкретной команды: нельзя автоматически ретраить произвольное создание и восстановление, не проверив marker/revision. Формальная публичная OpenAPI-спецификация и отдельное версионированное стороннее API не подтверждены; пока это внутренний контракт web-клиента. Для нового публичного API потребуется договор совместимости, но отсутствие `/v1` само по себе не объявлено багом.

В async-пути используются pg Pool, файловые promises, потоки выдачи. Главные ограничения ресурсов — D04, D05, D07, D10. Доказанного sync-over-async, deadlock или утечки socket/file-handle в проверенных путях не найдено. Большие сериализации/JSON.parse могут занимать event loop даже при асинхронной БД (D08). Не предполагается, что вся обработка изображений идёт в JavaScript: Sharp использует native-процессинг, но его CPU/RAM всё равно общий ресурс хоста.

## База данных и целостность

### Текущее состояние

Production: **PostgreSQL 18.6**, локальный Unix socket, TCP-listener БД выключен. Рабочая роль не superuser и не BYPASSRLS. При проверке: 2 архива, 162 человека, 99 фото, 13 документов, БД около 29 MB. Это текущий агрегат, а не доказательство поведения многомиллионной БД.

Схема сочетает JSONB для семейного документа и типизированные таблицы/индексы связей, аккаунтов, членства, квот, публикаций и задач. PK/FK и archive-context не заменены клиентскими проверками. FORCE RLS включён на 60 таблицах. Числовые/датовые семейные инварианты дополнительно проверяются domain; PostgreSQL не является единственным валидатором произвольных полей JSON.

Миграции PostgreSQL в `ops/postgres`, SQLite в `src/server/schema.ts` применяются последовательно. Переезд завершён без двойной записи. Для SQLite сохранён compatibility-path; удалять его только потому, что production на PG, без решения о локальном режиме нельзя. Миграционный rollback через восстановление копии отличается от отката приложения: совместимость схемы необходимо учитывать до активации предыдущего release.

Изменения одного архива сериализуются блокировкой его строки (`store-database.ts:296`) и revision. Это уменьшает вероятность частичной записи и lost update, но ограничивает параллельные записи в один архив. Точечные person patches уже обновляют нужную окрестность; старое замечание «каждая правка переписывает всё» не подтверждено для всех команд. Read-only snapshots и TTL контекста препятствуют чтению после окончания транзакции.

### Текущие и будущие bottleneck

- Сейчас: первый расчёт сложного графа, подготовка холодных previews/PDF, стоимость загрузки крупных модулей на слабом устройстве. На малой production-БД постоянное исчерпание CPU/RAM не наблюдалось.
- При росте одного архива: JSON parse/projection/serialization, полный поиск и источники, большая геометрия, браузерный рендер и перечитывание после revision.
- При росте числа архивов: opening/eviction runtime, общий бюджет соединений, общие queues/native CPU, локальный диск/backup.
- При всплеске: прежде полезно ограничить admitted expensive work и измерить p95/p99, чем увеличивать pools и бесконтрольно параллелить Sharp.

В сборке крупные ленивые модули: Human около 1,56 MB, ELK Worker около 1,42 MB, PDF Worker около 1,265 MB, ECharts около 593 kB, discussion chunk около 537 kB до gzip. Это **не сумма начального bundle**: динамические границы уже есть. Предупреждение Vite >500 kB само по себе не основание удалить функциональность; проверить Network на конкретном первом пути и загрузку модулей только при необходимости.

Nginx настроен на gzip и HTTP/2; static assets могут кэшироваться отдельно. Private no-store медиа связан с отзывом прав и не записан как ошибка «нет кеширования». Ускорять его допустимо только сохранив авторизацию/отзыв. Brotli/CDN/HTTP/3 не проверены как рабочие возможности, для нынешнего размера не являются обязательным условием исправления.

**Не удалось проверить** репрезентативные production LCP/INP/CLS/TTFB и полевые Core Web Vitals. HTTP 200 без console-errors не заменяет Web Vitals. Возможные причины плохого INP: cold-layout ожидание, large parse/render, длинные main-thread операции; LCP — сеть/портреты/инициальный UI. Числа без измерений не присвоены.

## Нагрузка и масштабирование

Сервер при чтении состояния: 3 logical CPU, RAM 3398 MiB, swap 2047 MiB, корневой диск 30 GB с примерно 14 GB свободными; idle app cgroup около 86,7 MiB, 0 рестартов. Эти данные не описывают его пиковую нагрузочную ёмкость.

| Одновременно | Оценено по архитектуре, не измерено на production |
|---:|---|
| 1 | Нынешний малый архив; холодная геометрия определяется топологией, не числом зрителей |
| 10 | Вероятно посильно обычное чтение небольшого архива; параллельные AI/PDF/restore и разные архивы существенно меняют картину |
| 100 | Нужен benchmark: крупные ответы и общий CPU/PG budget могут дать деградацию; четверых «открытых архивов» недостаточно для гарантии 100 читателей |
| 1 000 | На этой машине готовность не доказана; pool admission/соединения и CPU/медиа вероятны раньше максимума HTTP-сокетов |
| 10 000 | Не поддерживаемая текущими измерениями цель; текущий один хост, local storage и очереди нельзя считать готовыми |

Пользователь с уже загруженным древом почти не равен пользователю, одновременно вызывающему expensive API. Количество соединений нельзя вычислить как «один пользователь — одно PG-соединение». Latency/throughput/процент отказов для 100–10k не выдумываются.

Всплеск нескольких архивов: сначала ограничивает runtime admission (до четырёх и 5 s ожидания), либо бюджет PG и CPU JSON/native-задач в зависимости от запросов. Для больших upload — диск до приложения (D02). Для сложного древа задержка часто браузерная геометрия, не backend SQL.

**Можно запускать два backend на одном shared volume**, что проверялось отдельно; общие сессии/данные в PG не требуют обычной sticky-session. Но локальные ИИ-исполнители и фоновые ресурсы нельзя считать автоматически переносимыми между узлами. Горизонтальный запуск на разных серверах требует общего оригинального хранилища/ключей, ясного ownership/lease задач, согласованных quotas и общего budget БД. Local previews можно пересоздавать, оригиналы нельзя. Redis, PgBouncer и брокер выбирать после измерения нужной задачи; микросервисы для исправления D04/D05 не нужны.

## Надёжность, эксплуатация и восстановление

| Отказ | Механизм / фактический статус |
|---|---|
| PG недоступна/медленна | Health проверяет БД; connection timeout около 5 s, SQL/lock budgets есть; D04 может усиливать ожидание |
| Внешний ИИ медленный | Server timeout/cancel, leases и сохранённые chats; SSE keep-alive ~20 s; D05 — отдельная ошибка ownership |
| Клиент отключился | Выдача отсоединяется; медиа освобождает ресурсы, ИИ должен продолжаться, но может попасть под eviction |
| Повтор запроса/двойной клик | Revision/proposal state и серверная повторная проверка; не делать безусловный retry всех мутаций |
| Диск заполнен | Свободное место, quota/reservations, атомарные temporary → final записи; D02 ранняя стадия/D06 retention остаются |
| Повреждённый файл | Проверки форматов и ограничений; D10 не гарантирует ограниченное время декодирования |
| Перезапуск | Durable записи остаются, активные работы имеют явное завершение/отмену; гарантии продолжения произвольного задания после crash не подтверждены |
| Параллельные изменения | Транзакции, revision conflicts, проверка текущей области; блокировка архива сериализует writes |
| Deploy failure | Отдельные immutable release directories, копия перед активацией, health/rollback; схема БД требует отдельно совместимого плана |

Circuit breaker для каждого сервиса не является автоматической рекомендацией: нужен конкретный эффект на повторяющиеся дорогие ошибки. Retry с backoff для read/provider-технических ошибок должен отличаться от повторного применения изменения. В существующей реализации есть timeout/retry механизмы; аудит не объявляет их отсутствующими из-за отсутствия общей библиотеки.

### DevOps / текущая инфраструктура

Systemd запускает непривилегированную рабочую роль; `PrivateTmp=yes`, `ProtectHome=yes`, `ProtectSystem=strict`, `NoNewPrivileges=yes` действуют. Node слушает 127.0.0.1:3107, наружу опубликован Nginx 80/443, PostgreSQL не открыт TCP. env — 0600 root, ключ приложения — 0600 рабочей роли, pgBackRest config — 0640 root/postgres. Значения секретов в отчёт не скопированы.

TLS 1.2/1.3, certificate Let's Encrypt действителен до 22 декабря 2026; работоспособность следующего автоматического продления не проверялась. Docker используется для CI/PostgreSQL restore tests, production deploy — systemd. Отсутствие production Dockerfile само по себе не делает выпуск небезопасным. Наблюдаемой DEBUG-конфигурации или dev-server в рабочем процессе не найдено.

### Backup / RPO / RTO

Локальная цепочка pgBackRest при проверке: 11 копий/элементов chain, последняя differential 6 октября, статус OK, retention-full=2. Архивирование WAL включено, 442 успешных, 0 failed на момент чтения. Ежедневная media-копия 6 октября около 276 MB с checksum; uploads около 276 MB, previews около 43 MB, pgBackRest около 2,4 GB. Health timers выполняются ежечасно. Это не гарантия независимого disaster recovery.

- Если цела локальная копия и потеряны только рабочие media: ориентировочно до суток между ежедневными копиями, при успешном расписании; общий host-loss этим не покрывается.
- DB: восстановление до доступного WAL; при archive_timeout=0 верхняя временная граница неотправленного сегмента не задана.
- Host/disk loss: локальные копии не дают гарантированного RPO/RTO вообще.
- Restore-check timer следующий 1 ноября, автоматическое месячное выполнение ещё не произошло; ручная репетиция октября и CI restore были успешны. Full-machine/off-host recovery и его RTO не измерены.

Резервировать нужно PG/WAL, оригиналы фото/документов, нужные ключи шифрования и конфигурацию восстановления. Previews воспроизводимы. Source/release нужны для совместимой версии схемы. Одного сервера достаточно для небольшого приложения, но один сервер **не может быть независимым хранилищем своей аварийной копии**.

## Privacy

Хранятся семейные имена/даты/родственные связи, места, биографии, источники, пользовательские фото/документы и отметки/face-векторы; отдельно аккаунты, OAuth identifiers/email и сессии. При удалении учтены авторство обсуждений и блокировка владельца/последнего администратора. История и бэкапы имеют retention, физические оригиналы — D06. Remote AI cleanup имеет собственные записи и повторные действия; неизвестный remote ID и копии у провайдера не позволяют обещать мгновенное удаление всех следов. Журнал HTTP полезен для расследования, но полное forensic восстановление цепочки каждого read/proposal не подтверждено (D16).

Нельзя восстановить уже скопированное другим участником/скачанное содержимое простым отзывом ссылки. Сроки хранения и ограничения нужно описывать честно; это свойство экспорта/приватности, а не повод скрывать их в UI.

## Тесты и качество кода

Сильная сторона — содержательные проверки прав, восстановлений, геометрии, конфликта/undo и анимаций, а не один процент coverage. Большой passing-набор не закрыл ownership-баг D05, потому что disconnect, eviction и background task раньше не были проверены вместе.

Приоритетные недостающие регрессии:

1. Mock AI turn + disconnect + runtime eviction, включая очередь разных архивов.
2. Полные budgets соединений при двух процессах и малом `max_connections`.
3. Ready preview при полной очереди и fallback размеров ответа.
4. PDF deadline/termination/параллельный обычный HTTP.
5. axe + screen hit-area на fit-zoom; обе темы, клавиатурный маршрут.
6. Standard-only документ события после GEDZIP export без собственных расширений.
7. Production-like PG checks как обязательный gate exact SHA.
8. Реальные SMTP, off-host restore и целевые внешние генеалогические программы.

Найдены крупные функции/координаторы D18 и намеренные временные решения D06/D20. Catch fallback в media действительно меняет resource-policy (D07); не каждый catch является exception swallowing. По количеству TODO или длине файла дефекты не начислялись. Dead-code и все nullable ветки всей кодовой базы исчерпывающе доказать не удалось; TypeScript/lint проходят, динамическую достижимость всех conditional UI-путей это не гарантирует.

## Технический долг

Отдельно от багов:

- **Опасный эксплуатационный долг:** известный локальный этап DR, отсутствие полного multi-archive/history/backup inventory для безопасного GC, неполная наблюдаемость ресурсов. D03/D06/D16 имеют реальные последствия, а не косметическую ценность.
- **Мешающий развитию:** смешанные lifecycle в D18, coarse snapshot и JSON-citation contracts D08/D09, поддержка двух storage adapters без одного гарантированного CI gate D15, нестандартные export extensions D20.
- **Косметический/организационный:** устаревшие текущие описания D17, уточнение визуальной плотности inherited admin fields. Не ставить эти задачи раньше HIGH и data recovery.

## Целевая архитектура — только оправданные изменения

Сохранить модульный монолит React/Node/PostgreSQL и чистый domain. Добавить ownership lease исполняемых задач к archive-runtime, согласовать общий pool budget, перейти от полного семейного документа к конкретным проекциям там, где endpoint просит страницу или ссылки документов. Разделять обработчики по правам и жизненному циклу, не создавать универсальную абстракцию поверх каждой функции.

Файловые оригиналы остаются отдельным ресурсом; независимое backup-хранилище нужно сейчас, общий объектный storage для нескольких app-хостов — только при такой необходимости. Поддержка PostgreSQL не требует «ещё миграции на Postgres»: требуется довести операции/масштабирование вокруг уже рабочей БД.

- Отдельные real workload benchmarks: маленькие архивы во множестве, 10k один архив, upload/AI всплеск — M.
- Только при подтверждённом спросе: shared original storage и работа разных app-hosts — L.
- PgBouncer/общий executor/дополнительные серверы — решение по измеренному saturation, не предварительная обязательная инфраструктура — M–L.
- Полевые Web Vitals и контролируемое сравнение первых загрузок/долгих сессий — M.

## Не удалось проверить

- Полное восстановление после утраты хоста из независимой копии и его RTO/RPO.
- Нагрузка production на 100/1000/10 000 активных пользователей; синтетические fixtures не заменяют её.
- Фактическая отправка SMTP и доставляемость/конфигурация домена email-входа.
- Произвольные реальные запросы ко всем Yandex-моделям, свежий compaction/rollout и старые неудачные пользовательские чаты. Тесты AI-прав и UI не проверяют все фактические ответы нейросети.
- Поведение всех внешних геокодеров/исторических справочников при текущем сбое провайдера.
- Реальные внешние «Древо Жизни»/другие GED readers для всего обмена, помимо локальных format-tests.
- Все формы/модальные состояния на всех ширинах, физические телефоны, screen readers и полный WCAG 2.2 AA.
- Репрезентативные полевые LCP/INP/CLS/TTFB, HTTP/3/Brotli/CDN и внешняя SEO-индексация.
- Внешний мониторинг, не видимый в доступных серверных services/GitHub; будущая автоматическая выдача сертификата.
- Все классы секретов во всей истории, все динамические зависимости/ветки и отсутствие любой невыявленной уязвимости.

## Что сделано хорошо

- Реальный production PostgreSQL с непривилегированной ролью, archive-context и FORCE RLS; разные права не сведены в один UI-флаг.
- Domain-правила, серверная валидация и revision/conflict защищают совместные изменения; модель ИИ применяет только подтверждённые предложения через прикладной интерфейс.
- Сессии не являются открытыми пользовательскими ID; защищённые cookies/headers и права повторно проверяются перед чувствительной выдачей.
- Оригиналы сохраняются атомарно, uploads имеют лимиты, квоты и reservations; приватный URL сам по себе не открывает файл.
- Геометрия вынесена в собранный Worker; кэш ограничен и содержит access/account scope, не строится огромный Canvas на весь архив.
- Анимационные инварианты и мобильные жесты проверяются браузером, включая reduced motion, входной скрытый кадр и разделение canvas/browser zoom.
- Динамическая загрузка тяжёлых подсистем и раздельные профильные компоненты уже есть; не весь большой JS нужен первому экрану.
- GEDCOM birth surname/coordinates/source data исправлены в текущем коде; импорт собственного расширения не скрывает оставшиеся ограничения стандартного обмена.
- CI содержит PostgreSQL и реальный restore smoke, Actions закреплены commit SHA; immutable releases/health/rollback реализованы.
- Локальная память агента и датированные доказательства существуют; решения о privacy, ролях и исключённых задачах записаны. Нужно устранить конкретный drift D17, а не создавать новую параллельную систему документации.
