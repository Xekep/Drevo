# Пошаговый выбор опубликованной ветки

Владелец архива может продолжить уже выбранную ветку подтверждённой межархивной пары на одну связь за запрос. `GET /api/discovery/matches/:id/branch-share/options/:viaId` показывает страницу до 30 опубликованных соседей выбранной карточки своего архива. `POST` добавляет одну карточку по полученному отпечатку просмотра. Корень пары нельзя использовать как `viaId`: сначала нужно явно выбрать и разрешить ближайшего родственника. Общий предел остаётся 20 выбранных карточек на сторону; прямой выбор родителей, детей, супругов и существующий выбор второго поколения сохраняются.

Промежуточные карточки должны оставаться выбранными и опубликованными. Отпечаток связывает точную пару, ревизию дерева, действующее разрешение со сроком, состав выбранной ветки, версии публикаций корня и всех шагов до `viaId`, а также версию новой карточки. Изменение любого из этих входов требует нового просмотра. Один `person_id` хранится в разрешении только один раз с одним явно выбранным `via_person_id`; альтернативный путь к тому же человеку пока не хранится как отдельное свидетельство. Нет автоматического доступа к произвольной глубине, закрытым соседям, файлам или другим архивам.

Выдача карточки и списка противоположной стороны по-прежнему требует двух действующих разрешений. Перед HTTP-ответом сервер повторно блокирует сеанс, членство и владельца, публикации всей выбранной цепочки, подтверждённую пару и оба разрешения. Отзыв до этой границы закрывает выдачу; отзыв во время короткого ответа ждёт завершения передачи. Медленный ответ ограничен пятью секундами. Отзыв публикации промежуточной карточки удаляет зависимые выбранные карточки через существующий внешний ключ; правка дерева и передача владения отзывают разрешение целиком.

Миграция `092_discovery_branch_depth.sql` меняет только CHECK допустимых видов связи. Существующие строки удовлетворяют более строгому прежнему CHECK; новый CHECK добавляется `NOT VALID`, но проверяет все новые записи. На локальной синтетической таблице из 200 000 строк изменение заняло 0,68 мс; во время транзакции PostgreSQL удерживал `AccessExclusiveLock`, конкурентный `UPDATE` с `lock_timeout=100ms` получил `55P03`. Отдельная `VALIDATE CONSTRAINT` заняла 35,24 мс, удерживала `ShareUpdateExclusiveLock`; конкурентный `UPDATE` завершился за 3,17 мс. Это оценка формы блокировок на тестовом хосте, не замер производственного архива.

После инвентаризации всех архивов оператор выполняет отдельную короткую транзакцию под административной ролью: `BEGIN; SET LOCAL lock_timeout = '1s'; SET LOCAL statement_timeout = '30s'; ALTER TABLE discovery_branch_members VALIDATE CONSTRAINT discovery_branch_members_relation_check; COMMIT;`. Перед этим следует проверить `SELECT convalidated FROM pg_constraint WHERE conrelid = 'discovery_branch_members'::regclass AND conname = 'discovery_branch_members_relation_check';` — ожидается `false`, после успешной операции `true`. При таймауте транзакцию откатывают и повторяют в отдельное окно; запуск приложения эту операцию не выполняет.
