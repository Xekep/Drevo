# Оптимизация отрисовки древа

Раскладка в Worker и отрисовка сцены измеряются отдельно: время ELK не объясняет задержки перемещения уже построенного древа.

## Что оптимизировано

- Пересечения маршрутов кэшируются по геометрии рёбер. Выбор и подсветка связи не требуют повторно искать геометрические пересечения, пока маршруты не изменились.
- `PersonNode` и `RelationshipEdge` используют специализированные comparators и не перерисовывают внутреннее содержимое, когда их значимые входы не изменились.
- Layout worker переиспользуется между последовательными расчётами. Если активный расчёт уже устарел, worker завершается, чтобы старый ELK не конкурировал за CPU с новым расчётом.
- Ответы worker помечены `requestId`, поэтому устаревший результат не может подменить актуальную геометрию.
- Проекция layout по-прежнему содержит только данные, влияющие на геометрию дерева. Текстовые изменения человека не должны сами по себе менять ключ раскладки.

## Проверки

Добавлены отдельные тесты для кэша пересечений и comparator данных карточки человека. Полный `typecheck`, `lint`, `test` и `build` следует запускать перед слиянием в `main`.

## Профиль большого древа, 2 октября 2026

Проверена production-сборка на синтетической семье `randomFamily(5, 9)`:
977 человек, 1290 маршрутов, портреты, viewport 1280×720. Это семья с браками
между ветвями, а не тысяча несвязанных прямоугольников. Фотографии заменены
небольшими SVG-заглушками через тестовый HTTP-маршрут; декодирование реальных
фотографий и сеть пользователя этот замер не воспроизводит.

Браузер — Chrome 155, Windows, GTX 1070, аппаратные Canvas/GPU compositing/WebGL
включены. Для стресс-прогона CPU замедлен через CDP в 4 раза. Запись Playwright
trace отключена: обход DOM при каждом действии искажает измерения. Подробный
CPU-профиль включается отдельно, его запуск/остановка не входят в выборку rAF.

Общий обзор уже использует ограниченный размерами viewport Canvas 2D. При
600+ карточках и масштабе ниже 18% он рисует целую сцену; на меньших деревьях
рисует только миниатюры поверх HTML/SVG. В приближении работают React Flow
и отсечение невидимых элементов. Портреты 48×48 заранее обработаны и кэшируются;
во время движения камеры обзорный Canvas преобразуется одной CSS-матрицей,
затем перерисовывается после остановки.

Найденная лишняя работа: `hidden: true` не отключает внутренние подписки
React Flow. Скрытый `EdgeWrapper` всё ещё вычисляет позиции handles на каждом
обновлении store, а отключённое отсечение сохраняет скрытые `NodeWrapper`.
Обзорный режим теперь передаёт пустой массив рёбер и включает отсечение
скрытых узлов. Метаданные узлов и их размеры остаются для `fitView` и перехода
к человеку; маршруты Canvas и экспорт берут полную геометрию отдельно.

Один контрольный замер одинакового движения мыши туда и обратно (160 шагов),
после окончания раскладки и загрузки изображений:

| Масштаб и операция     | До: JavaScript | После: JavaScript |
| ---------------------- | -------------: | ----------------: |
| 5%, панорамирование    |        3165 мс |            490 мс |
| 17,9%, панорамирование |        3097 мс |            426 мс |

Это суммарное время скриптов в жесте, не время одного кадра и не обещание
такого же ускорения на любом компьютере. В покое в том же стресс-прогоне
скрипты занимали около 12–13 мс за две секунды; непрерывного пересчёта layout
не обнаружено.

Оставшаяся проблема — HTML/SVG и переход между сценами. При 21,5% на экране
119 карточек, 284 связи, около 3940 DOM-элементов. В исходном стресс-прогоне
панорамирование имело p95 интервалов rAF 217 мс, пересечение порога 18% —
400 мс. После устранения скрытых подписок задержки в HTML/SVG сохранились:
большая часть времени уходит в работу браузера со стилями и отрисовкой.
Это обосновало следующий этап с отдельным GPU-слоем. В первом изменении
сравнительного WebGL-прототипа ещё не было; его замеры приведены ниже.

### Следующий этап: единая сцена WebGL

1. Сохранить координаты и маршруты Worker; рисовать линии, портреты и подписи
   в одном слое при любом масштабе. При движении менять только матрицу камеры,
   без пересоздания карточек и загрузки геометрии в GPU каждый кадр.
2. Портреты объединять в ограниченные по размеру атласы текстур, подписи —
   в атлас глифов с кириллицей и SDF/MSDF. Избежать отдельной маски/фильтра
   и отдельной текстуры на каждого человека. Ограничить память, освобождать
   ресурсы при смене архива.
3. Сохранить существующие закругления/разрывы маршрутов, пунктир, выделение,
   оранжевую отметку проверки и реальные разрешённые URL портретов.
4. Оставить HTML для панели человека и небольшой интерактивной накладки:
   приватность, раскрытие ветви, клавиатура и мобильные действия. Проверку
   попадания выполнять по мировой геометрии, учитывая текущую камеру.
5. Рисовать по запросу, без вечного ticker в покое. Предусмотреть потерю
   WebGL-контекста и резервный текущий renderer. PDF/TXT и доступ по общей
   ссылке используют прежние границы данных.
6. Сравнить оба renderer на одной геометрии с реальными разрешёнными
   миниатюрами: 1000 и 3000 человек, обзор/средний/близкий масштаб,
   непрерывный zoom и панорамирование, память, rAF и задержка клика.
   Целевой порог первой проверки — p95 rAF до 33 мс на описанном desktop
   без искусственного замедления CPU; это критерий будущего прототипа.

Подходы для изучения: [Sigma: программы узлов/линий и атлас портретов](https://www.sigmajs.org/docs/advanced/renderers/),
[PixiJS: batching, текстуры и ограничения фильтров](https://pixijs.com/8.x/guides/concepts/performance-tips),
[PixiJS: BitmapText и SDF/MSDF](https://pixijs.com/8.x/guides/components/scene-objects/text/bitmap).
PixiJS — кандидат для прототипа сценического слоя. Sigma полезна как пример
пакетной отрисовки; её стандартные рёбра не заменяют специализированные
генеалогические маршруты Drevo. Зависимость renderer пока не добавлена.

### Воспроизводимый замер

После `npm run build`, в PowerShell:

```powershell
$env:DREVO_LAYOUT_SCALE_E2E = '1'
$env:DREVO_LAYOUT_SCALE_PORTRAITS = '1'
$env:DREVO_RENDER_PROFILE = '1'
$env:DREVO_RENDER_CPU_THROTTLE = '4' # 1 для обычного прогона
$env:DREVO_RENDER_PROFILE_TARGETS = '0.05,0.15,0.19'
npx playwright test tests/e2e/tree-scale-benchmark.spec.ts --project=desktop
```

Порт задаётся `DREVO_E2E_PORT`, внешний Chrome —
`PLAYWRIGHT_CHROMIUM_EXECUTABLE`. Не включать одновременно другие специальные
режимы benchmark (`ALIGNMENT`, `KINSHIP`, `SLOW_THUMB`, `SCREENSHOT`, `CLICK`):
они меняют камеру или загрузку портретов. Без `PROFILE_TARGETS` проверяются
шесть масштабов. `DREVO_RENDER_CPU_PROFILE=1` добавляет CPU-профили в attachments;
полный прогон с замедлением CPU и профилированием может превысить лимит теста,
для него следует выбирать один-два масштаба. JSON с измерениями, сведения о GPU
и снимки состояний сохраняются в результатах Playwright; в production
инструментирование не входит.

## Сравнение с WebGL2, 2 октября 2026

Добавлен отдельный стенд `tests/render-lab`. Он собирается в disposable-каталог
вне репозитория и не входит в production-приложение. Новых зависимостей нет.
Текущая сцена использует настоящие `PersonNode`, `RelationshipEdge`,
`DistantPortraits`, React Flow, его store и отсечение невидимых элементов.
WebGL2-прототип полностью заменяет эту сцену на время своего прогона.
Скрытых HTML-карточек или React Flow под GPU-сценой нет.

Оба варианта получают одну геометрию `unionGeometry`, одинаковый адаптер
узлов/рёбер, портреты, положение камеры и её траекторию. Сохранены скругления,
разрывы путей на пересечениях, пунктир супругов, круглая обрезка и оранжевая
отметка проверки. Позиции портретов дополнительно проверены по пикселям
снимков; на семье 3313 совпали все проверенные точки: 30/30 при 10%,
15/15 при 21,5%, 8/8 при 30%, 20/20 при 17%.

В WebGL неизменные координаты, глифы и линии загружаются в буферы один раз.
Фотографии размещены в ограниченных атласах до 2048×2048; кириллица использует
общий атлас глифов. При движении меняется uniform камеры. На кадр приходится
7 draw calls для 977 человек и 17 для 3313. В покое стенд не рисует непрерывно.
Это следует рекомендациям о пакетной отрисовке и бюджете памяти из
[WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices).

### Методика и границы сравнения

- Windows, headless Chrome 155.0.8059.26, аппаратный GTX 1070,
  viewport 1280×720, DPR 1. Playwright trace и CPU profiler отключены.
- Семьи `randomFamily(5, 9)` — 977 человек, `randomFamily(5, 12)` — 3313.
  На 977 выполнено по три прогона каждого варианта для CPU×1 и CPU×4,
  на 3313 — по два для CPU×1. Порядок рендереров чередуется.
- У каждого человека свой детерминированный JPEG с текстурой и силуэтом:
  `tiny` 48×48 / quality 45, `thumb` 400×400 / quality 76. Общий payload
  обоих размеров — 26,3 МиБ для 977 и 89,2 МиБ для 3313. Это синтетические
  растровые изображения; сеть и обработка фотографий production-сервером
  не воспроизводятся.
- Камера движется по одной функции времени в течение заданных четырёх секунд.
  Измерение начинается после подготовки сцены и загрузки видимых изображений.
  Долгая блокировка может растянуть фактическую длительность жеста.
  Измеряются интервалы rAF, long tasks, CDP Script/Layout/Style/TaskDuration,
  DOM и JS heap. rAF — показатель задержек, а не измерение времени GPU
  или гарантированный FPS пользовательского браузера.
- В этом headless-прогоне стабильный интервал rAF около 31–32 мс у обоих
  вариантов. Разницу нужно искать в задержках и работе CPU; обещать
  ускорение FPS пропорционально сокращению JavaScript нельзя.
- Стенд сравнивает ядро отрисовки. Панели приложения, физические события
  ввода, выбор, приватность, клавиатура, мобильные жесты, восстановление
  WebGL-контекста и fallback в прототипе не реализованы. Тени и типографика
  ещё отличаются: bitmap-глифы требуют улучшения качества и переноса строк.
  Это измерение возможности GPU-слоя, а не готовой замены всех функций.

### Результаты: 977 человек

Обычный CPU. JavaScript — медиана суммарного времени скриптов за один жест
из трёх прогонов; последний ряд содержит максимальную задержку кадра.

| Операция               | Метрика                     | Текущая сцена | WebGL2 |
| ---------------------- | --------------------------- | ------------: | -----: |
| Панорамирование, 10%   | JavaScript                  |         39 мс |   9 мс |
| Панорамирование, 21,5% | JavaScript                  |        418 мс |   9 мс |
| Панорамирование, 30%   | JavaScript                  |        308 мс |  10 мс |
| Панорамирование, 90%   | JavaScript                  |        129 мс |   9 мс |
| Zoom 17% → 23% → 17%   | Максимальный интервал кадра |        531 мс |  32 мс |

При 21,5% текущая сцена монтирует 119 карточек и 284 ребра,
в стенде 3240 DOM-элементов; WebGL — один canvas, всего 12 DOM-элементов.
Нативный p95 при обычном панорамировании около 32 мс у обоих вариантов.

При CPU×4 — медиана p95 трёх прогонов, кроме последнего ряда:

| Операция               | Метрика                     | Текущая сцена | WebGL2 |
| ---------------------- | --------------------------- | ------------: | -----: |
| Панорамирование, 10%   | p95 интервала rAF           |         94 мс |  32 мс |
| Панорамирование, 21,5% | p95 интервала rAF           |        125 мс |  32 мс |
| Панорамирование, 30%   | p95 интервала rAF           |        125 мс |  32 мс |
| Панорамирование, 90%   | p95 интервала rAF           |         32 мс |  32 мс |
| Zoom через 18%         | Максимальный интервал кадра |       4594 мс |  32 мс |

При 21,5% текущий вариант успевает выполнить 48–63 обновления камеры,
WebGL — 129–130. GPU-прототип тоже не без исключений: в обзорном режиме
CPU×4 встречались отдельные интервалы до 281 мс, хотя p95 оставался 32 мс.
На среднем масштабе и при переходе порога таких скачков в этих прогонах нет.
Замедление CPU не заменяет проверку на настоящем телефоне или слабом GPU.

### Результаты: 3313 человек и память

При CPU×1 p95 панорамирования снова около 32 мс у обоих вариантов.
Переход через 18% даёт максимальный интервал **1531–1593 мс** у текущего
варианта и **32 мс** у WebGL. В этом положении камеры на 21,5% видны только
27 карточек и 236 рёбер: размер архива сам по себе не определяет нагрузку.
На 90% центр попадает в промежуток между карточками; этот случай проверяет
линии, но не позволяет делать выводы о производительности близких карточек.

| Явно выделенные GPU-ресурсы    |   977 человек |  3313 человек |
| ------------------------------ | ------------: | ------------: |
| Атласы RGBA8 с mipmaps, оценка |      98,8 МиБ |     318,4 МиБ |
| Статические vertex buffers     |      16,4 МиБ |      73,1 МиБ |
| Сумма                          | **115,2 МиБ** | **391,5 МиБ** |

Это расчёт размеров ресурсов, не измеренный полный VRAM: framebuffer,
multisampling и накладные расходы драйвера не включены. JS heap сохранён
в JSON, но также не показывает всю память изображений и GPU. На 3313 в GPU
сцене наблюдалось около 202 МиБ JS heap; мгновенные значения зависят от GC.

Подготовка WebGL-сцены занимает 1,0–3,3 с на 977 при обычном CPU,
5,2–8,8 с при CPU×4; на 3313 — 14,2–15,3 с при обычном CPU.
Она включает декодирование всех `thumb`, атласы, глифы и геометрию.
Текущая сцена заранее загружает `tiny`, а `thumb` получает только для
монтируемых карточек; время её монтажа не является равнозначным тестом
загрузки всех 400×400 изображений. Сравнительного выигрыша холодной загрузки
эти числа не доказывают.

Вычисление раскладки в Node/ELK перед первым прогоном заняло 18,8–24,4 с
для 977 и **242,3 с для 3313**. Последний результат отдельно сохранён,
геометрия повторно использована для A/B. Это время Node-стенда,
не замер browser Worker. WebGL не ускоряет данный этап.

### Решение по результатам

Единый GPU-слой оправдан для снятия нагрузки CPU и задержки при переключении
Canvas/HTML на 18%. До включения в рабочее древо нужны:

1. Ограниченный кэш атласов для видимой области с запасом, очередь загрузки
   и освобождение ресурсов. Заранее загружать все `thumb` архива слишком дорого.
2. Чёткие глифы, корректная типографика и переносы; проверка качества портретов
   на разных zoom/DPR и сохранение маршрутов без изменения раскладки.
3. Небольшая HTML-накладка для действий, клавиатуры и доступности, hit testing
   по мировой геометрии, мобильные жесты и fallback при потере контекста.
4. Отдельный бюджет времени/памяти layout для 3000+ и проверки на реальных
   архивах. Поколенные ограничения должны сокращать проекцию до расчёта.

После сборки приложения, в PowerShell:


Сборка стенда, геометрия и итоговые JSON находятся в
`$env:TEMP/drevo-render-lab`; снимки и attachments — в output Playwright.
Для повторного запуска допустимо задать `DREVO_WEBGL_GEOMETRY` путём
к `geometry-977.json` или `geometry-3313.json`: проверяются fixture и commit,
локальные изменения domain/dependency запрещают использовать этот кэш.
Если менялась раскладка, следует пересчитать геометрию.

## Рабочий GPU-слой, 2 октября 2026

`TreeGpuScene` включает WebGL2 после завершения раскладки и вступительной
анимации, начиная с 500 видимых карточек в режиме поколений. React Flow
сохраняет камеру и метаданные координат. GPU рисует портреты, подписи, линии,
семейные подложки и оранжевые ободки. Переход через 18% не меняет рендерер.
HTML-карточки остаются только для наведения, клавиатурного фокуса, ограниченного
набора выбранных людей и концов выбранных/дополнительных связей.

Портреты загружаются возле камеры: 48px tiny и 264px плитки из thumb.
Две страницы атласа с mipmaps занимают **26,7 МиБ** при бюджете 32 МиБ
(tiny хранится в одном канале), максимум шесть одновременных загрузок;
LRU освобождает плитки вне области. При повышении качества сохраняется tiny.
Для качества действует гистерезис: thumb включается выше 34%, tiny возвращается
ниже 26%. Это предотвращает повторные переключения возле границы при зуме.
Изменение выделения не сбрасывает кэш. Перед первым включением GPU прежняя
сцена остаётся видимой до готовности портретов или двухсекундного дедлайна.
При смене архива, удалении фотографии
или отзыве общей ссылки старые запросы и ресурсы освобождаются.

Общий атлас глифов с mipmaps занимает 5,33 МиБ. Геометрия ограничена 24 МиБ;
штриховка вычисляется фрагментным шейдером вместо тысяч отдельных квадратиков.
При движении внутри подготовленной области обновляется камера; новые буферы
портретов нужны при выходе за запас, загрузке фотографии или смене выделения.
Canvas ограничен viewport, DPR≤2 и 2,5 млн пикселей. Эти бюджеты не включают
framebuffer, MSAA и внутренние расходы драйвера.

При отсутствии аппаратного WebGL2, потере контекста, превышении бюджета,
неподдерживаемых маршрутах, внешних/анимированных портретах или необходимости
сложного shaping текста используется прежняя сцена. Для более 64 выбранных
или дополнительных SVG-связей также сохраняется нативная отрисовка.
При перетаскивании конца связи временно доступны все обычные ручки React Flow.
Хронология, веер и вступительная анимация сохраняют свои рендереры.
Экспорт получает полную модель, независимо от экранного слоя.

## Готовые поколения вместо плотного промежуточного графа ELK

После профилирования ELK 0.12 найден дорогой промежуточный шаг:
`PartitionMidprocessor` соединяет каждый блок одного поколения с каждым
блоком следующего. Число временных рёбер внутри компоненты равно
`Σ nᵢ × nᵢ₊₁`. У fixture `randomFamily(5, 9)` из 977 человек это
652 блока союзов, 965 реальных рёбер и ещё 48 877 временных рёбер.
Затем этот граф обрабатывает Network Simplex. Второе дорогое место —
`SortByInputModel`, который сортирует слои вставками и поддерживает
транзитивные множества порядка.

На проекциях больше 300 человек `presetGenerationLayers` передаёт ELK уже
вычисленные поколения через реальные координаты `node.y` и
`layering.strategy=INTERACTIVE`, отключая `partitioning.activate`.
Интервалы поколений не перекрываются: шаг учитывает наибольшую высоту блока
в каждом поколении. Метаданные поколений остаются для `generation-bands`.
Проверка требует плоский граф DOWN с известными портами и только связями
из старшего поколения в младшее; при несовместимом входе используется
прежний solver. Фиксированные порты, порядок модели, crossing minimization,
seeds, перестановки супругов и маршрутизация сохранены. Инкрементальный
sketch ограничен 200 людьми и не пересекается с новым режимом.

## 2026-10-02: минимизация пересечений широких поколений

На проекциях больше 900 человек отключена дорогая сортировка `NODES_AND_EDGES`.
В ELK 0.12 она выполняет два прохода сортировки каждого слоя и сохраняет
транзитивные множества порядка. Одного `NONE` оказалось недостаточно:
несколько тестовых деревьев рассчитывались быстрее, но получили больше пересечений.

Теперь сравниваются два профиля с `considerModelOrder.strategy=NONE` и обычным
`LAYER_SWEEP`:

- `greedy`: thoroughness 1, затем двусторонние перестановки соседних блоков;
  `greedySwitch.activationThreshold=0` включает эту стадию и на больших графах;
- `sweep`: thoroughness 12 и стандартный порог greedy switch 40.

До 2000 человек каждый профиль проверяется с seeds 1 и 15, выше — с seed 1.
При отсутствии семейных контактов дополнительные расчёты пропускаются.
Кандидат должен улучшить число или повторяемость семейных контактов и пройти
проверку всех видимых маршрутов: contacts/crossings не растут, длина ограничена
15%, число изгибов — 15% + 2, проходы через карточки и наложения не увеличиваются.
Сохраняются прежние ограничения размеров раскладки и последующая локальная
оптимизация супругов и семей. Эти проверки сравнивают кандидата с текущим
лучшим вариантом; старая дорогая раскладка в браузере дополнительно не вычисляется.

До 900 человек настройки и число попыток сохранены. Поколения, фиксированные
порты, отдельные карточки и генеалогические записи не меняются. Геометрия больших
деревьев может измениться, поэтому версия кэша поднята до 10.

Не включены в рабочий код: группировка терминальных детей (усложнила порядок
и ухудшила часть маршрутов), `MEDIAN_LAYER_SWEEP` (резко увеличил пересечения
на проверенных больших графах), одиночный профиль `NONE`.

## 2026-10-02: один проход оценки семейных маршрутов

При проверке перестановок супругов и соседних семей ранее отдельно вычислялись
`branchContactCounts` и `routingQuality`. Оба прохода строили пространственный
индекс одних и тех же сегментов. Теперь для геометрии без дополнительных
отношений один проход сохраняет две оценки: уникальные семейные контакты
и сырое число касаний пар сегментов, а также пересечения, длину, изгибы
и контакты по группам.

Результат кэшируется в `WeakMap` внутри одного вызова `unionGeometry`.
Готовые геометрии кандидатов не изменяются; новые перестановки создают новые
объекты. При наличии дополнительных маршрутов сохраняются прежние отдельные
оценки семейных линий и всех видимых отношений. Не менялись условия принятия
кандидатов, число попыток, порядок супругов, координаты и версия кэша раскладки.

На 977 людях медиана трёх чистых чередующихся пар AB/BA/AB снизилась
с 6,05 до 5,49 с, на 9,3%. Полная геометрия совпала побайтно во всех
15 сравнениях: большие деревья, дополнительные связи, циклы, повторные
предки, оба направления и перерасчёт после редактирования. Входные данные
сохранены, проверки фактов, поколений, карточек и маршрутов пройдены.

На одиночных парах 503 и 782 человека полное время почти не изменилось:
6,87 → 6,93 с и 15,46 → 15,39 с. Время самого ELK заметно варьировалось.
Остаток `layoutMs − elkMs` полезен для диагностики, но не является отдельным
замером доменного алгоритма. Ускорение на 977 относится к полному расчёту
в Node 22.14 на Ryzen 9 5950X; браузерный FPS на этом этапе не измерялся.
Объединённый проход вычисляет качество и для части ранее отброшенных
кандидатов, поэтому выигрыш нельзя переносить на любой архив.

Шесть новых тестов сравнивают оценки с прежним подсчётом и независимым
перебором пар сегментов. Проверяются общие семейные шины, повторные
сегменты, касания, пересечения, наложения, идентификаторы групп, пустые
маршруты, дополнительные отношения и отсутствие мутации. Отдельный
случай защищает точный порядок сложения дробных длин.

Полные метрики и хеши: [исходные замеры](benchmarks/layout-contact-score.json).

## 2026-10-02: холодный запуск приложения и очередь портретов

Сквозной замер обнаружил задержку после завершения раскладки: React Flow
сначала монтировал большой вид при zoom 1, до первого `fitView`. Карточки
успевали запросить портреты `thumb` всего архива. В двух исходных прогонах
на 977 людях первый GPU-слой появлялся через 40,35 и 39,65 с от начала
навигации, хотя запрос Worker завершался за 3,94 и 3,98 с. Каждый прогон
запрашивал 977 `thumb`, около 26 МБ, с пиком 983/984 незавершённых
media-запросов. Это задержка запуска сцены, а не время самого ELK.

Теперь загрузка обычных портретов откладывается до готовности начальной
камеры и на время больших переходов или передачи сцены GPU. Для вступления
на 500+ карточках существующий Canvas выбирается ещё до первого
позиционирования камеры. React Flow получает скрытые карточки с прежними
координатами и размерами. Промежуточный вариант камеры использовал
`fitView` с `includeHiddenNodes`; теперь вписывание рассчитывается прямо по
геометрии Worker, независимо от DOM-измерений. Минимальный бюджет вступительной
анимации 2,2 с сохранён только для 2500+ карточек. На больших архивах
отсечение остаётся включённым при переходе к малой проекции. Учитываются
размер исходного архива и отображаемые узлы, включая уходящие: асинхронное
принятие новых nodes в store React Flow не должно временно отключать
отсечение для ещё сохраняющегося полного вида.
Canvas получает портреты текущей проекции. Scope GPU сохраняется при
открытии карточки человека внутри архива, но различает архивы, разрешения общих
ссылок, аккаунты и параметры доступа.

Дополнительный профиль переходов выявил особенность React Flow:
`forceInitialRender` пропускает узлы через viewport culling, пока неизвестны
границы handles. После GPU-режима это могло снова монтировать весь архив
для измерения карточек. В модель добавлены статические handles через
публичное поле `Node.handles`: четыре стороны карточки с размерами,
соответствующими CSS, и пустой список у декоративных household-узлов.
Существующие DOM-handles и действия со связями сохранены; изменения
координат Worker и патчей исходников React Flow нет.

В профиле также обнаружены синхронные чтения layout observer-ом кнопки
ИИ-ассистента после изменений DOM дерева. При выключенном ИИ этот observer
теперь не подключается. При включённом ResizeObserver, resize/fullscreen и
изменения нужных панелей объединяют измерения в один `requestAnimationFrame`.
MutationObserver реагирует на появление/удаление панелей управления,
а не на каждую смену карточек или GPU-слоя; отложенные измерения отменяются
при cleanup.

### GPU-подписи: в буфере только текущий масштаб

На 3313 людях проявился отдельный предел: прежний GPU-буфер одновременно
хранил варианты подписей для всех масштабов и превышал бюджет 24 МиБ,
из-за чего приложение переходило к нативной отрисовке. Бюджет сохранён;
теперь в GPU загружается только вариант текущего масштаба.

При создании сцены прежние раскладки текста сохраняются в трёх CPU-массивах
`Float32Array`: zoom ниже 0,18, от 0,18 до 0,52 и от 0,52. Сохранены тот же
атлас шрифта, измерение и размещение glyphs, переносы строк, подписи household,
цвета и условия отображения. Первый кадр выбирает нужный массив; при
пересечении порога 0,18 или 0,52 один `gl.bufferData` заменяет содержимое
того же буфера подписей. Панорамирование и zoom внутри одного диапазона
не требуют такой загрузки. Другие буферы, координаты и маршруты Worker,
layout-кэш и его версия не меняются.

Компромисс — хранение трёх готовых массивов в памяти CPU и передача одного
из них при смене диапазона. В отдельном успешном прогоне 3313/desktop/CPU×1
суммарные GPU-буферы занимали около 10,55 МиБ в дальнем виде и 14,49 МиБ
в ближнем, CPU-массивы подписей — около 18,53 МиБ. Последнее не является
всей памятью main thread или пиком создания сцены. Текущие размеры и LOD
экспортируются через `data-gpu-label-bytes`, `data-gpu-label-cpu-bytes` и
`data-gpu-label-lod`; при уничтожении сцены ссылки на CPU-массивы очищаются.

В этом прогоне первый GPU-слой появился через 10,46 с, после persistent
reload — через 7,90 с. Все фазы прошли без GPU fallback. Это промежуточная
одиночная проверка 3313 на данном устройстве, до следующих изменений
кэширования и вступления; итоговая последовательная матрица CPU/mobile
приведена отдельно ниже. Загрузка подписей текущего
масштаба не означает устранения задержек пересборки сцен или переключений
проекции, а предыдущие long tasks нельзя автоматически приписывать новому
состоянию GPU-кода.

### Persistent-кэш и устойчивое вступление при загрузке деталей

Проверка 3313/CPU×4 воспроизвела ещё одну ошибку: после первоначального
расчёта в IndexedDB оставалось ноль записей. Срок фоновой записи 1000 мс
истекал при занятом main thread подготовки большой сцены, и операция
прерывалась. Срок записи увеличен до 5000 мс, чтения — со 150 до 500 мс;
лимиты размера, числа записей и возраста кэша сохранены. Запись остаётся
необязательной и не ожидается для показа дерева. Ошибка или недоступность
хранилища ведёт к обычному расчёту; медленное чтение может теперь задержать
его запуск дольше. Эти сроки обслуживаются event loop, поэтому не являются
жёстким пределом реального времени при блокировке main thread.

Загрузка подробных карточек заменяла массив `people` 21 раз — по числу
страниц в проверенном архиве 3313. Даже неизменные факты вступления получали
новую identity, пересоздавали расписание и запускали его таймер заново.
Теперь вход расписания стабилизирован по содержимому всего архива:
`id`, `birth`, `parents`, `spouses`, с сохранением порядка. Изменения этих
фактов обновляют расписание; добавление текста, фото и других деталей
не перезапускает его. Правило расчёта поколений и бюджет анимации сохранены.

Для Canvas стабилизирован по содержимому также список URL портретов:
неизменная очередь не запускается повторно при очередной странице деталей.
`Path2D` и нужные вступлению результаты `gpuRoute` переиспользуются по
строке маршрута; кэш ограничен путями текущей проекции, старые удаляются,
массивы сегментов освобождаются после роста. Уже дорисованная линия
рисуется через готовый `Path2D`, вместо перебора всех её сегментов каждый
кадр. Координаты, связи и данные архива этим не изменяются.

В промежуточном подтверждённом прогоне 3313/desktop/CPU×4 первый GPU-слой
появился через 15,54 с, после persistent reload — через 11,50 с без нового
Worker-запроса. В предыдущем одиночном прогоне reload занимал 31,53 с.
Это наблюдение конкретного сценария до следующего исправления обновления
GPU-сцены, а не медиана или итог всей матрицы.
Матрица окончательного состояния приведена отдельно ниже.

### Обновление GPU по отображаемому содержимому

Следующий прогон 3313/CPU×4 в touch-эмуляции обнаружил повторные пересборки
GL-сцены при поступлении каждой страницы подробных карточек. Они давали
задачи порядка 3 с уже после reload и во время движения камеры. Причиной
служило сравнение identity объектов `Person`, функции родства и маршрута:
новый объект с прежним отображаемым содержимым считался новой сценой.

Теперь сцена сохраняет неизменный снимок строк, которые действительно
рисуются: `fullName`, годы жизни и результат функции родства. Обновление
сравнивает эти значения, а не ссылки на `Person` или callback. Для рёбер
сравнивается итоговый SVG path, включая построенный из точек маршрут,
а не identity объекта route. Изменённый текст или геометрия по-прежнему
требуют соответствующего обновления сцены. Новые nodes принимаются и без
пересборки текста: пол, отметка проверки и фото обновляются динамически,
допустимый набор URL portrait-кэша обновляется вместе с ними.

Одна оставшаяся пересборка в touch-прогоне была связана с `props.canEdit`:
во время overview он был `false`, после загрузки всех деталей становился
`true`, меняя scope GPU-кэша. Это готовность редактирования, а не изменение
доступа к чтению. Параметр исключён из scope; архив, token общей ссылки,
аккаунт, роль, параметры доступа к чтению и restricted-состояние сохранены.
Действия по-прежнему получают актуальный `canEdit`; изменение готовности
редактирования само по себе больше не сбрасывает кэш сцены.

Проверка дополнена накопительным счётчиком `programCreations`. Равное число
живых программ после действия не исключало delete/create с тем же итогом;
новый счётчик обнаруживает и такую пересборку. Предыдущие промежуточные
замеры не следует считать результатами окончательного состояния кода.
Его последовательная матрица приведена отдельно ниже.

### Вписывание камеры без ожидания измерений карточек

Следующая приёмка выявила зависание камеры: публичные статические handles
позволяли корректно отсекать немонтированные карточки, но queued `fitView`
по-прежнему ожидал измерения nodes в React Flow. Ожидающее вписывание могло
не завершиться даже при уже готовой геометрии и оставляло навигацию в
ожидании. Пять прошедших сценариев предыдущей матрицы остаются
промежуточными; остановившийся 977/mobile не подтверждает приёмку всех шести.

Все операции вписывания древа — начальный вид, переходы к семье, кнопки
обзора и выбранного человека — используют границы узлов из модели Worker,
включая скрытые и немонтированные карточки. `getViewportForBounds`
рассчитывает viewport с прежними ограничениями zoom/padding, затем
`setViewport` выполняет переход. Идентификатор человека разрешается в
его occurrence; перед обновлением проверяются `viewportInitialized` и
размеры полотна. Координаты раскладки не меняются, приватные setters
измерений/store React Flow не используются. Результаты повторной сквозной
матрицы этого состояния приведены ниже.

### Переход от touch-жеста к кнопкам

Прогон 977/mobile обнаружил оставшийся флаг подавления click после
долгого касания без завершающего совместимого клика. Первое нажатие

Worker. Имя после настоящей HTTP-правки сохраняло кэш, дата рождения требовала
нового layout. Экранные GPU buffers оставались ниже прежнего лимита 24 МиБ;
явные текстуры составляли около 32 МиБ, CPU-массивы подписей на 3313 —
около 18,53 МиБ. Это отдельные виды памяти, не общий лимит RAM/VRAM.

Heap-поля JSON — `JSHeapUsedSize` main thread после принудительного GC.
Они исключают Worker, GPU, другие процессы браузера и внешнюю память
ArrayBuffer backing stores. CPU-массивы подписей учитываются отдельно;
по этим показателям нельзя заявлять общий предел памяти приложения.
Матрица относится к синтетическим JPEG и архивам `randomFamily(5, 9/12)`,
не к пользовательскому архиву или физическому телефону. Личный вступительный
полёт к человеку авторизованного аккаунта отдельно не измерялся.

### Методика повторения

Обычная функциональная GPU-проверка в CI принудительно обходит отказ от
SwiftShader, чтобы проверить шейдеры, 3313 узла и три уровня подписей.
Она удерживает ответы обзорных портретов до перехода к выбранной карточке,
затем проверяет настоящий upload и следующий кадр. Это отделяет проверку
взаимодействий от массового software-mipmap throughput; в production
SwiftShader выбирает fallback. Сквозная матрица выше не удерживает media
и не обходит проверку аппаратного GPU.

```powershell
npm run build
$env:PLAYWRIGHT_CHROMIUM_EXECUTABLE = 'C:\Program Files\Google\Chrome\Application\chrome.exe'
$env:DREVO_E2E_ANGLE = 'vulkan'
$env:DREVO_TREE_ACCEPTANCE = '1'
$env:DREVO_TREE_ACCEPTANCE_PEOPLE = '977' # либо 3313
$env:DREVO_TREE_ACCEPTANCE_CPU = '1' # либо 4
npx playwright test tests/e2e/tree-acceptance-benchmark.spec.ts --project=desktop
```

Для touch-эмуляции используйте `--project=mobile`. На этой Windows/NVIDIA
конфигурации backend D3D11 зависал при последовательной серии, поэтому
итоговая матрица выполнена с ANGLE Vulkan. `DREVO_E2E_ANGLE` — только параметр
запуска тестового Chrome, не изменение GPU-политики приложения или
принудительное включение его eligibility. Прежние прогоны default ANGLE
не дают корректного сравнительного коэффициента FPS с этой матрицей.
Наблюдение массовой фотоочереди до исправления и её ограничение описаны
отдельно, без такого FPS-сравнения.

Backend создаёт отдельную временную SQLite-базу и оригиналы JPEG 400px;
превью генерируются настоящим серверным путём. Генерация fixture заканчивается
до начала измеряемой навигации. Нет `page.route`, подмены ответов, принудительного
включения GPU или использования заранее рассчитанной геометрии. Первый вход
идёт в новом browser context, затем reload сохраняет IndexedDB и серверный
кэш превью на диске. Приватные портреты отвечают с `no-store`: тёплый результат
нельзя объяснять HTTP-кэшем изображений.

Сценарий пишет `tree-acceptance.json`: отметки `performance.now` от навигации,
время запросов/отмен Worker, media-запросы, long tasks, кадры и явно выделенные
GL-ресурсы. Для состояния с незакоммиченными изменениями поле `commit`
указывает базовый HEAD; точные измеренные исходники идентифицирует
`sourceHashes`. Heap-снимки после принудительного GC относятся только к
main thread, без Worker, GPU и остальных процессов браузера. Проект `mobile`
использует touch-эмуляцию Chrome, не физический телефон. Шесть сценариев
подтверждают указанную матрицу на данном устройстве; личный вступительный
полёт к человеку авторизованного аккаунта и завершение всех оптимизаций
этими замерами не подтверждены.

### Подготовленный индекс родства для привязанного аккаунта

В шести аппаратных сценариях выше аккаунт не был привязан к карточке.
Они не измеряют массовое вычисление подписей относительно пользователя.
Для этого пути добавлен `createKinshipAnalyzer`: один явный снимок семейного
графа с индексами людей, входящих и дополнительных связей. Обходы предков
переиспользуются внутри замыкания; пути хранят расстояние и предшественника,
а массив выбранного пути создаётся при выдаче результата. Кеш содержит
не более 16 обходов и `max(32768, people.length)` записей предков; глобального
кеша с меняемыми массивами нет.

Публичный `analyzeKinship` сохраняет прежние правила, роли, пояснения,
направление связей и разрешение равных путей. Подготовленный анализатор
сохраняет также семантику явно переданных `a/b`: их исходный пол определяет
брачную роль, имена участвуют в пояснении бокового родства. Снимок графа
не меняется при последующих мутациях исходных карточек. Без `asOf` статус
союза вычисляется на текущий UTC-день, как прежде; UI передаёт день снимка,
чтобы первые обращения к разным подписям не смешивали статусы на границе суток.

В `tree-canvas` один анализатор и кеш подписей сохраняются на семантическую
версию семьи. Ключ учитывает порядок людей и связей, идентификаторы,
имена и отчества для определения пола, фамилии, пол, родителей, супругов,
полноту родительских сведений, тип/направление/примечание дополнительных
связей, тип близнецов и даты статуса семейных союзов. Загрузка фото,
биографий, источников и других подробностей не сбрасывает этот кеш.
Архив, аккаунт, read policy, разрешение общей ссылки, привязанная карточка
и UTC-день отделяют снимки. Карточка предыдущего вида, отсутствующая
в текущем снимке, получает «Родство не установлено» без обращения к её
устаревшим связям; это защитное правило UI, не изменение domain API.

### Рывки при догрузке сведений — 3 октября 2026

Аппаратный [baseline на `d170214`](benchmarks/pan-20261003/pan-baseline-measure.json)
отделяет панорамирование сразу после persistent reload от движения после
полной догрузки. На 3313 людях, CPU×4, первая серия дала p95 кадра 333,7 мс
и 13 длинных задач; после догрузки — 16,8 мс и ни одной длинной задачи.
Количество загрузок портретов в GPU осталось 26, программ — 2 в обоих
интервалах. Новая загрузка текстур не объясняет этот случай.

В [разборе исходного профиля](benchmarks/pan-20261003/pan-baseline-summary.json)
основные затраты приходятся на повторную подготовку моделей узлов и связей:
каждая страница подробностей меняла `family`, хотя видимый граф оставался
тем же. Профиль используется для нахождения причины, а не сравнения скорости;
вложенные времена нельзя складывать. Проверены соответствующие исходники
и собранные chunks, их хеши сохранены в отчёте.

`TreeCanvas` теперь сохраняет снимок `archiveOverview` по содержимому.
Подгрузка биографий, занятий, источников, наград, событий и галереи не
пересобирает дерево. Имена, даты, портрет, пол, отметка проверки, владельцы,
родители, супруги и сведения связей остаются входами этого снимка. Живые
сведения человека передаются нативным карточкам отдельным контекстом;
инспектор, timeline и экспорт используют полный актуальный архив.
Все поля существующего поиска есть в overview. Равные массивы подсвеченного
пути и общих предков также сохраняются при сравнении двух людей.

портрета обновляют нативную карточку без потери этих сведений.

#### Завершение загрузки: права отдельно от маршрутов

Следующая правка отделяет `prepareTreeEdges` от `applyTreeEdgePermissions`.
Подготовка сохраняет геометрию, подписи, выбор связей и обработчики;
отдельный проход применяет актуальные `user/canEdit/busy` только к
самостоятельным связям. Индексы этих связей вычисляются внутри адаптера,
без догадок по идентификатору или типу. Семейные ветви и черновики никогда
не становятся переподключаемыми. Если самостоятельных связей нет, изменение
прав возвращает прежний массив целиком. Обработчики остаются явными
зависимостями подготовки: изменение callback не скрывается кешем.

На том же оборудовании и с тем же протоколом выполнены ещё два полных
прогона на `09dd963` (runtime `7feda34`). Профиль записан на `e5cc4b3`;
между ними изменён только сбор метаданных benchmark. Все 24 хеша полного
отчёта совпали между прогонами и исходниками. Полный collector этих двух
прогонов не записал хеш адаптера; он есть в отдельном diagnostic.
[Проверка идентичности](benchmarks/pan-permissions-20261003/runtime-identity.json)
подтверждает этот хеш и отсутствие изменений runtime после измерений.

прошли, зум не дал длинных задач. Холодный/повторный вход занял 18,70/12,32 с
на desktop и 19,40/11,83 с на touch; улучшение полного входа не подтверждено.

В [новом профиле](benchmarks/pan-permissions-20261003/edge-permissions-summary.json)
подготовка линий, `React Flow` adoption и обновление GPU-модели не попали
в выборку. Остались сериализация снимка, финальная `validateFamily` и сводка
архива. Отсутствие samples не означает гарантированное нулевое время;
окна профилей различаются и не используются как speed benchmark.
[Diagnostic](benchmarks/pan-permissions-20261003/edge-permissions-pan-diagnostic.json)
сохраняет метод, аппаратный renderer, состояние догрузки и хеши.

Пять новых unit-регрессий проверяют сохранение массива ветвей, отделение
самостоятельных связей от черновиков, владельцев и отзыв прав, источники,
маршруты, обновление имён/пола/источников и актуальные обработчики мыши/клавиатуры. Восемь targeted unit-тестов
и семь browser-проверок карточек/камеры прошли. Полная смена проекции всё ещё
даёт задачи до 3262 мс на desktop и 3629 мс на touch с CPU×4: подготовка
текстового слоя остаётся отдельной следующей задачей. На итоговой версии
прошли typecheck, lint, все 947 unit-тестов, сборка и три проверки собранного Worker.
 


#### Портреты: подготовка анимации, хронология и дальний масштаб

Причина вспышки — canvas задавал собственный `visibility: visible` и перекрывал
унаследованный `visibility: hidden` контейнера. До старта анимации счётчик
времени также считал все портреты уже появившимися. Слой остаётся смонтированным
для загрузки и согласования старта, но до старта очищается, не рисуется и скрыт
через `opacity` контейнера. В хронологии слой портретов не монтируется;
overview выключен при хронологии и подготовке раскладки. Размеры React Flow
сохраняются для работы камеры.

GPU-кэш выбирает размер маленького портрета по числу уникальных фото проекции:
48/28/20/16 px дают 1521/4096/7225/10404 места. Две существующие текстуры
2048×2048 не увеличиваются. Вместимость монотонна в течение жизни кэша:
обычный зум и движение камеры не перепаковывают атлас. На дальнем зуме
сохраняется фото; пока маленькая версия загружается, используется готовая
крупная. Загруженное фото не заменяется цветной заглушкой из-за уровня зума.
При размере в один-два экранных пикселя изображение естественно теряет детали.

Очередь загрузок продвигается курсором вместо повторного сканирования готового
префикса. Ошибки сохраняются на 30 секунд; история ограничена полной
вместимостью двух атласов, поэтому более 2048 отсутствующих фото не вызывают
бесконечного сброса истории и повторных запросов. Устаревшие обработчики
не могут изменить освобождённый или перепакованный кэш.

Если ограничение поколений скрывает найденного человека, явная кнопка
«К выбранному человеку» назначает его опорным, сохраняет числа поколений и
центрирует камеру после новой раскладки. Для видимого человека остаётся
обычное центрирование. Поиск и открытие карточки сами не меняют опору;
фильтры ассистента и свёрнутые ветви не снимаются этим действием.

Проверка итоговой версии: typecheck, lint, сборка, 974 unit-теста и три теста
собранного Worker прошли. В браузере прошли 13 функциональных проверок;
пять desktop-сценариев пропущены в mobile-проекте. Новые проверки используют
декодированное изображение, чтение пикселей canvas и фактическую видимость
при подготовке анимации, а также переход в хронологию и обратно. Два сценария
поиска проверяют смену опоры для скрытого человека и отсутствие такой смены
для видимого.

Два полных аппаратных прогона на `3deb737` (runtime `c478a30`): Chrome 155,
GTX 1070, ANGLE Vulkan, CPU×4, 3313 синтетических людей, временная SQLite и
настоящий backend. JPEG-оригиналы сервер превращает в WebP-превью. Подменён
только `user.personId` для привязанного аккаунта; семейные данные, media и
условия включения GPU не подменены. Прогоны последовательны, без параллельной
сборки и тестов. Touch — эмуляция Chrome 390×844, не физический телефон.
Все 28 хешей исходников совпадают между прогонами и текущими файлами;
[проверка идентичности](benchmarks/portrait-layers-20261003/runtime-identity.json)
сохраняет хеши неизменённых исходных отчётов.

| 3313 человека, CPU×4 | p95 кадра движения, мс | Максимум кадра движения, мс | p95 зума, мс |
| ------------------- | --------------------- | -------------------------- | ------------ |
| [Desktop](benchmarks/portrait-layers-20261003/portrait-layers-desktop-3313.json) | 33,4 | 133,5 | 16,8 |
| [Touch](benchmarks/portrait-layers-20261003/portrait-layers-mobile-3313.json) | 16,8 | 50,1 | 16,8 |

В desktop-обзоре при минимальном зуме 0,05 все 719 попавших в кадр фото имели
текстуру. Весь широкий граф из 3313 карточек физически не помещается в кадр
при этом минимуме. Первоначальная проверка ошибочно требовала более 1521
видимой карточки и была исправлена на проверку всех реально видимых фото;
runtime между этими прогонами не менялся. Вместимость для 3313 и 4096
портретов отдельно проверена unit-тестами. Объявленный объём текстур сцены
остался 33 554 433 байта — это учёт выделений, не вся VRAM браузера.

Оба полных сценария прошли повторный вход с кэшем Worker, движение, зум,
уровни подписей, открытие карточки, три цикла ограниченного/полного вида,
освобождение GL и настоящие HTTP-изменения имени и даты. Это по одному
прогону, а не доказательство общего ускорения. Холодный/повторный GPU-слой
появился через 18,20/12,03 с на desktop и 17,66/10,60 с на touch при CPU×4.
После циклов главный JS heap вырос с 47,6 до 60,3 МБ на desktop и с 47,6 до
55,0 МБ на touch; два checkpoint не устанавливают причину роста или
отсутствие утечки и не включают память Worker/GPU.

Ограничения: переход проекции через порог вместимости однократно очищает
маленький атлас и загружает его заново, сохраняя готовые крупные изображения.
Более 10404 уникальных маленьких портретов обслуживаются ограниченным набором
ближайших к кадру. Полная смена проекции и подготовка текстового слоя всё ещё
тяжёлые: максимальный интервал кадра в циклах достиг 3,72 с на desktop и
4,24 с на touch с CPU×4. Эта правка устраняет артефакты портретов и ограничение
старого атласа, но не завершает оптимизацию полного входа и смены проекции.
