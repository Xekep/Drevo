# Резервирование реестра очистки ИИ

Новые Conversation в PostgreSQL учитываются в платформенном реестре. Их исходные credentials шифруются отдельным ключом `ai-provider-cleanup.v1.key` рядом с настроенным платформенным `DATABASE_PATH`. Все экземпляры серверов архивов получают один и тот же платформенный путь от запускающего сервера. Ключ публикуется атомарно как приватный файл `600`; перед записью первого задания сервер проверяет его немедленную локальную копию в `backups/platform-keys/`.

Ключ включается в системный медиа-TAR, но не в переносимый TAR отдельного архива. Изолированная парная репетиция сверяет отпечаток ключа из медиа-TAR с восстановленной PostgreSQL БД. При физическом восстановлении ключ из соответствующего системного медиа-TAR нужно вернуть по прежнему платформенному пути с правами `600` до запуска приложения. Отсутствующий или чужой ключ запрещает создание новых Conversation и работу очереди; поверх существующего реестра новый ключ не создаётся. Это локальная копия на том же хосте, поэтому потерю сервера она не покрывает.

Переносимый TAR обнуляет действующие provider ID и ссылки на платформенную очередь, но сохраняет локальные сообщения. Следующий ответ создаёт новый Conversation и восстанавливает контекст из локальной истории. SQLite-режим не включает долговечный платформенный worker и оставляет прежний best-effort вызов удаления.

Этот этап охватывает новые зарегистрированные Conversation при явном удалении чата и потерю lease во время создания. Прежние remote ID без достоверно сохранённых исходных credentials, каскадное удаление аккаунта/архива и административное тестовое создание остаются отдельной работой. Падение процесса между успешным удалённым POST и получением/записью ID нельзя полностью устранить без поддерживаемой провайдером идемпотентности. DELETE Conversation у провайдера не подтверждает удаления его элементов.
