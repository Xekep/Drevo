# Архитектура и производительность

## Что уже изменено

Новые экранные разделы не должны раздувать `App.tsx`. Переключение вторичных страниц вынесено в `ArchiveSection`, а `Люди`, `Семьи`, `Фото`, `Места` и `Интересное` загружаются через `React.lazy`. Главный бандл не обязан содержать код экранов, которые пользователь ещё не открывал.

## Следующая декомпозиция

`App.tsx` всё ещё совмещает несколько ролей: управление выбранными людьми и родством, редактирование людей/связей, состояние фото-диалогов, маршрутизацию разделов и глобальные оверлеи. Следующий безопасный шаг — выделить `TreeWorkspace` и `ArchiveOverlays`, не создавая один «универсальный» компонент с десятками необязательных режимов.

`tree-canvas.tsx` также велик, но его не стоит механически дробить. Полезные границы уже видны: построение React Flow nodes/edges, управление камерой и панели инструментов. Эти части можно выносить после профилирования, сохраняя чистые зависимости от геометрии.

## Отдача данных

Главный серверный резерв находится в постраничной догрузке `/api/family?projection=page`. Сейчас каждый такой запрос вызывает полный `archive.read()`: SQLite читает и JSON-парсит всех людей, все связи, все фото и все теги, после чего сервер отрезает одну страницу. При `N` страницах объём серверной работы приближается к `N × размер архива`.

Рекомендуемая оптимизация: для page-проекции читать из SQLite только нужный диапазон `people` или `photos`, а ревизию и количество записей получать отдельными дешёвыми запросами. Для фото нужно догружать теги только выбранных `photo_id`. Права доступа и `pageToken` при этом остаются теми же.

Начальная `overview`-проекция тоже может быть специализирована: ей нужен граф людей и связей, но не полные биографии, события и массив фотографий. Сейчас эти данные сначала читаются, а затем отбрасываются.

На клиенте `completeArchive` вызывает `progress` после каждой страницы. Это полезно визуально, но каждая публикация нового `family` запускает производные `useMemo` и обновление React Flow. После серверной оптимизации стоит замерить загрузку и, если архив станет большим, публиковать прогресс реже или разделить состояние графа и тяжёлых деталей.

## Отрисовка дерева

React Flow уже использует `onlyRenderVisibleElements`, а раскладка вынесена в Web Worker. Это хорошие решения и их следует сохранить.

Следующие кандидаты для профилирования:

- ввод поиска пересобирает массив node-объектов и повторно проверяет ФИО для видимых вхождений;
- изменение подсветки/выбранной связи пересобирает edge-объекты, после чего `crossingPaths` может повторно анализировать геометрические пересечения, хотя сама геометрия не изменилась;
- `useTreeLayout` заново сериализует семейную проекцию при изменении массива `people`, даже когда поменялись только тяжёлые поля, не влияющие на раскладку;
- карта Leaflet и фото-галерея теперь не входят в стартовую загрузку благодаря route-level lazy loading.

Оптимизировать эти места следует по профилю на большом тестовом архиве, а не добавлять мемоизацию вслепую: лишний кэш тоже ест память и усложняет инвалидирование.
