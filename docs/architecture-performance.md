# Архитектура и производительность

## Что уже изменено

Новые экранные разделы не должны раздувать `App.tsx`. Переключение вторичных страниц вынесено в `ArchiveSection`, а `Люди`, `Семьи`, `Фото`, `Места` и `Интересное` загружаются через `React.lazy`. Главный бандл не обязан содержать код экранов, которые пользователь ещё не открывал.

## Следующая декомпозиция

`App.tsx` всё ещё совмещает несколько ролей: управление выбранными людьми и родством, редактирование людей/связей, состояние фото-диалогов, маршрутизацию разделов и глобальные оверлеи. Следующий безопасный шаг — выделить `TreeWorkspace` и `ArchiveOverlays`, не создавая один «универсальный» компонент с десятками необязательных режимов.

`tree-canvas.tsx` также велик, но его не стоит механически дробить. Полезные границы уже видны: построение React Flow nodes/edges, управление камерой и панели инструментов. Эти части можно выносить после профилирования, сохраняя чистые зависимости от геометрии.

## Отдача данных

Для обычного доступа `/api/family?projection=page` читает диапазон людей через `archive.peoplePage()` или фотографии через `archive.photoPage()`. Метаданные и выбранная страница читаются в согласованной транзакции; ревизия, область доступа и `pageToken` защищают от смешивания разных снимков. Теги догружаются только к выбранным фотографиям.

Для ограниченного доступа `common_ancestors` страницы уже выбираются SQL по
доступным ID. `archive.visibleIds()` использует общий ограниченный кэш минимального
графа и области видимости по ревизии; это не чтение биографий и всех фотографий.
Права определяет существующий `visiblePersonIds`: кровные, их прямые вторые
родители и партнёры, а также отдельные карточки, добавленные самим участником.

Обычная начальная `overview` использует `archive.overview()` и возвращает граф без
тяжёлых подробностей. Ограниченная — `archive.scopedOverview(user)`. Для узкой
области (не более половины людей) SQL читает JSON только доступных карточек,
связи с обоими доступными концами и союзы с обоими доступными участниками.
Граф и счётчик фотографий подготавливаются в согласованной read-only транзакции.
Для широкой области промах кэша переиспользует общую базовую overview: иначе
одновременный приход разных участников заставлял бы перечитывать почти весь JSON
для каждого. Перед совмещением базы, ID и фотографий проверяется ревизия; при
расхождении используется свежая согласованная SQL-выборка.

Готовые проекции используют `archiveSnapshotReader`: независимые JSON-копии,
объединение одновременных загрузок, проверка ревизии, отсутствие публикации
незавершённых транзакций и общий процессный бюджет памяти. Сохраняется максимум
16 reader для комбинаций аккаунта/привязанного человека/области/ролей/владения/
подтверждения доступа; каждая запись не более 16 МиБ в общем существующем бюджете.
Это кэш данных, не сессий и не HTTP-ответов. Проверки действующего доступа и ревизии
перед отправкой HTTP остаются обязательными. Полный снимок по-прежнему нужен для
экспорта и восстановления после конфликта постраничной загрузки.

### Замер проекции, 24 октября 2026

`node --experimental-strip-types tests/scoped-overview-benchmark.mjs`;
[результаты и исходные выборки времени](benchmarks/scoped-overview-20261024/results.json).
Node 22.14, Windows/Ryzen 5950X, синтетическая SQLite в памяти. Старый путь:
кэш общей overview → вычисление доступного подмножества → подсчёт фото. Новый:
проверка ревизии → копия кэшированной ограниченной проекции. Возвращённый JSON
сравнивается на равенство. Чередование старого/нового, прогрев и медиана 15 повторов.

| Всего людей | Доступно | Прежний повторный запрос | Новый повторный запрос |
| --- | --- | --- | --- |
| 1000 | 10 | 1,76 мс | 0,06 мс |
| 1000 | 900 | 2,39 мс | 1,16 мс |
| 10000 | 100 | 15,83 мс | 0,23 мс |
| 10000 | 9000 | 25,88 мс | 12,79 мс |

Первый новый запрос после прогретой общей overview занял 7–110 мс: это промах
кэша минимального графа и/или проекции, не холодный процесс. Простая SQL-фильтрация
без повторного кэширования в предварительном замере замедляла широкую область
примерно вчетверо; такой вариант не оставлен. Проверка 24 разных участников
подтверждает переиспользование общей базы после заполнения LRU.

Таблица измеряет стоимость JSON/проекции и кэша, а не скорость PostgreSQL, сеть,
100 одновременных HTTP-пользователей или RSS. Реальная SQL-ветвь отдельно проверена
на изолированной PostgreSQL 16.2 под ролью `NOSUPERUSER NOBYPASSRLS`, с реальными
политиками FORCE RLS, двумя древами и 1000 приватных карточек. Тест включён в
существующий CI на PostgreSQL 18. Дополнительно проверяются пустой доступ,
смена привязанного человека, отзыв HTTP-доступа, откат записи, сбой загрузки и
коммит между подготовкой ID и чтением общей базы. Рабочая БД не используется.

На клиенте `completeArchive` запрашивает до четырёх страниц по 40 элементов параллельно и публикует прогресс после 160 элементов или завершения коллекции. При конфликте токена получает один полный снимок. Изменять частоту публикаций следует по профилю большого тестового архива.

## Открытие PDF

Точные размеры страниц хранятся в серверном манифесте, подготовленном при загрузке документа. Старые документы заполняют кэш при первом запросе. Вход в ридер не требует `getPage()` для всех страниц в браузере: исходный PDF загружается диапазонами, начальный разворот отрисовывается сразу после чтения манифеста. Размеры смешанных форматов и повороты сохраняются. Повторные просмотры используют дисковый кэш, привязанный к оригиналу.

Blob URL отрисованных страниц имеют бюджет 24 страницы и 32 МБ; видимые страницы и соседний разворот сохраняются. При возвращении к вытесненной странице она отрисовывается заново. Закрытие документа освобождает все URL и PDF.js. Поиск работает по готовому текстовому слою; текст сканов не извлекается.

## Отрисовка дерева

React Flow уже использует `onlyRenderVisibleElements`, а раскладка вынесена в Web Worker. Это хорошие решения и их следует сохранить.

Следующие кандидаты для профилирования:

- ввод поиска пересобирает массив node-объектов и повторно проверяет ФИО для видимых вхождений;
- изменение подсветки/выбранной связи пересобирает edge-объекты, после чего `crossingPaths` может повторно анализировать геометрические пересечения, хотя сама геометрия не изменилась;
- `useTreeLayout` заново сериализует семейную проекцию при изменении массива `people`, даже когда поменялись только тяжёлые поля, не влияющие на раскладку;
- карта Leaflet и фото-галерея теперь не входят в стартовую загрузку благодаря route-level lazy loading.

Оптимизировать эти места следует по профилю на большом тестовом архиве, а не добавлять мемоизацию вслепую: лишний кэш тоже ест память и усложняет инвалидирование.
