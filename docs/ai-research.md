# ИИ-исследователь и MCP

Drevo использует единый read-only слой исследовательских инструментов. Его вызывают встроенный веб-ассистент и внешний MCP endpoint. Это не даёт модели прямого доступа к SQLite и не дублирует генеалогическую логику в промптах.

Для временного отбора людей на древе инструмент `control_archive_view` принимает
`action=filter_by_criteria`, `mode=include|exclude`, `criteria` и необязательный короткий `label`.
Общий инструмент `query_people` использует тот же отбор для поиска и подсчёта.
Его schema автоматически доступна встроенному ассистенту и MCP с `tree:read`.
Поддерживаются фамилия (также при рождении, с грамматическими формами),
подстрока полного имени, места рождения/смерти, занятие, пол, годы рождения/смерти,
возраст смерти (`deathAgeFrom` включительно, `deathAgeBefore` строго меньше),
записанный факт смерти, отметка проверки, наличие корректных дат, источников и фото.
Источники собираются общим `collectPersonSources`, включая факты, события и награды;
фото учитывают портрет и отметки на доступных фотографиях. Это признаки наличия,
а не доказательство достоверности. Поиск имени с опечатками остаётся в `search_people`.

Поля действуют как И; группы `allOf` — И, `anyOf` — ИЛИ, `noneOf` — исключение
совпадений. В группе от 1 до 10 простых условий без вложенных групп; неизвестные
поля, неверные типы и обратные диапазоны отклоняются, без молчаливого расширения.
Все условия проверяются на всей доступной пользователю выборке.
`eventType/eventPlaceContains/eventYearFrom/eventYearTo` должны совпасть в одном
событии; годы относятся к записанной корректной дате начала, приблизительный
`dateText` не превращается в точную дату. `relativeOf` и `relation` задаются вместе:
предки, потомки, родители, дети, супруги или люди с общим известным родителем.
Они используют только доступные записанные `parent/spouse` связи; недоступный
якорь отклоняется, обход ограничен проекцией пользователя и защищён от циклов.

`query_people` принимает обязательные `criteria`, `mode=include|exclude`
(по умолчанию include), `offset` и `limit=0..100` (по умолчанию 50).
`total` — точное число выбранных людей, `matchedCount` — число совпавших с условиями,
`totalPeople` — размер доступного архива; `people` — только страница с именами и
основными жизненными данными. `hasMore/nextOffset` позволяют продолжить список;
при `limit=0` возвращается только подсчёт (`countOnly=true`), без списка и продолжения.
Сортировка стабильна по полному имени и ID; каждый вызов проверяет текущий архив.
Для показа выборки ассистент передаёт те же `criteria/mode` в `filter_by_criteria`,
без выгрузки всех страниц или передачи большого набора ID через модель.

Пример «сколько женщин родилось в Москве или Туле в 1900–1950 годах»:

```json
{
  "criteria": {
    "sex": "f",
    "birthYearFrom": 1900,
    "birthYearTo": 1950,
    "anyOf": [
      { "birthPlaceContains": "Москва" },
      { "birthPlaceContains": "Тула" }
    ]
  },
  "limit": 0
}
```

Модель передаёт условия, а не сотни ID; лимит 300 ID у ручного `filter_people`
на такой отбор не распространяется. При исключении умерших до 18 лет живущие,
люди с неизвестным возрастом смерти и неточными датами на границе 18 лет остаются.
Данные архива не изменяются. Даже пустой результат можно сбросить кнопкой «Всё древо».
Отдельная команда фильтра завершается проверенным подтверждением приложения без ещё
одного вызова модели. При совмещении с анализом модель получает только счётчики,
а не список ID. После отдельной команды следующая реплика восстанавливает сохранённую историю
в новом диалоге провайдера, чтобы не оставлять незавершённый вызов инструмента.

## AI-профили ролей

В **Админка → Yandex AI → AI по ролям** можно независимо настроить
администратора, исследователя, родственника и читателя. Роль **«Исследователь»**
назначается в разделе «Участники»; права на древо у неё такие же, как у родственника:
создание своих объектов, изменение своих карточек и фотографий, без админки.
Ограничение «Общие предки» также действует. Это роль участника архива,
а не тариф аккаунта и не новые права на чужие данные.

По умолчанию все роли наследуют прежние общие настройки. Снимите «Использовать
общие настройки», чтобы задать собственный профиль. Настраиваются:

- доступ к ИИ и модель диалога из существующего списка моделей Yandex;
- поиск по доверенным ресурсам и отдельно разрешение глобального поиска;
- анализ фотографий и, при необходимости, отдельная модель с поддержкой изображений;
- создание PDF-отчётов и предложения изменений с ручным подтверждением;
- личные минутные и дневные лимиты запросов/токенов, сжатие контекста и число шагов инструментов.

В админке сначала видны общий выключатель ИИ и доступ выбранной роли. Параметры
подключения Yandex и общие лимиты вынесены в раскрывающийся блок. Личные
лимиты и контекст выбранной роли находятся в блоке «Модель фото, лимиты и контекст».

Читатель не получает предложения изменений даже при включённой опции профиля.
Поиск и вычисления по доступной части архива, справочник ресурсов и навигация остаются
базовыми возможностями ассистента. Выключение PDF в AI не запрещает обычный экспорт древа.
Внешний поиск использует модель выбранного профиля; автоматический выбор модели для
анализа фото сохраняет существующую логику Drevo, если отдельная модель не указана.

Кнопка «Проверить сохранённую модель роли» отправляет короткий платный запрос через
существующий Responses-клиент. Это проверка ответа модели, не сертификация всех её
инструментов. Разрешение функции в Drevo не добавляет модели отсутствующую возможность:
поддержку изображений и API нужно сверять с [каталогом моделей Yandex](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/models).
Настройки контекста используют существующие параметры [Responses API](https://aistudio.yandex.ru/en/docs/ai-studio/api/Responses/createResponse).
Новые SDK и параметры Yandex API не добавлены.

Общий выключатель ИИ действует на все роли. Общие дневные лимиты архива сохраняются
поверх личных лимитов профиля; ноль отключает соответствующий лимит. Счётчики личных
лимитов привязаны к пользователю, поэтому смена роли не обнуляет использование за день.
Лимиты проверяются перед новым ходом; число токенов уже выполняющегося ответа может
превысить оставшийся дневной бюджет, как и прежде. Настройки применяются со следующего
запроса, в том числе в существующем диалоге; начатый ход использует снимок настроек.

API-ключ и Folder ID общие, ключ остаётся на сервере. Новые env-переменные не нужны.
Конфигурация ролей хранится в `ai_settings.role_profiles`, типы — в
`src/shared/ai-role-profiles.ts`. `aiRuntimeConfig(settings, user.role)` разрешает
настройки по серверной сессии. Клиентский `role`, `model` или список возможностей
не управляют политикой. Agent loop ограничивает schema и повторно проверяет имя
инструмента перед выполнением; глобальный scope проверяется отдельно. Изменение
профилей попадает в существующий журнал аудита без credentials.

SQLite расширяется миграцией `2026-09-ai-role-profiles` с сохранением пользователей,
сессий и внешних ключей. PostgreSQL использует `ops/postgres/012_ai_role_profiles.sql`:
добавляется колонка в существующую таблицу с FORCE RLS, расширяется CHECK роли.
Миграция применяется при запуске под общей advisory-блокировкой и при импорте.
Перед откатом на версию без роли «Исследователь» переназначьте таких участников
родственниками: старая версия не знает название и правила новой роли.

## Веб-ИИ

Серверные маршруты `/api/ai/chat` и `/api/ai/chat/stream` используют Yandex Responses API для агентного цикла. Для каждого локального чата создаётся отдельный объект через Yandex Conversations API. Администратор платформы задаёт API-ключ и Folder ID в разделе **«Yandex AI»**; список доступных моделей загружается через `/models`. API-ключ никогда не возвращается браузеру. Отдельный вызов Chat Completions пока остаётся только для анализа изображения инструментом `analyze_photo`.

При сохранении через админку API-ключ шифруется AES-256-GCM. Ciphertext хранится в SQLite, а 32-байтный локальный ключ шифрования — в файле `<database>.secrets.key` с правами владельца процесса. Этот файл намеренно не включается в переносимый backup: после переноса архива на другой сервер API-ключ вводится заново.

Переменные окружения `YANDEX_AI_API_KEY`, `YANDEX_AI_FOLDER_ID` и `YANDEX_AI_MODEL` остаются fallback-настройками. Сохранённые в Drevo значения имеют приоритет. `YANDEX_AI_BASE_URL` необязателен. Для работы нужна явно выбранная или заданная через окружение модель: сервер не подставляет потенциально недоступную модель по умолчанию.

ИИ доступен только вошедшему участнику с правом чтения закрытого архива. Для участника с ограничением common_ancestors Research Tools получают ту же серверную проекцию, что и остальные способы чтения древа.

### Состояние чата и контекст

Каждое сообщение браузера передаёт `context.timeZone` из `Intl.DateTimeFormat().resolvedOptions().timeZone`. Сервер проверяет допустимость пояса и на каждом раунде Responses API добавляет текущие дату, время и UTC-смещение из собственных часов; дату браузера не принимает. Инструмент `get_current_time` позволяет модели отдельно уточнить время. Если пояс отсутствует или некорректен, используется UTC с явной пометкой, что местный пояс неизвестен. Переход суток, смена пояса и летнее время учитываются заново, в том числе в старом диалоге после compaction. Часовой пояс — настройка устройства, не установленное местонахождение человека.

Для ответа о текущем возрасте `get_person` в веб-ассистенте возвращает вычисленные кодом `age.label`, `age.kind` и `age.asOfDate` на календарную дату пользователя. Неполные даты сохраняют приблизительность, неизвестный возраст — `null`, а умершим не вычисляется текущий возраст вместо возраста на дату смерти. Текущая дата передаётся доменному инструменту отдельно от аргументов модели; исторический возраст требует другой даты расчёта. Внешний MCP не получает браузерный часовой пояс автоматически.

SQLite хранит `ai_chats` и `ai_chat_messages`: владельца, сообщения для интерфейса, Yandex Conversation ID и до восьми подтверждённых `personId` в маленьком `session_state`. Данные родства в этом состоянии не кешируются. При открытии панели браузер загружает последний доступный чат; когда чатов несколько, можно выбрать предыдущий. Очистка удаляет текущий локальный чат и вызывает best-effort `DELETE /v1/conversations/{id}`. По документации Yandex удаление conversation само по себе не гарантирует удаление её отдельных remote items.

Обычный запрос к модели содержит только текущую реплику, актуальную инструкцию и результаты вызванных в этом раунде инструментов. Локальная история не посылается снова на каждом ходе. `conversation` хранит контекст на стороне AI Studio; `previous_response_id` одновременно с ним не используется. При отсутствии или HTTP 404 remote conversation Drevo создаёт новый объект и один раз передаёт не более десяти последних локальных сообщений. Ранее существовавшие до этой версии сообщения жили только в памяти открытой страницы, поэтому мигрировать их после перезагрузки невозможно.

Responses API запрашивает `context_management: [{type: "compaction", compact_threshold: 32000}]` и `truncation: "auto"` по умолчанию. При проверке Yandex API 24 сентября 2026 года массив принимался, а объект из документации Yandex возвращал HTTP 400 `Failed to read request`. Порог, включение сжатия, truncation и максимум шагов инструментов доступны в сворачиваемом блоке админки. Если массив отклонён с HTTP 400, Drevo пробует документированную объектную форму. Если обе формы отклонены, запрос повторяется без `context_management`, несовместимость запоминается для модели на время работы процесса и пишется `ai.compaction_unavailable` в лог. Админская проверка подключения сообщает, удалось ли включить сжатие. В режиме без сжатия длинный контекст защищает только `truncation=auto`; при переполнении даже с truncation запрос завершается ошибкой без бесконечных повторов.

Один и тот же чат одновременно обрабатывает только один запрос: SQLite lease возвращает HTTP 409 для конкурирующей реплики и продлевается во время обработки. Чаты привязаны к текущей роли, области древа и привязанному человеку; для ограниченного доступа дополнительно проверяется состав видимых людей и фото. После изменения области данных старый чат не открывается через API, чтобы не повторно использовать контекст с прежними разрешениями. Источник фактов всегда текущая БД Drevo и ответы Research Tools, а не память модели.

Модель видит имя связанного с аккаунтом человека и его фактическую область доступа. Все обычные инструменты работают только с серверной проекцией, разрешённой этому участнику. Фотографии доступны отдельными инструментами поиска, чтения метаданных и визуального анализа: сервер проверяет право на снимок и передаёт ограниченную WebP-копию только после явного tool call. Пути к медиа, `createdBy`, face descriptors, аккаунты и настройки доступа модели не передаются.

Панель ИИ открывается компактной кнопкой рядом с управлением камерой и перетаскивается мышью на компьютере. Ответы поддерживают Markdown, GFM-таблицы, Mermaid-графы и формулы LaTeX: `$…$`, `$$…$$`, `\(…\)`, `\[…\]` и блоки `latex`/`tex`. Формулы отображаются через KaTeX; оформление ответа загружается по требованию. По явной просьбе пользователя отдельный проверяемый tool может плавно показать людей или цепочку в древе, открыть карточку человека либо разрешённую фотографию; модель не управляет интерфейсом по собственной инициативе.

Проверенные блоки Mermaid graph/flowchart, pie и xychart в чате отображаются интерактивно через Apache ECharts на Canvas: схему можно развернуть, перемещать и менять масштаб, а значения диаграмм смотреть при наведении. Для PDF схемы раскладываются алгоритмом ELK. Пока запрос выполняется, интерфейс показывает этапы обработки отдельно от ответа. Готовый ответ появляется целиком после проверки сервером.

Для вопросов о личном родстве ассистент берёт степень и цепочку из `get_relationship`; схема этой цепочки и годы жизни вычисляются из тех же карточек сервером. Подсчёты по датам рождения выполняет `get_birth_statistics`, который возвращает полное распределение по десятилетиям и точный размер выборки. `search_photos` умеет сортировать снимки по числу уникальных отмеченных людей. Для вопросов о пробелах в источниках модель получает сокращённый набор подходящих инструментов; `find_evidence_gaps` возвращает числа по видам пробелов для всего доступного архива, даже если примеры ограничены страницей. Это не меняет область доступа участника.

Если Yandex завершил ответ без видимого текста, сервер повторяет формулирование до двух раз. Если поток оборвался без `response.completed` на первом шаге, сервер один раз пробует обычный ответ API с коротким тайм-аутом. Эти повторы не применяют изменения к архиву: запись по-прежнему требует отдельного подтверждения предложения пользователем.

На обычных вопросах инструменты создания предложений не передаются модели: они доступны только при явной просьбе добавить или изменить сведения. Визуальный анализ файла фотографии тоже включается только по просьбе описать изображение; поиск и открытие снимка используют его метаданные. Для однозначных запросов о родстве со связанным человеком, диаграмме рождений, наиболее многолюдном фото, показе найденных фотографий и сводке пробелов сервер завершает ответ непосредственно из результата соответствующего read-only инструмента. Это устраняет лишний завершающий вызов модели и исключает неподтверждённые пересказы точных расчётов.

По явной просьбе модель может вызвать `create_pdf` и приложить PDF из подготовленного текста. Файл доступен только создавшему его участнику по временной ссылке в течение 30 минут. В PostgreSQL байты лежат во временном закрытом каталоге архива на общем томе backend-процессов: другой процесс и перезапущенный backend могут выдать тот же файл после повторной проверки прав. Общий лимит таких файлов для архивов одного сервера — 64 МиБ; в нём учитываются и физически оставшиеся файлы после сбоя, пока очистка их не удалит. При удалении диалога файл удаляется; при запуске и периодически очищаются файлы удалённых диалогов и устаревшие файлы. В SQLite временный файл по-прежнему хранится в памяти процесса и исчезает после перезапуска. Инструмент недоступен через MCP; содержимое ограничено 30 000 символами. PDF поддерживает кириллицу благодаря включённому в релиз шрифту DejaVu Sans.

Запросы «сделай экспорт», «экспорт древа в PDF», «скачай GEDCOM» и «сделай роспись» обрабатываются отдельно от генерации PDF-отчёта. Чат показывает доступные варианты файла; PDF древа создаётся тем же браузерным экспортом, что и контекстное меню, в текущем виде или со всеми ветвями. GEDCOM 7/5.5.1 и текстовая роспись строятся сервером из разрешённой участнику проекции архива; для росписи нужен выбранный человек. Полный GEDZIP с медиа по-прежнему доступен только администратору через меню экспорта.

## MCP

Endpoint:

    https://<host>/mcp

Авторизация:

    Authorization: Bearer drevo_mcp_...

Токен создаётся администратором в разделе «Управление → MCP-токены». Новые токены дают выбранные read-only возможности для всего архива; пользовательская привязка сохранена только для совместимости с ранее созданными токенами. Полный секрет возвращается только при создании; в SQLite хранится SHA-256 и короткая подсказка.

Scopes:

- tree:read — поиск людей, карточки, семья, предки и потомки;
- sources:read — источники;
- analysis:read — родство, пробелы, противоречия и сводная аналитика.

MCP работает stateless поверх JSON-RPC. Для MCP 2026-07-28 поддержан `server/discover` и прямые `tools/list` / `tools/call`; для клиентов 2025-era сохранён `initialize` и `notifications/*`. Дополнительная runtime-зависимость от MCP SDK для первого read-only слоя не требуется.

Встроенный ассистент умеет запускать детерминированный `get_branch_insights`: выбранный человек, направление ветки и глубина задаются отдельно, а Drevo сам считает полноту, пробелы и предупреждения до передачи результата модели.

Все опубликованные MCP tools на первом этапе read-only.

## Граница доверия

Языковая модель объясняет и сопоставляет сведения, но вычисляемые проверки выполняет Drevo. Запись реализована только через узкие `propose_*` операции. Они создают отдельное предложение и никогда не меняют семейный граф до нажатия пользователем кнопки подтверждения.

## Предложения изменений

Пользователь с правом редактирования может попросить ИИ сохранить конкретное уточнение как предложение. Для карточки человека доступен tool `propose_person_update`.

Предложение хранится отдельно от семейного графа и содержит исходные значения полей, новые значения, основание, дополнительные свидетельства и ревизию архива. В сообщении ИИ оно показывается как «было → станет» с кнопками ✓ и ×. Текстовое «подтверждаю» не применяет изменение и возвращает пользователю предложение нажать одну из этих кнопок.

До подтверждения семейный архив не меняется. При принятии сервер повторно проверяет права и доменную валидацию. Если затронутое поле изменилось после создания предложения, применение останавливается конфликтом вместо тихой перезаписи новых данных.

Поддерживаются четыре типа предложений: новый человек, безопасные поля карточки человека, новый источник карточки и новая связь между существующими людьми. Для связи `parent` направление явно задано как «from = родитель, to = ребёнок»; супружество симметрично, дополнительные роли используют те же направления, что и обычная модель Drevo.

Источник и связь тоже не меняют архив до ручного подтверждения. Перед применением Drevo проверяет, что соответствующие источники или связи не изменились после создания предложения, а затем пропускает результат через обычные права и `validateFamily`.

## Исследовательский backlog

`get_research_backlog` строит план следующего поиска без участия языковой модели в ранжировании. Tool может работать по всему архиву или по выбранной ветке и глубине.

Для каждого человека Drevo формирует кандидаты документов: запись о рождении/крещении, запись о браке, запись о смерти/погребении и перепись/посемейный список/домовую книгу. Приоритет учитывает, какие пробелы документ способен закрыть, есть ли уже поисковые ориентиры по году и месту и насколько человек близок к выбранному узлу ветки.

Результат содержит причину приоритета, ожидаемые поля и известные ориентиры для поиска. Тип документа остаётся обобщённым: конкретный архивный фонд или учреждение зависит от страны, периода и административной истории и не придумывается Drevo без источника.

## Вероятные дубли

`find_possible_duplicates` отделён от `find_inconsistencies`: возможный дубль является гипотезой, а не ошибкой архива.

Сначала Drevo сужает число пар по нормализованному имени, затем выставляет балл по совокупности признаков. Учитываются кириллическое/латинское написание фамилии, небольшие опечатки, фамилия при рождении, отчество, известный год рождения и смерти, частично совпадающие места, общие родители и супруги. Неизвестный год не считается конфликтом, а заметно разные известные годы снижают балл.

Tool возвращает только пары выше порога и объясняет, какие признаки повысили оценку и какие известные данные ей противоречат. Даже высокий балл остаётся кандидатом для ручной проверки и не приводит к автоматическому объединению карточек.

## Ссылки из ответа

Веб-ИИ возвращает вместе с текстом структурированный список `references`. Список строится сервером из результатов реально выполненных tool-calls, а не извлекается моделью из собственного текста.

Для человека reference содержит стабильный `personId` и отображаемое имя. Имена становятся ссылками прямо в тексте ответа и открывают соответствующую карточку. При неоднозначном поиске ИИ выводит кликабельных кандидатов, поэтому пользователю не нужно искать внутренний ID. Для источника reference содержит владельца карточки, название, архивную ссылку и безопасный HTTP/HTTPS URL, если он был записан в источнике.

Сервер ограничивает число возвращаемых references. Разрешённые фотографии могут быть показаны ссылкой на снимок; face descriptors, аккаунты и служебные поля не включаются.

## Настройка AI Studio в админке

В разделе **«Yandex AI»** администратор платформы задаёт API-ключ и Folder ID, затем выбирает модель из списка, который сервер получает для этого каталога через `/models`. Владелец или администратор отдельного древа без платформенного допуска не может менять подключение, запускать проверку или получать список моделей. Для сохранённого API-ключа интерфейс показывает только источник конфигурации; прочитать ключ обратно нельзя.

Можно временно выключить встроенного ИИ-исследователя без удаления конфигурации, заменить API-ключ, удалить локально сохранённый ключ и вернуться к env fallback, изменить Folder ID или модель. Изменения применяются к следующим запросам без перезапуска Drevo и записываются в аудит без значения секрета.

Кнопка **«Проверить подключение»** создаёт временную Yandex Conversation и выполняет минимальный запрос к Responses API с определением function tool, compaction и truncation. Это проверяет необходимые для исследователя возможности выбранной модели. Затем временная conversation удаляется best-effort.

## Лимиты и наблюдаемость

Администратор задаёт три независимых ограничения: число запросов в минуту на пользователя, число запросов в день на весь архив и число токенов в день на весь архив. Значение `0` отключает соответствующий лимит. При превышении минутного лимита `/api/ai/chat` отвечает HTTP 429 и, когда возможно, заголовком `Retry-After`; запрос в AI Studio при этом не выполняется.

Одна пользовательская реплика считается одним запросом Drevo. Если для неё модель делает несколько function-calling раундов, они отражаются отдельно как `providerCalls`. Для Responses API токены берутся из `usage` ответа AI Studio; отсутствующее значение записывается как ноль, а не как выдуманное использование. `cached_input_tokens` сохраняет сообщённую провайдером часть входных токенов. Отдельный вызов анализа фото по Chat Completions по-прежнему использует оценку, если `usage` отсутствует. Счётчик не является биллинговым документом.

В админке показываются дневные запросы, provider calls, input/output/total tokens, ошибки, средняя задержка и последние технические записи. Таблица `ai_usage` не хранит тексты сообщений, ответы модели или аргументы Research Tools.

## MCP: аудит и rate limit

Каждый MCP-токен имеет собственный лимит запросов в минуту. По умолчанию это 60 запросов/мин; `0` отключает ограничение. При превышении endpoint отвечает HTTP 429 с `Retry-After`, не выполняя Research Tool.

Для валидных RPC-вызовов Drevo хранит технический журнал `mcp_usage`: токен, RPC-метод, имя инструмента для `tools/call`, результат и задержку. Параметры JSON-RPC, аргументы Research Tools, поисковые строки и идентификаторы из arguments не сохраняются.

Администратор видит дневное число вызовов, ошибок, среднюю задержку по токену и последние технические записи в разделе **«MCP-токены»**.

## Потоковый ответ

Веб-интерфейс использует `POST /api/ai/chat/stream`. Drevo отвечает как `text/event-stream` и отправляет события:

- `status` — текущий этап обработки без чувствительных аргументов tools;
- `chat` — ID локального чата при начале нового запроса;
- `delta` — подготовленный сервером проверенный текст ответа;
- `done` — финальный текст, проверенные ссылки `references` и созданные файлы `files`;
- `error` — ошибка после открытия потока.

Запросы к Responses API выполняются с `stream: true` для потокового endpoint. Сервер собирает финальный `response.completed`, исполняет структурированные `function_call`, возвращает `function_call_output` с исходным `call_id` в ту же conversation и только после проверки посылает готовый ответ браузеру. `POST /api/ai/chat` сохранён как JSON endpoint для совместимости.

Rate limits, дневные лимиты, usage-метрики, права доступа и ResearchSuggestion применяются к обоим endpoint одинаково. Nginx-буферизация для SSE отключается заголовком `X-Accel-Buffering: no`.

## Диаграммы и проверка ответов

`get_lifespan_statistics` использует ту же доступную проекцию Family и scope `analysis:read`, что и остальные аналитические инструменты. Включает детские смерти по умолчанию, отдельно возвращает число записей, пропуски и неопределённость частичных дат; `adultsOnly` включается по явной просьбе. Возраст считается в полных годах, для неполных дат берётся середина возможного диапазона. Живущие не входят в среднюю завершённую жизнь. Готовое поле `mermaid` содержит подписи поколений и размер выборки.

Чат нормализует альтернативные языки fenced-блоков `xychart`, `xychart-beta`, `pie`, `graph` и `flowchart` в поддерживаемый Mermaid до рендеринга, в том числе для истории. Подписи с пробелами сохраняются целиком; несовпадение количества подписей и чисел отклоняется. Сообщения пользователя этой нормализации не подвергаются.

Остановка ответа находится в форме ввода: самолётик сменяется квадратом на время обработки активного чата. Переключение диалогов не останавливает остальные запросы. При перетаскивании древа окно чата временно становится полупрозрачным; собственное перемещение окна и программные движения камеры этого не включают.

Живая проверка модели: [сценарии и результаты от 25 сентября 2026](ai-research-evaluation-2026-09-25.md).

## MCP: область данных

Интерфейс выдаёт новые MCP-токены на весь архив и предлагает только выбрать read-only набор разрешений. Существующая серверная поддержка `boundUserId` оставлена для ранее созданных интеграций: такой токен наследует `treeAccess` и `personId` участника.

Для `common_ancestors` MCP использует тот же `projectFamilyForUser`, что и веб-интерфейс: Research Tools получают только разрешённую проекцию Family. Отдельная параллельная реализация правил доступа не вводится.

Если привязанный участник заблокирован, аутентификация токена прекращается. Если участник удалён, связанный токен удаляется каскадом. Это не позволяет удалению или блокировке случайно превратить ограниченный токен в токен всего архива.

## Совместимость внешних MCP-клиентов

Drevo проверяется в CI официальным TypeScript-клиентом `@modelcontextprotocol/client@2.0.0` в двух режимах:

- `versionNegotiation: { mode: "auto" }` — должен выбрать modern era `2026-07-28` через `server/discover`;
- `versionNegotiation: { mode: "legacy" }` — должен пройти initialize lifecycle 2025-era.

Оба smoke-теста выполняют `tools/list` и реальный `tools/call` через Streamable HTTP с Bearer-токеном. Modern responses содержат обязательный `resultType`, server identity в `_meta`, а cacheable `server/discover` / `tools/list` — консервативные `ttlMs: 0` и `cacheScope: "private"`.

Явный cross-origin HTTP-запрос к `/mcp` блокируется с 403; серверные MCP-клиенты без Origin продолжают работать. Это соответствует требованию Streamable HTTP проверять Origin при его наличии.

### Yandex AI Studio MCP Hub

Для развернутого Drevo:

- Transport: **Streamable HTTP**
- URL: `https://<drevo-host>/mcp`
- Authorization type: **Access token**
- Authorization header value: `Bearer <drevo_mcp_token>`

Для AI Studio лучше выдавать отдельный токен с минимальными scopes и, если агент не должен видеть весь архив, привязать его к участнику с нужным `treeAccess`. Секрет MCP-токена показывается Drevo только при создании.

CI подтверждает wire-совместимость с официальным MCP-клиентом. Отдельная живая проверка именно из Yandex AI Studio MCP Hub остаётся deployment-задачей, потому что для неё нужны публичный HTTPS endpoint и реальный секретный токен.

### Проверка после выкладки

Репозиторий содержит `ops/check-mcp.sh`. С реальным MCP-токеном он проверяет публичный HTTPS endpoint через modern `server/discover`, затем `tools/list` и `tools/call search_people`. Это отделяет ошибки приложения от проблем reverse proxy/TLS до подключения Yandex AI Studio MCP Hub.

Production Nginx имеет отдельный `location = /mcp`: Authorization передаётся явно, buffering отключён, тайм-аут увеличен для Streamable HTTP.

## Yandex Web Search

Внешние сведения ищутся через `web_search` в существующем agent loop:

```text
createResearchRunner → web_search → WebSearchService → WebSearchProvider
                                                        └─ YandexWebSearchProvider
                                                           └─ yandexResponsesClient
```

В коде приняты фабрики `createWebSearchService` и `yandexWebSearchProvider`.
HTTP composition root (`ai-research-http.ts`) передаёт сервис агенту; tool не импортирует Yandex.
Новые SDK и зависимости не нужны. Основная LLM и существующие инструменты сохраняются.

### Включение

В админке AI включите «Поиск в интернете». По умолчанию выключен, чтобы обновление само не добавляло платные запросы.
Провайдер — Yandex, начальный scope всегда `trusted`.
Используются существующие серверные `YANDEX_AI_API_KEY`, `YANDEX_AI_FOLDER_ID`,
`YANDEX_AI_MODEL`, опционально `YANDEX_AI_BASE_URL` (по умолчанию `https://ai.api.cloud.yandex.net/v1`).
Зашифрованные credentials и модель из настроек Drevo имеют прежний приоритет над env.
Отдельный ключ поиска не требуется; сервисному аккаунту нужны права на AI Studio и поиск.
Поддержку web search выбранной моделью и квоты нужно проверить в своём облаке.

Дополнительные серверные переменные (пример — `.env.example`):

- `AI_WEB_SEARCH_ENABLED=false`: начальное значение переключателя; сохранённая настройка админки важнее.
- `AI_WEB_SEARCH_PROVIDER=yandex`: выбор реализации; неизвестное значение не включает tool.
- `AI_WEB_SEARCH_TIMEOUT_MS=60000`: общий срок одного поиска, от 1000 до 90000 мс.

Ключ не передаётся клиенту, в tool output или диагностику. Не используйте `VITE_` для credentials.

### Каталог и режимы

Единственный реестр — существующий каталог **«Ресурсы поиска»**, таблица `research_resources`.

Пункт **«Ресурсы»** в основной и мобильной навигации открывает справочник `/resources`: категории,
поиск по названию, описанию и адресу, прямые ссылки на сайты. Он получает данные из того же реестра
через `GET /api/research-resources`, без отдельного списка или AI-запроса. Чтение доступно участникам
с доступом к древу и гостям публичного древа; редактирование остаётся в админке. Справочник показывает
все записи, включая выключенные для автоматического веб-поиска. API отдаёт только название,
описание, URL и идентификаторы; параметры поискового backend не нужны для просмотра.

Все существующие ресурсы с корректным HTTP(S) доменом доступны для trusted search.
Адаптер `web-search-sources.ts` получает домен из URL и начальные категории из категории каталога;
он не содержит самостоятельного списка сайтов. Настройки конкретной записи хранятся в `ai_search`.

Для добавления источника добавьте запись в админке ресурсов. Укажите ссылку, при необходимости
переопределите домен, назначьте категории через запятую (`archives,genealogy`, `military,ww2`,
`books,newspapers` и т. п.) и приоритет (большее число раньше). Допустимы новые английские идентификаторы
категорий: они автоматически попадают в schema tool. Выключите «Разрешить веб-поиск ИИ» для закрытых,
неиндексируемых ресурсов. Это не удаляет ресурс из справочника.

`trusted` — значение по умолчанию. Категории объединяются по OR; источники с большим числом совпавших
категорий идут раньше, далее учитывается приоритет и порядок каталога. Whitelist формирует сервер,
передавая Yandex `filters.allowed_domains`. Произвольный `allowedDomains` в tool input отклоняется.

Yandex допускает **до пяти доменов** в одном вызове. Drevo выбирает одну группу и возвращает
`searchedDomains`, `remainingDomains`, `nextSourcePage`. Следующую группу агент запрашивает явно
параметром `sourcePage`, поэтому ни один ресурс не исключён навсегда и нет скрытого веера платных запросов.
Если категории не заданы, группы идут по приоритету всего каталога.
`global` передаётся явно; whitelist отсутствует. Автоматического global fallback и повторов при ошибке нет.
Для явно выбранного global категории и номер страницы справочника игнорируются:
они относятся только к trusted и не должны блокировать расширение поиска.
Агенту предписано сначала искать и уточнять запрос в trusted, расширять поиск только при недостатке сведений
или явном запросе пользователя. Каждый поиск учитывается в существующей статистике вызовов и токенов;
стоимость Search API отдельно не вычисляется.
Если результаты относятся к другому региону или сайт нужного архива ещё не проверен,
агенту предписан global-поиск с полным названием, регионом и шифром. Ответ после поиска
должен содержать Markdown-ссылку из полученной выдачи: иначе выполняется одна попытка
уточнения. Если ссылки снова нет, вместо неподтверждённого ответа показывается список
страниц для проверки. Это проверка наличия источников, а не автоматическое доказательство
достоверности каждого утверждения модели.

### Источники и ограничения API

Формат проверен по официальной документации 28 сентября 2026:
[Web Search](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/agents/tools/websearch),
[пример Responses API](https://aistudio.yandex.ru/en/docs/ai-studio/operations/agents/create-websearch-text-agent).
Используется `/responses` с `tools: [{ type: "web_search", filters: { allowed_domains: [...] } }]`.
Yandex самостоятельно решает, выполнять ли встроенный поиск. Пустые citations дают `WEB_SEARCH_NO_RESULTS`.
Один вызов ограничен одним встроенным поиском (`max_tool_calls: 1`) и бюджетом
6000 выходных токенов, который включает рассуждения модели. Следующий поисковый
запрос при необходимости выбирает основной агент. Незавершённый ответ не считается
пустой выдачей: возвращается `WEB_SEARCH_INCOMPLETE`, а полученная статистика токенов
учитывается даже при таком сбое. Агент получает явное указание не делать из ошибки
поиска вывод об отсутствии документа.
Если за весь ответ ни один внешний поиск не завершился, итог заменяется сообщением
о сбое поиска: неподтверждённое «документ не найден» пользователю не передаётся.

Во время долгих поисков и генерации сервер каждые 20 секунд отправляет SSE-комментарий
`keep-alive`, чтобы reverse proxy не закрыл соединение по тайм-ауту бездействия.
Разрыв соединения с браузером по-прежнему не отменяет сохранённый диалог.
Ошибки SSE от провайдера показываются понятным сообщением без сырого тела ошибки;
код ошибки и идентификатор ответа доступны в `ai.turn_failed` для диагностики.
Если внешний поиск уже вернул ссылки, а следующий вызов модели оборвался или
превысил тайм-аут, ссылки сохраняются в ответе с явным предупреждением о незавершённом
анализе (`ai.web_answer_fallback`). Это не применяется при явной остановке пользователем
или наличии подготовленных изменений/файлов. Удалённый контекст сбрасывается;
следующий запрос восстанавливает историю из локального диалога.

Документированный `url_citation` гарантирует URL, но **title может быть пустым, позиции фрагмента — нулевыми**.
Поэтому нельзя честно восстановить поисковый snippet из этого API. Результат всегда содержит поля
`title`, `url`, `domain`, `snippet`; отсутствующий заголовок заменяется названием ресурса/доменом,
а отсутствующий фрагмент остаётся пустым с `snippetKind: "unavailable"`. Синтезированный текст находится
отдельно в `summary` и явно обозначен как ответ поисковой модели, а не цитата страницы.
Для настоящих выдержек в будущем нужен backend с документированными snippets или отдельное безопасное чтение страниц.
`maxResults` ограничивает только выдачу Drevo (1–10); это не параметр Yandex и не обещание числа результатов.
Фильтры языка и диапазона дат не заявлены для используемого API, не входят в schema и отклоняются.

Ссылки сохраняются в существующих references сообщения, показываются в раскрывающемся списке чата
и доступны для Markdown-цитирования. Найденная страница и совпадение имени не доказывают идентичность человека
или исторический факт: агент должен сообщать неопределённость и необходимость сверки первичного документа.

Нормализуются hostname, IDN и `www`; допускаются только совпадающий домен и его поддомены.
Удаляются URL-дубли, fragment и известные tracking-параметры; HTTP/HTTPS учитываются как один ключ.
Объявленные страницей canonical URL не загружаются и не принимаются на веру.
Отбрасываются credentials в URL, нестандартные порты, очевидные redirect wrappers и чужие домены.
При отбрасывании citations по whitelist общее резюме также убирается, поскольку его факты нельзя безопасно
связать с оставшимися источниками. Drevo не переходит по найденным страницам или их редиректам;
при последующем открытии страницы пользователем её перенаправления и содержание могут измениться.
Доменный фильтр не ограничивает путь: например, ресурс `yandex.ru/archive` разрешает домен `yandex.ru`.

Внешний текст всегда считается недоверенными данными. В system/tool instructions запрещено выполнять
инструкции из выдачи. Передаётся только запрос поиска, без истории архива, в отдельный запрос Responses.
По документации Yandex поиск использует индекс Яндекса и работает вне контура, аттестованного по ФЗ-152;
учитывайте это при включении функции и выборе данных для внешнего запроса.

Ошибки возвращаются контролируемыми кодами `WEB_SEARCH_UNAVAILABLE`, `WEB_SEARCH_TIMEOUT`,
`WEB_SEARCH_RATE_LIMITED`, `WEB_SEARCH_INVALID_CREDENTIALS`, `WEB_SEARCH_MALFORMED_RESPONSE`,
`WEB_SEARCH_UNSUPPORTED_FILTER`, `WEB_SEARCH_INVALID_INPUT`, `WEB_SEARCH_INVALID_CATEGORY`,
`WEB_SEARCH_CANCELLED`, `WEB_SEARCH_INCOMPLETE`; пустая выдача — `WEB_SEARCH_NO_RESULTS`.
Отмена запроса пользователя прерывает поиск. Логи содержат только provider, scope, проверенные категории,
число доменов/результатов, длительность и тип ошибки, без запросов, тела ответа и ключей.

## Продолжение ответа после перезагрузки

Запущенный ответ принадлежит сохранённому диалогу. Перезагрузка или закрытие вкладки
закрывает доставку SSE, но не отменяет серверную обработку. Готовый ответ сохраняется
в истории; открытый чат периодически проверяет серверный `busy` и получает результат.
Это работает в пределах жизни серверного процесса: перезапуск сервера не возобновляет
незавершённую генерацию, а оставшаяся lease-блокировка истекает через минуту.

Кнопка «Остановить ответ» доступна и для запроса, запущенного до перезагрузки или в другой
вкладке. Она вызывает `POST /api/ai/chats/:id/stop`; только владелец диалога с прежней
областью доступа может остановить работу. `DELETE /api/ai/chats/:id` также сначала
отменяет активную генерацию. Блокировка снимается после выхода agent loop, чтобы
завершающийся запрос не записал ответ в удалённый диалог или поверх нового запроса.
Сигнал отмены передаётся и при создании/восстановлении Yandex conversation.

При нескольких backend-процессах остановка записывается в БД для текущего lease.
Исполнитель проверяет её каждую секунду и перед фиксацией предложения или ответа.
Эти проверки также отсекают поздний ответ, если lease истёк или перешёл другому исполнителю.
В PostgreSQL проверка перед записью удерживает строку lease до конца короткой
транзакции; обращение к провайдеру выполняется вне неё. Запись или сброс удалённого
контекста привязаны к токену исполнителя, поэтому старый ход не меняет контекст нового.
Сигнал старого запроса не переносится в следующий ход; запрос удаления ждёт до
двух секунд и возвращает 409, если исполнитель ещё не освободил блокировку.
Допуск запроса и запись входного сообщения атомарны с проверкой общих и личных
лимитов количества запросов. Лимит токенов проверяет уже известный расход,
без предварительного резервирования стоимости незавершённых ответов.

## Восстановление после сбоя модели

`yandex-responses.ts` завершает чтение SSE по `response.completed`, не ожидая
закрытия сокета. `response.incomplete` сохраняет причину и response ID, а не
превращается в ошибку отсутствующего события. Ошибки авторизации, ограничения
частоты и тайм-ауты различаются в UI; журнал содержит endpoint и тип ошибки,
без текста запроса и ответа провайдера.

На шаг модели отводится 60 секунд. За ход допускается одна попытка восстановления
после тайм-аута/502/503/504 или `incomplete_max_output_tokens`: новая remote
conversation, восстановленная локальная история, непотоковый ответ, общий бюджет
повторной попытки 60 секунд. Если инструменты уже выполнялись, восстановление
получает последние восемь результатов (не более 20 000 символов каждого,
усечение помечается) и завершает ответ с отключёнными инструментами. Выполненные
действия не повторяются. Найденные веб-источники сохраняет существующий fallback
со ссылками, без дополнительной генерации. На последней разрешённой итерации
инструменты также отключаются: модель должна подвести итог и назвать ограничения.
Отмена пользователя и 401/403/429 не повторяются автоматически. При восстановлении
длинного диалога сохраняются первые два сообщения и последние десять: повторные
«ку» после ошибок не вытесняют исходный вопрос.
Неудачный ответ провайдера оставляет в локальном контексте скрытый служебный статус
с безопасным текстом ошибки. Следующий ответ может объяснить зафиксированный сбой;
модели запрещено выдумывать ожидание архива или продолжающуюся работу. Исходное
сообщение провайдера и credentials в этот статус не попадают.

Только для отдельного поискового запроса семейства Qwen
передаётся `reasoning.effort: none`. Это отключает отдельный режим рассуждений,
сохраняя вызов поиска. Основной агент и остальные модели получают свои настройки по умолчанию: проверка создания человека показала ухудшение выбора инструментов при отключении рассуждений основному агенту.
[Документация Yandex о поддержке режимов](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/chain-of-thought).
На ответ агента задан предел 8000 выходных токенов. Этот бюджет включает рассуждения
модели; при подтверждённом `incomplete_max_output_tokens` единственная повторная
попытка получает 16 000. Это может увеличить стоимость хода и не гарантирует успешный
ответ. Поиск сохраняет свой бюджет 6000.
За один ход допускается до трёх внешних поисков, после чего инструмент убирается
из следующего запроса; сервер также отклоняет вызовы сверх лимита.

Проверка 28 сентября 2026 года, изолированная временная база и реальный API с
`qwen3.6-35b-a3b/latest`: старый код выполнил семь поисков и через 122 секунды
завершился ошибкой лимита инструментов. Исправленный код завершил продолжение
«да ищи в гасо» после двух «ку» за 8 секунд, выполнив один внешний поиск.
Это отдельные наблюдения, не SLA и не проверка достоверности найденной архивной
записи. Production-журнал исходного инцидента отдельно зафиксировал тайм-аут
90 секунд до первого инструмента и три более ранних отказа 403 при создании
контекста; точную причину этих отказов на стороне провайдера восстановить нельзя.

Регрессии воспроизводит `tests/ai-response-recovery.test.ts`: незакрывающийся поток,
незавершённый ответ, восстановление контекста, запрет бесконечных повторов,
различение отказа доступа, завершение по сохранённым результатам без повторного
выполнения инструментов, восстановление после лимита токенов и бюджет поиска.

## Вычисления и документальная обоснованность

`get_distribution_statistics` выполняет точный расчёт в доменном слое на всей
доступной пользователю выборке. Признаки: фамилия, поколение, пол, десятилетие
рождения, место рождения и количество известных родителей. Ответ содержит частоты,
размер выборки, пропуски, энтропию Шеннона в битах, формулу и нормированное значение.
Первые 50 категорий ограничивают только выдачу, а не расчёт. Неизвестные значения
исключаются явно. Это энтропия выбранного распределения, не универсальная
«энтропия древа» и не оценка качества исследования. Произвольный код не выполняется.

`get_evidence_coverage` возвращает сводку по всей выборке и отдельную страницу
карточек с `offset`/`hasMore`. Наличие ссылки в карточке не подтверждает факт:
инструмент не читает документы и не проверяет отдельный каталог PDF. Модель должна
отделять учёт источников от анализа их содержания и не делать вывод «доказательств
недостаточно» только по неполной странице карточек. Регрессии:
`tests/distribution-statistics.test.ts`.

## Code Interpreter: Python, графики и таблицы

В **Админка → Yandex AI** включите общую галочку **Code Interpreter** и сохраните
настройки. По умолчанию она выключена. В «Доступ по ролям» возможность называется
**Вычисления Python и файлы**. Общий выключатель имеет приоритет над разрешением
роли. Роли с общими настройками получают эту возможность после общего включения;
ранее сохранённым индивидуальным профилям нужно включить её отдельно. Отключённый
ИИ или персональный запрет AI по-прежнему блокирует доступ.

Агент вызывает `run_code_interpreter`, сервер собирает выбранные поля уже
авторизованной части древа, а существующий Yandex-клиент загружает JSON через Files
API и делает отдельный Responses-запрос с `code_interpreter`. Используются модель
AI-профиля, прежний серверный API-ключ и Folder ID; новых env-переменных и SDK нет.
При отказе модели Drevo сообщает о недоступности среды, не подменяя модель автоматически.
Yandex рекомендует модели с большим контекстом, например Qwen. Требуются права
`ai.assistants.editor`, `ai.languageModels.user` и scope ключа
`yc.ai.foundationModels.execute`.

Инструмент получает описание расчёта, список необходимых полей и необязательные
ID людей. Без ID берётся вся доступная выборка; недоступные ID отклоняются. Пустой
список полей позволяет считать без выгрузки архива. Заметки, документы, фотографии,
учётные данные и произвольные локальные файлы не выгружаются. Связи ограничиваются
людьми выбранной выборки. Данные и результаты исполнения считаются недоверенными
данными, не инструкциями агенту. Код выполняется только в Yandex, не на сервере Drevo.

Ограничения Drevo: два вызова за ход, до четырёх запусков кода в каждом запросе,
90 секунд ожидания включая загрузку и скачивание, 16 000 выходных токенов,
2 МБ входного JSON. В конфигурации контейнера передаются память `1g` и
`network_policy: {type: "disabled"}`. Эти ограничения должен поддерживать backend;
при отказе Drevo не повторяет запрос с ослабленными ограничениями. Отмена чата
прерывает HTTP-запросы; это не гарантия мгновенного завершения кода у провайдера.
Yandex описывает срок жизни автоматического контейнера как 20 минут без активности.

Из аннотаций текущего контейнера принимаются PNG, CSV, XLSX, TXT, JSON и PDF
(последний только при разрешённом PDF в профиле). До трёх файлов за расчёт,
10 МБ на файл и 20 МБ суммарно. Ссылки на чужие контейнеры и произвольные URL не
скачиваются. Файлы выдаёт существующий `/api/ai/files/:id` как вложения, только
владельцу с действующим доступом к диалогу и прежней областью доступа. Локальные
ссылки действуют 30 минут и теряются после перезапуска сервера. Расчёт не записывает
результаты в карточки. Для новых файлов расчёта общий буфер вложений ограничен 64 МБ.

После обработки сервер пытается удалить загруженный файл и обнаруженные выходные
файлы через Files API; очистка имеет отдельный лимит 5 секунд и выполняется также
при отмене. На входном файле задан резервный срок хранения 1 день — минимальный
срок в Files API. При обрыве процесса или ответа провайдера неизвестные выходные
файлы могут остаться у Yandex; полного удаления таких файлов Drevo не гарантирует.
В журнале есть длительность, количество строк/файлов и ошибки очистки, без кода,
запросов пользователя и секретов. Расход токенов среды учитывается в статистике AI;
счёт за контейнер определяется тарифом Yandex и не представлен лимитом токенов Drevo.

Проверки: `tests/code-interpreter.test.ts`, `tests/code-interpreter-http.test.ts`,
`tests/ai-role-profiles.test.ts`, `tests/e2e/ai-role-profiles.spec.ts`.
SQLite обновляет колонку при запуске, PostgreSQL — миграцией
`ops/postgres/020_code_interpreter.sql`. Проверки провайдера используют mock API,
реальный запуск Python в Yandex ими не подтверждается.

Документация API: [пример Code Interpreter](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/agents/use-code-interpreter),
[контейнеры](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/agents/tools/code-interpreter),
[загрузка файлов](https://aistudio.yandex.ru/ru/docs/ai-studio/api/Files/createFile).
Песочница не заменяет проверку документальных свидетельств.

### Вложения и библиотека диалога

Скрепка рядом с полем сообщения выбирает несколько файлов; их также можно
перетащить в любую часть окна ассистента. До отправки вложение можно убрать.
Поддерживаются PDF, JPEG, PNG, WebP, TXT, Markdown, CSV, TSV, JSON, GEDCOM и XLSX.
Текстовые файлы должны быть в UTF-8. Лимиты: 3 файла за сообщение, 5 МБ на файл,
10 МБ суммарно; в библиотеке одного диалога — до 100 файлов и 100 МБ.
XLSX требует включённого Code Interpreter; фотографии — разрешения анализа фото.
Кнопка «Вложения» показывает все отправленные файлы текущего диалога, позволяет
скачать оригинал или начать вопрос о выбранном файле.

Новые вложения передаются в текущий запрос. Старые файлы модель выбирает через
`read_chat_attachments`: без `fileIds` получает каталог, с ID — читает до трёх
файлов общим размером до 10 МБ. Чужие ID и произвольные пути недоступны.
Выбранные файлы также передаются в Code Interpreter через существующий Files API;
очистка удалённых копий и срок хранения такие же, как для данных расчёта.
Фотографии обрабатывает настроенная модель анализа фото. PDF передаётся выбранной
основной модели как `input_file` с `filename` и `file_data` по
[контракту Yandex Responses](https://aistudio.yandex.ru/en/docs/ai-studio/api/Responses/createResponse).
Для PDF модель должна поддерживать файловый ввод; Drevo не меняет её автоматически
при отказе провайдера. Содержимое текстового файла в контексте ограничено первыми
40 000 символами с явной отметкой усечения; полный файл доступен Code Interpreter.
Распознавание изображений может ошибаться. Вложения считаются недоверенными данными,
а не инструкциями для агента и не автоматически проверенными доказательствами.

Оригиналы хранятся сервером в `uploads/ai-chat-files/<chatId>/` под случайными
именами, метаданные — в существующей истории сообщений. Эта папка входит в резервную
копию uploads. Публичных `/media`-ссылок нет: `/api/ai/attachments/:chatId/:fileId`
проверяет владельца, доступ к AI и прежнюю область доступа к архиву. Перезагрузка
страницы и перезапуск сервера сохраняют библиотеку. Удаление диалога удаляет и
оригиналы; после каскадного удаления аккаунта осиротевшие папки старше суток
убираются при следующем запуске сервера. Резервные копии живут по общей политике
хранения резервных копий архива.

На пользователя в архиве разрешено до 10 сохранённых диалогов. Ограничение
проверяется атомарно в SQLite/PostgreSQL, включая параллельные запросы. Старые
диалоги сверх лимита не удаляются автоматически: сначала нужно удалить лишние.
Диалог с прежними правами доступа можно удалить из списка, но его текст и вложения
после изменения области доступа не выдаются. Новых env-переменных и миграций нет.

Проверки вложений: `tests/ai-attachments.test.ts`, `tests/code-interpreter.test.ts`,
`tests/e2e/research-attachments.spec.ts`. Проверка лимита PostgreSQL включена в
`tests/integration/postgres-runtime.ts`. Сетевые вызовы Yandex в тестах заменены mock.
