# DNA: архитектура веб-приложения

**Статус: согласованное направление и план, без реализации. Решение от 27 сентября 2026 года.** Этот документ не означает, что DNA API, хранилище или анализ уже доступны. Работы согласуются с [миграцией PostgreSQL](postgres-migration.md) и изоляцией архивов из [дорожной карты](roadmap.md).

## Границы приложения

Drevo остаётся веб-приложением. Отдельного desktop client, Electron/Tauri, нативного клиента, локального Rust-модуля, desktop-only storage и локального native DNA engine в клиенте не будет. DNA не проектируется под возможный desktop-клиент. Дополнительные вычислительные мощности подключаются только как backend worker/service.

```text
Drevo Web UI
  ↓
Drevo API / Backend
  ↓
DNA domain/services
  ├── metadata storage
  ├── raw DNA import
  ├── DNA match import
  ├── segment analysis
  ├── relationship estimation
  └── evidence system
  ↓
PostgreSQL metadata/results + отдельное защищённое DNA/raw storage
```

Frontend загружает файлы, показывает статус импорта, управляет тестами, совпадениями и доказательствами, отображает хромосомы и связывает совпадения с людьми и предками. Парсинг raw DNA, нормализация, сравнение генотипов и тяжёлый анализ выполняются на сервере. Любое исключение для обработки в браузере требует отдельного обоснования; штатный поток от него не зависит.

Домен содержит независимые от HTTP, хранилища и внешних программ модели и правила. Серверные сервисы координируют доступ, импорт, хранение и задания. Браузерные Workers для геометрии древа остаются отдельной задачей и не становятся DNA engine.

## Метаданные и raw dataset

В PostgreSQL хранятся `DnaTest`, `DnaMatch`, `DnaSegment`, `DnaEvidence`, метаданные импорта и результаты анализа. Все записи и операции относятся к проверенному сервером архиву и соответствующим разрешениям на DNA. Право просмотра карточки человека само по себе не открывает генетические данные.

| Сущность | Назначение |
| --- | --- |
| `DnaTest` | Тест, его владелец/привязка к человеку, провайдер, происхождение и ссылка на dataset |
| `DnaMatch` | Импортированное или рассчитанное совпадение, сводные показатели, источник и подтверждаемая привязка к человеку |
| `DnaSegment` | Нормализованный сегмент: хромосома, координаты, genome build, единицы и доступные показатели качества |
| `DnaEvidence` | Генетическое свидетельство в пользу или против гипотезы о связи/предке, основание, автор и статус проверки |

Raw genotype может содержать сотни тысяч SNP. **Не создавать ORM-строку на каждый SNP в PostgreSQL**, в том числе в виде обходной таблицы импорта. Генотипы хранятся отдельно: compressed object/blob, indexed compressed file, binary representation или dedicated DNA storage. Конкретный формат выбирается при реализации импорта по требованиям потоковой записи и последующего чтения; предметная модель не зависит от него.

Поля `DnaTest`, относящиеся к raw dataset:

```text
provider
genomeBuild
rawDataFormat
rawDataReference
rawDataChecksum
snpCount
importedAt
```

`rawDataReference` — непрозрачная серверная ссылка, а не публичный URL или путь, который выбирает клиент. Она разрешается только серверным хранилищем после проверки прав. При отсутствии raw dataset ссылка и связанные поля отсутствуют: импорт совпадений не требует загрузки генотипов. `importedAt` фиксируется после успешного завершения, `snpCount` — по принятому нормализованному набору. Неизвестный genome build не подменяется догадкой; несовместимые сборки не сравниваются как одинаковые.

Файлы, индексы и промежуточные данные находятся вне `public/`, `dist/` и каталогов с публичной раздачей. Raw genetics и метаданные хранятся раздельно. Обычные API возвращают разрешённые метаданные и результаты, без генотипов, внутренних ключей объектов и путей хранения.

## Потоковый импорт

```text
Browser → streaming/multipart upload → Backend
  → format detection → stream parser → normalization
  → защищённое DNA storage → metadata/results в PostgreSQL
```

1. До принятия данных сервер проверяет архив, отдельное разрешение на DNA, ограничения размера и доступность места. Имя файла и заявленный MIME не считаются подтверждением формата.
2. Backend принимает поток с backpressure. Определение формата использует ограниченный заголовок; парсер обрабатывает записи порциями. Не читать весь файл через `readFile`, `arrayBuffer`, `text` или накопление всех SNP в массиве. Не передавать весь raw DNA через JSON API. Ограничения действуют и на распакованный объём, длину записи и время обработки.
3. При приёме сервер потоково вычисляет SHA-256 исходного файла для `rawDataChecksum`. Дубликаты проверяются в пределах разрешённого владельцу/архиву контекста, без раскрытия наличия чужих datasets. Это обнаружение одинакового файла; одинаковые генотипы в разных форматах не считаются найденными этим checksum автоматически.
4. Парсер нормализует данные, считает принятые SNP и агрегированные ошибки, записывает защищённый временный dataset. Диагностика не содержит исходных строк генотипов. Формат и genome build сохраняются явно; неподдерживаемый формат завершается понятной ошибкой.
5. Dataset становится доступен только после завершения записи, проверки целостности и сохранения метаданных. Между файловым хранилищем и PostgreSQL предусмотреть восстановление после сбоя и уборку осиротевших объектов; частичный файл не помечается как успешно импортированный. Повтор запроса не создаёт второй завершённый импорт.
6. UI получает идентификатор импорта и состояния «Загрузка», «Обработка», «Готово», «Ошибка», «Отменено», прогресс и безопасную сводку. Отмена/обрыв/ошибка освобождают временные данные; возобновление работы после сбоя не публикует неполный результат.

Импорт `DnaMatch` и `DnaSegment` имеет собственные адаптеры форматов провайдеров и тот же контроль прав. Он сохраняет происхождение и отличает импортированный результат от вычисленного Drevo. Сам по себе импорт совпадения не создаёт человека или подтверждённое родство.

## Серверный анализ

При реализации ввести узкую backend abstraction `DnaAnalysisEngine`. Ни браузер, ни доменная модель не зависят от CLI, файловых форматов и моделей конкретного внешнего инструмента. Ниже — план контракта, а не существующие типы приложения:

```typescript
interface DnaAnalysisEngine {
  estimateKinship(input: KinshipInput): Promise<KinshipResult>;
  findIbdSegments(input: IbdInput): Promise<IbdSegment[]>;
}
```

Входные типы содержат серверные ссылки на разрешённые datasets, genome build и параметры анализа; это внутренний контракт, не JSON API с массивами SNP. Результаты нормализованы в понятия Drevo и сохраняют метод, версию алгоритма, параметры, происхождение и ограничения оценки. Импортированные сегменты и предположение о родстве не выдаются за подтверждённую родословную.

Первая реализация может ограничиться базовым анализом доступных сводных показателей и импортированных сегментов. Если поиск IBD или иной метод ещё не поддерживается, сервис возвращает явное состояние «не поддерживается», а не пустой список как доказательство отсутствия совпадений. Объём первой реализации фиксируется до включения функции в UI.

Позже серверный адаптер может запускать PLINK 2, KING, IBIS, Beagle или hap-ibd в изолированном worker/process/container:

```text
Drevo API → DNA Analysis Service → Job Queue / Worker
  → внешний инструмент → normalized result → PostgreSQL
```

Это возможные будущие инструменты, а не обязательные зависимости первого этапа и не обещание одинаковых возможностей всех engines. Worker ограничивается по CPU, памяти и времени, получает только нужные datasets, проверяет актуальные права перед запуском и публикацией результата и удаляет промежуточные файлы. Конвертация форматов и специфические параметры остаются в адаптере. Очередь/отдельный сервис вводятся по потребности длительных заданий; API уже в первом этапе не должен блокироваться тяжёлым анализом.

## Приватность и жизненный цикл

DNA считается особо чувствительными данными. Эти условия обязательны до включения загрузки:

- Raw DNA не попадает в application logs, analytics, трассировки, тексты ошибок, дампы HTTP-запросов или вывод внешнего инструмента в общий журнал. В аудите достаточно идентификаторов действий, исполнителя и результата, без генотипов; диагностический сбор соблюдает те же ограничения.
- Обычные endpoints карточек, дерева, поиска, JSON/GEDCOM-экспорта, публичных ссылок, ИИ и MCP не возвращают raw genotype. Генетические метаданные и результаты также требуют явно определённого доступа, независимо от публичности древа.
- Raw DNA endpoints требуют отдельной серверной авторизации: аутентификация плюс явное разрешение на действие и конкретный dataset. Сессия или роль редактора архива сами по себе недостаточны. Если появится скачивание raw, оно проходит через эту границу, без публичных URL файлов.
- Encryption at rest распространяется на исходные и нормализованные datasets, индексы, временные файлы и резервные копии. Ключи и разрешения отделены от данных; до выпуска выбираются механизм, управление ключами и процедура восстановления. Передача — по защищённому соединению.
- Полное удаление охватывает исходник, нормализованные копии, индексы, временные данные, кэш и генетические результаты согласно политике удаления теста. Задания отменяются; отложенный worker не может опубликовать результат удалённого теста. Связанные evidence удаляются или явно теряют основание, а не сохраняют скрытую копию генотипов.
- Для резервных копий до выпуска определить срок физического удаления либо уничтожение относящихся к данным ключей и проверяемую процедуру. Восстановление бэкапа применяет журнал удаления до возобновления доступа и не возвращает удалённые datasets. Пользователь видит состояние удаления; завершение не заявляется, пока предусмотренные копии остаются доступными.
- Checksum служит обнаружению повторного импорта, а не авторизации. Метаданные и raw genetics хранятся раздельно; служебный доступ к хранилищу ограничивается необходимыми операциями.

Статический HTML-пакет, переносимый архив дерева и обычный экспорт не включают raw DNA автоматически. Возможный отдельный DNA-экспорт требует явного выбора и тех же специальных разрешений.

## Web UI

DNA-раздел является частью основного Drevo:

```text
Person → DNA
  ├── Tests       — тесты и состояние импорта
  ├── Matches     — совпадения и привязка к людям
  ├── Chromosomes — chromosome browser
  └── Evidence    — основания гипотез о родстве и предках
```

В русскоязычном интерфейсе: «Тесты», «Совпадения», «Хромосомы», «Доказательства». Chromosome browser — обычный SVG/Canvas web-компонент, который получает разрешённые сегменты и подготовленные результаты, а не весь raw genotype. Нужны понятные единицы, genome build, происхождение сегментов, клавиатурное управление и текстовое представление выбранного сегмента. Специализированный desktop renderer не предусматривается.

## Этапы и приёмка

1. **Хранение и доступ:** PostgreSQL-модель, отдельные DNA-разрешения, закрытое raw storage, encryption at rest, правила удаления и бэкапов. Проверить изоляцию двух архивов и отсутствие доступа через обычные API/публичные ссылки.
2. **Импорт и Tests:** потоковая загрузка, адаптер первого формата, checksum, прогресс, отмена и уборка. На файле с сотнями тысяч SNP измерить ограниченное потребление памяти; проверить дубликат, обрыв, повреждённый файл, сбой записи и отсутствие генотипов в логах/analytics.
3. **Matches, Chromosomes, Evidence:** импорт совпадений и сегментов, происхождение, привязки с подтверждением, SVG/Canvas. Проверить различие импортированного совпадения, вычисленной оценки и подтверждённого человеком доказательства.
4. **Базовый анализ:** реализовать согласованный объём `DnaAnalysisEngine`, ограничения и воспроизводимость результатов. Проверить неподдерживаемые методы, отзыв прав и удаление dataset во время задания.
5. **Позже, при необходимости:** очередь и изолированные внешние engines с нормализованными результатами. Их отсутствие не блокирует первый выпуск.

Для проверок использовать синтетические fixtures без реальных генетических данных. Документ задаёт целевую архитектуру DNA; он не переключает текущую БД и не меняет действующие права приложения.
