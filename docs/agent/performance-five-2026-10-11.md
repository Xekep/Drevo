# Пять оптимизаций — 11 октября 2026

Изменения подготовлены по команде пользователя после UI-аудита. Этот документ
описывает код и проверки; факт публикации подтверждается отдельно релизом.

## Изменения

1. **Редактор обсуждений.** `discussion/lazy-comment-editor.tsx` показывает лёгкое
   нативное поле. CodeMirror загружается после фокуса или вставки Mermaid, включая
   редактирование старого сообщения. Текст, выделение и фокус переносятся в редактор;
   при сетевой ошибке остаётся обычное поле с повтором загрузки. Чтение обсуждения
   не требует CodeMirror. Объём discussion chunk уменьшился с 537,73 до примерно
   40 kB; отдельный редактор — около 501 kB / 175 kB gzip. Это размеры build,
   не замер времени загрузки в production.
2. **Приоритет чтений.** `data/archive-details.ts` обслуживает текущую пачку
   карточек/снимков/разделов между группами фоновых страниц (до 160 элементов).
   Очередь сохраняет единственного владельца снимка и не голодает фон при новом
   потоке запросов. Не меняются повтор чтения после конфликта, токен доступа и
   защита от отката завершённой записи. Приоритетный снимок из поздней страницы
   не исчезает и не меняет окончательный порядок всей коллекции.
3. **Проекции и галерея.** `projection=insights` возвращает результаты анализа,
   а не биографии, награды и источники всех людей. `projection=places` возвращает
   события и фотографии; полные массивы событий сохраняют свидетельства при
   изменении координат. Уже прочитанные сведения карточек не затираются.
   Галерея получает по 30 объектов: альбомы с обложкой/счётчиком либо снимки.
   Для перелистывания передаётся отдельный список ID в порядке альбома;
   соседние кадры и прямые ссылки читаются `projection=photos` через SQL `IN`
   (максимум 40 ID), с теми же ограничениями доступа. Автоподгрузка проверяет
   короткие/повторяющиеся страницы, гонки фильтров и двойное нажатие.
4. **Холодная раскладка.** Для графов больше 900 людей на desktop с точным
   указателем, шириной от 1024 px, минимум восемью логическими процессорами и
   известным `deviceMemory >= 8` используются не больше двух ELK Worker.
   Освободившийся слот получает следующий seed без ожидания медленного соседа.
   Результаты оцениваются в прежнем порядке, с теми же критериями контактов,
   длины/поворотов, наложений и размеров. Неоконченные задачи дожидаются завершения
   до следующего расчёта. Кеши и анимации не обходятся; геометрия не упрощается.
5. **CI.** Сборка и статические проверки — `prepare`; её artifact используется
   четырьмя E2E shard на независимых VM и отдельной группой unit/built-worker.
   У каждой VM свой сервер и SQLite, подготовленные изображения наград и модели.
   Обязательный статус `check` выполняется даже при отказе зависимости и требует
   `success` всех групп. PostgreSQL workflow не заменён и не ослаблен.

## Раскладка: измерено

Синтетический `randomFamily(5, 9)`: 977 людей. Реальный Chrome, собранный Worker,
пустая страница без React/Canvas, новый Worker для каждого запуска. Три пары,
порядок чередуется. Сборка и тесты во время измерения не выполнялись.

| Запуск | Один Worker, ms | Два Worker, ms |
| --- | ---: | ---: |
| 1 | 3052,7 | 2384,6 |
| 2 | 2927,8 | 2365,7 |
| 3 | 2992,1 | 4147,1 |
| Медиана | 2992,1 | 2384,6 |

Медиана уменьшилась примерно на 20%; был и медленный параллельный запуск.
Это локальный замер холодного расчёта, не обещание такой скорости на каждом
компьютере, не FPS и не production benchmark. SHA-256 **всей** геометрии всех
шести запусков совпал с прежним алгоритмом:
`1026d591cba21d38edc0a4cfbff3170edbfe2f3809366f80ec9875ddd8637e0a`.

Начальный Node-эксперимент с ожиданием целых пар кандидатов не дал ускорения:
два запуска из трёх стали медленнее. В браузере этот начальный вариант дал
только около 6% по медиане. Именно поэтому рабочий вариант использует очередь
с освобождением слотов, а не барьер `Promise.all` каждой пары.

## Ограничения

- Карта всё ещё получает все фотографии и события, необходимые для её точек.
  Кластеры с загрузкой по viewport пока не реализованы.
- Сервер сводки/карты/галереи использует существующий кеш ревизионного снимка,
  уже ограниченного правами. Постраничная выдача не означает, что устранены все
  серверные расходы полного снимка. Агрегация альбомов остаётся на сервере
  в памяти; отдельный индекс ID тоже растёт с альбомом. SQL keyset pagination
  и проекция точек по viewport потребуют отдельного изменения контракта.
- Полные чтения остаются для проверки записей, подробной хронологии и операций,
  которым нужен полный архив. Начальное древо уже использовало лёгкий overview.
- Второй Worker увеличивает потребление памяти, поэтому неизвестные/мобильные/
  слабые устройства сохраняют последовательный расчёт.
- Deploy workflow пока выполняет полный E2E самостоятельно. Четыре shard
  сокращают критический путь проверки PR, а не автоматически весь deploy.

сохранение источников/биографий при загрузке карты, порядок и размер страниц,
приоритет чтения карточки/позднего снимка и сброс агрегатов после записи.
