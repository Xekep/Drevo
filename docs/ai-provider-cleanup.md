# Очистка диалогов у ИИ-провайдера

Статус на 4 октября 2026 года: первый этап реализован в PostgreSQL и слит в `main` в [PR #760](https://github.com/Xekep/Drevo/pull/760). Он охватывает новые зарегистрированные Conversations, обычное удаление чата и потерю привязки; каскады, административные тесты и операционный интерфейс остаются отдельной работой. Это не гарантия полного удаления данных у провайдера. Настройки Yandex AI доступны только администратору платформы.

## Что делает текущий код

`src/server/ai-research-http.ts` через `ai-chats.ts` атомарно переводит зарегистрированную привязку в платформенную очередь и удаляет локальный чат. `ai-provider-cleanup.ts` повторяет очистку после временных ошибок или завершения процесса; HTTP выполняется вне SQL-транзакции. Для прежних ID без проверенного исходного подключения и SQLite остаётся однократная попытка. `account-self-deletion.ts` собирает локальные ID для удаления файлов; каскадное удаление аккаунта, членства или архива пока не ставит активную привязку в очередь. `platform-ai-orphan-sweep.ts` очищает только файлы.

Проверка подключения `/api/admin/ai/test` в `admin-ai-http.ts` тоже создаёт Conversation и однократно удаляет его в `finally`; она должна участвовать в том же реестре. Каскады охватывают удаление членства через `runtime_member_deleted`, удаление личных чатов привилегированной функцией обезличивания аккаунта и удаление архива по внешнему ключу. Постановку в очередь нужно проверить для каждого пути, включая RLS и привилегированные функции.

Удалённый ID ещё лежит в `ai_chats` открытым текстом, а исходное подключение для очистки хранится зашифрованно в платформенном реестре. Из журналов завершения, ошибки и восстановления ответа удалены удалённые идентификаторы. `postgres-portable-backup.ts` обнуляет ID и ссылку на очередь в архивном TAR, сохраняя локальные сообщения; реестр и платформенный ключ туда не входят. Следующий ответ после переноса восстанавливает контекст из локальной истории в новом Conversation. Генеалогический `.drevo` не содержит ИИ-чатов.

`ai-research-runner.ts` после создания Conversation долговечно регистрирует известный ID с исходным подключением, затем проверяет результат условной привязки к текущему lease. Просроченная или потерянная привязка остаётся доступной очистке; обработанная ошибка регистрации вызывает однократную компенсацию с исходным подключением. Окно падения между удалённым POST и долговечной регистрацией полностью не закрыто. Запрос к провайдеру выполняется вне SQL-транзакции.

## Граница обещаний

Yandex прямо указывает, что удаление Conversation **не удаляет его элементы**. Отдельное удаление элемента сейчас не поддерживается. Поэтому успешный DELETE не подтверждает полное удаление содержимого у провайдера. [DELETE Conversation](https://aistudio.yandex.ru/en/docs/ai-studio/api/Conversations/deleteConversation), [DELETE элемента](https://aistudio.yandex.ru/en/docs/ai-studio/api/Conversations/deleteConversationItem).

AI Studio не поддерживает ключ идемпотентности. Если процесс завершился после создания Conversation на стороне провайдера, но до получения и долговечной записи ID, повтор POST не позволяет надёжно найти прежний объект. Этот остаточный риск должен быть указан отдельно; очередь решает повторяемое удаление уже известных ID. [Ограничения идемпотентности Yandex](https://yandex.cloud/en/docs/api-design-guide/concepts/idempotency).

## Этап 1 — реестр, очередь и восстановление

Реализован для PostgreSQL. Проверки используют временную БД и подставной провайдер: два пула, просроченный lease и чужое подтверждение, смена API-ключа, HTTP-удаление чата, ошибки провайдера и пара ключей. Полный CI #760 прошёл PostgreSQL, физическое восстановление, браузерные и Node-проверки. Он не выполнял удаление рабочих диалогов у Yandex.

- Платформенные таблицы PostgreSQL без внешних ключей, удаляющих строку вместе с аккаунтом или архивом. Состояния: активная привязка, ожидающее удаление, выполняющаяся попытка, повтор, блокировка из-за конфигурации, завершение.
- Неизменяемые ID Conversation, базовый URL, Folder ID и исходный API-ключ хранятся зашифрованно отдельным платформенным ключом с версией. Новый ключ не создаётся вместо отсутствующего ключа существующего реестра. Не использовать ключ архива: он исчезает при удалении архива. Не выводить ID, конфигурацию и секреты в клиент или журналы; в операционном статусе достаточно локального ID задания, состояния и категории ошибки.
- Короткая транзакция забирает ограниченную порцию через `FOR UPDATE SKIP LOCKED`, выдаёт токен и срок lease. Сетевой DELETE с таймаутом выполняется после освобождения SQL-соединения. Подтверждение и перенос срока повтора принимаются только для действующего токена.
- Успех и 404 завершают задание. Таймаут, 429 и временные 5xx повторяются с ограниченным exponential backoff; 401/403 сохраняют заблокированное задание для администратора, а не теряют его. Потеря процесса оставляет задание доступным после истечения lease.
- Системная резервная копия включает таблицы и соответствующий платформенный ключ. pgBackRest сохраняет БД, но сам по себе не сохраняет внешний файл ключа. Проверить совместное восстановление и ошибку при отсутствии ключа; исключить реестр, указатели активных привязок и ключ из переносимого пакета отдельного архива.

Системный медиа-TAR включает основной `ai-provider-cleanup.v1.key` и побайтово равную приватную копию в `backups/platform-keys/`. Парная репетиция сверяет обе копии с отпечатком в восстановленной PostgreSQL; отсутствие, неверный ключ, широкие права или размер больше 4096 байт отклоняются. Она не запускает приложение или провайдера. Реализована одна версия ключа, ротация платформенного ключа ещё не предусмотрена. `backup-files.ts` копирует ключ отдельного архива; такой TAR не является физической платформенной копией. `restore.ts` подготавливает прежний архивный ключ, но не применяет его автоматически к рабочей конфигурации. [Пути, права и пределы восстановления](ai-provider-cleanup-operations.md).

## Этап 2 — связывание и компенсация

Условная привязка, смена/сброс удалённого контекста и обычное удаление чата реализованы. Далее нужно атомарно переводить прежнюю привязку в очередь при каскадном удалении аккаунта, членства или архива и регистрировать временные Conversations административной проверки подключения. Несколько backend-процессов не должны подтверждать чужую попытку или удалять новую привязку старого исполнителя.

Обычное локальное удаление зарегистрированного чата не ждёт доступности Yandex. Нужно добавить отдельный платформенный статус отложенных и заблокированных попыток; такого интерфейса пока нет. Он не должен называть удалёнными данные, для которых API провайдера такого результата не гарантирует.

## Обязательная проверка

Проверки выполняются с подставным провайдером и временной БД, без удаления рабочих диалогов:

- создание → отзыв прав/удаление архива до привязки: известный ID остаётся в очереди;
- замена конфигурации и ключа, удаление локального чата/аккаунта/архива: используется сохранённое исходное подключение;
- два процесса, просроченный lease, завершение процесса между DELETE и подтверждением: повтор безопасен, чужой токен отвергается;
- 404, 429, 5xx, таймаут и 401/403: ожидаемые конечные/повторяемые состояния;
- восстановление БД с правильным, отсутствующим и неверным ключом; перенос отдельного архива не восстанавливает старые активные привязки;
- отсутствие секретов и удалённых ID в логах, HTTP-ответах, `.drevo` и архивном TAR.
