# Очистка диалогов у ИИ-провайдера

Статус на 4 октября 2026 года: для новых зарегистрированных Conversation в PostgreSQL работают долговечная очередь и постановка при удалении чата, членства, аккаунта, архива и после административной проверки подключения. Полного удаления данных у провайдера этот этап не гарантирует. Настройки Yandex AI доступны только администратору платформы; пользовательские права на чат не расширяются.

## Что делает текущий код

`src/server/ai-research-http.ts` через `ai-chats.ts` ставит зарегистрированный Conversation в платформенную очередь при явном удалении чата. `ai-provider-cleanup.ts` повторяет сетевой DELETE после временных ошибок и завершения процесса, не удерживая SQL-транзакцию. PostgreSQL-триггер ставит зарегистрированный ID в ту же очередь при удалении чата через членство, обезличивание и удаление аккаунта или FK-каскад архива. `account-self-deletion.ts` и `platform-ai-orphan-sweep.ts` отдельно очищают локальные файлы. Прежние удалённые ID без сохранённого исходного подключения не получают гарантию повторной очистки.

Проверка подключения `/api/admin/ai/test` регистрирует известный Conversation с исходным подключением во временном задании. `finally` переводит его в ожидание очистки; при падении процесса задание становится доступным worker после ограниченного срока. Проверки PostgreSQL охватывают `runtime_member_deleted`, привилегированную функцию удаления истории аккаунта, внешний ключ архива и откат транзакции под рабочей ролью с RLS.

Удалённый ID ещё лежит в `ai_chats` открытым текстом, но исходное подключение для очистки хранится зашифрованно в платформенном реестре. ID исключён из журналов завершения/ошибки ответа; архивный TAR обнуляет ID и ссылку на очередь, сохраняя локальную историю сообщений. Реестр и ключ туда не входят; генеалогический `.drevo` не содержит ИИ-чатов.

`ai-research-runner.ts` долговечно регистрирует известный ID до условной привязки к локальному чату и проверяет её результат. Неудачная привязка остаётся в очереди; при обработанной ошибке регистрации выполняется однократная компенсация с исходным подключением. Окно падения между успешным удалённым POST и записью ID полностью не закрыто. Запросы к провайдеру выполняются вне SQL-транзакции.

## Граница обещаний

Yandex прямо указывает, что удаление Conversation **не удаляет его элементы**. Отдельное удаление элемента сейчас не поддерживается. Поэтому успешный DELETE не подтверждает полное удаление содержимого у провайдера. [DELETE Conversation](https://aistudio.yandex.ru/en/docs/ai-studio/api/Conversations/deleteConversation), [DELETE элемента](https://aistudio.yandex.ru/en/docs/ai-studio/api/Conversations/deleteConversationItem).

AI Studio не поддерживает ключ идемпотентности. Если процесс завершился после создания Conversation на стороне провайдера, но до получения и долговечной записи ID, повтор POST не позволяет надёжно найти прежний объект. Этот остаточный риск должен быть указан отдельно; очередь решает повторяемое удаление уже известных ID. [Ограничения идемпотентности Yandex](https://yandex.cloud/en/docs/api-design-guide/concepts/idempotency).

## Этап 1 — реестр, очередь и восстановление

Реализован для PostgreSQL. Проверки используют временную БД и подставной провайдер: два пула, просроченный lease и чужое подтверждение, смена API-ключа, HTTP-удаление чата, ошибки провайдера и пара ключей. Полный CI #760 прошёл PostgreSQL, физическое восстановление, браузерные и Node-проверки. Он не выполнял удаление рабочих диалогов у Yandex.

- Платформенные таблицы PostgreSQL без внешних ключей, удаляющих строку вместе с аккаунтом или архивом. Состояния: активная привязка, ожидающее удаление, выполняющаяся попытка, повтор, блокировка из-за конфигурации, завершение.
- Неизменяемые ID Conversation, базовый URL, Folder ID и исходный API-ключ хранятся зашифрованно отдельным платформенным ключом с версией. Новый ключ не создаётся вместо отсутствующего ключа существующего реестра. Не использовать ключ архива: он исчезает при удалении архива. Не выводить ID, конфигурацию и секреты в клиент или журналы; в операционном статусе достаточно локального ID задания, состояния и категории ошибки.
- Короткая транзакция забирает ограниченную порцию через `FOR UPDATE SKIP LOCKED`, выдаёт токен и срок lease. Сетевой DELETE с таймаутом выполняется после освобождения SQL-соединения. Подтверждение и перенос срока повтора принимаются только для действующего токена.
- Успех и 404 завершают задание. Таймаут, 429 и временные 5xx повторяются с ограниченным exponential backoff; 401/403 сохраняют заблокированное задание для администратора, а не теряют его. Потеря процесса оставляет задание доступным после истечения lease.
- Системная резервная копия включает таблицы и соответствующий платформенный ключ. pgBackRest сохраняет БД, но сам по себе не сохраняет внешний файл ключа. Проверить совместное восстановление и ошибку при отсутствии ключа; исключить реестр, указатели активных привязок и ключ из переносимого пакета отдельного архива.

Системный медиа-TAR включает основной `ai-provider-cleanup.v1.key` и побайтово равную приватную копию в `backups/platform-keys/`. Парная репетиция сверяет обе копии с отпечатком в восстановленной PostgreSQL; отсутствие, неверный ключ, широкие права или размер больше 4096 байт отклоняются. Она не запускает приложение или провайдера. pgBackRest сам по себе сохраняет только БД: для физического восстановления необходима согласованная пара БД и ключа. Реализована одна версия ключа, ротация пока не предусмотрена. `backup-files.ts` копирует ключ отдельного архива; такой TAR не содержит платформенный ключ или реестр и не является физической платформенной копией. Внешнее хранение системной копии не настроено. [Пути, права и пределы восстановления](ai-provider-cleanup-operations.md).

## Этап 2 — связывание и компенсация

После успешного создания Conversation код долговечно записывает исходное подключение и ID, затем в короткой транзакции условно привязывает запись к локальному чату по текущему lease. Если привязка не состоялась, запись остаётся в очереди. Смена или сброс удалённого контекста, обычное удаление чата и PostgreSQL-каскады при удалении аккаунта, членства или архива переводят прежнюю привязку в очередь. Условные изменения по токену не позволяют одному backend-процессу подтвердить чужую попытку или удалить новую привязку старым исполнителем.

Каскады зарегистрированных привязок теперь охвачены PostgreSQL-триггером на удаление `ai_chats`: обычное удаление, удаление членства, привилегированное обезличивание и удаление аккаунта, а также внешний ключ архива переводят прежний ID в очередь в той же транзакции. Откат сохраняет чат и прежнее состояние задания. Восстановление семейных данных через `restoreStore.apply` чаты не заменяет; переносимый архив обнуляет удалённые ID и ссылки на очередь, а системное восстановление требует соответствующую пару БД и ключа.

`/api/admin/ai/test` по-прежнему доступен только администратору платформы. Успешно созданный Conversation получает отдельное временное задание с исходным подключением до проверки модели. Создание и ответ используют общий сигнал на 240 секунд; временная привязка истекает через 300 секунд после регистрации, чтобы падение процесса не оставило её активной навсегда. В штатном `finally` задание сразу становится ожидающим удаления. Сетевая очистка выполняется worker вне SQL-транзакции. Проверены ответ, отзыв платформенного права, ошибка провайдера, истечение временной привязки и отсутствие удалённого ID в HTTP-ошибке.

Локальное удаление остаётся быстрым и не зависит от доступности Yandex. Отдельный платформенный статус отложенных и заблокированных попыток остаётся следующей задачей. Он не должен называть удалёнными данные, для которых API провайдера такого результата не гарантирует.

## Обязательная проверка

Проверки выполняются с подставным провайдером и временной БД, без удаления рабочих диалогов:

- создание → отзыв прав/удаление архива до привязки: известный ID остаётся в очереди;
- замена конфигурации и ключа, удаление локального чата/аккаунта/архива: используется сохранённое исходное подключение;
- два процесса, просроченный lease, завершение процесса между DELETE и подтверждением: повтор безопасен, чужой токен отвергается;
- 404, 429, 5xx, таймаут и 401/403: ожидаемые конечные/повторяемые состояния;
- восстановление БД с правильным, отсутствующим и неверным ключом; перенос отдельного архива не восстанавливает старые активные привязки;
- отсутствие секретов и удалённых ID в логах, HTTP-ответах, `.drevo` и архивном TAR.
