# Технический аудит «Древа» — 12 сентября 2026

## Executive summary

**Production readiness: 4/10. Для закрытого семейного архива с реальными персональными данными выпуск в текущем состоянии не рекомендован.** Основные препятствия — модель допуска читателей, физическое удаление фотографий, некорректное восстановление авторских объектов и потеря биометрических образцов при обычной записи отношений. ## Реестр проблем

Каждая запись ниже — отдельная первопричина. Упоминания этих ID в тематических разделах не увеличивают число замечаний.

### [A01] Закрытый архив доступен любому новому пользователю Яндекса

Категория: Security / авторизация / privacy  
Severity: HIGH  
Priority: P0 — исправить немедленно  
Confidence: HIGH

Где: `src/server/users.ts:46`, `src/server/users.ts:62`, `src/server/archive-query-http.ts:30`, `src/server/archive-query-http.ts:83`, `src/server/media-http.ts:21`.

**Что происходит:** новый OAuth-пользователь автоматически становится reader. Чтение закрытого дерева, альбома и экспорта разрешено по наличию любого user, без проверки допуска в семью.

**Почему это проблема:** аутентификация у провайдера не подтверждает членство в конкретном архиве. Это соответствует нынешней модели ролей, но делает интерфейсное обещание «закрытый семейный архив» недостаточным для приватной семейной информации.

**При каких условиях проявится:** publicTree/publicAlbums выключены, OAuth доступен, посторонний входит своим аккаунтом.

**Последствия:** раскрытие биографий, дат, отношений, мест и фотографий; возможность массового экспорта. Понижение до reader не отзывает чтение; заблокированной роли нет.

**Как воспроизвести:** на отдельной БД установить ARCHIVE_PRIVATE=1; создать архив администратором; войти новым provider ID. Получено /api/family: 200 и /api/export.json: 200 вместо отказа; анонимный запрос получил 401. Подделывать чужую сессию не требуется.

**Как исправить:** отделить вход от допуска: pending/invited/approved/blocked, явное одобрение администратором, отзыв сессий при блокировке. Один policy допуска использовать в query/export/media/search/geocoding. Публичный просмотр оставить явно отдельной настройкой.

**Сложность исправления:** M.

### [A02] Удаление текущей ссылки уничтожает файл, необходимый истории и резервным копиям

Категория: Целостность данных / backup / файловое хранилище  
Severity: HIGH  
Priority: P0 — исправить немедленно  
Confidence: HIGH

Где: `src/server/database.ts:46`, `src/server/database.ts:351`, `src/server/database.ts:409`, `src/server/media-gc.ts:35`, `src/server/full-backup.ts:30`.

**Что происходит:** обычная запись после COMMIT удаляет оригиналы, отсутствующие в новом Family. Проверяется текущая модель, а не ссылки history и retained backup. Отдельный GC тоже ориентируется на текущее состояние.

**Почему это проблема:** SQL snapshot содержит URL, но не байты. Восстановление записи не восстанавливает удалённый файл. Создание full backup сначала фиксирует SQLite, затем асинхронно архивирует изменяемый uploads — удаление в промежутке также нарушает согласованность пары.

**При каких условиях проявится:** удаление фото/замена портрета, возврат прежних данных, восстановление старой SQLite, конкурентная сборка полного backup.

**Последствия:** необратимая потеря оригинала без отдельной полной копии; успешное восстановление JSON с неработающей фотографией.

**Как воспроизвести:** upload → удалить photo через changes → применить inverse changes. Получено 200 и восстановленная запись, но GET оригинала — 404; history ещё содержит URL. Это API/domain-проверка, не утверждение о наличии кнопки Undo в нынешнем UI.

**Как исправить:** отделить удаление ссылки от удаления bytes; tombstone и retention, учёт ссылок истории/backup/staging, pin набора файлов на время full backup. GC запускать только после вычисления достижимости и проверки срока хранения.

**Сложность исправления:** M.

### [A03] Валидный backup чужих авторских объектов невозможно применить администратору

Категория: Backend / restore / авторство  
Severity: HIGH  
Priority: P1 — до ближайшего релиза  
Confidence: HIGH

Где: `src/server/permissions.ts:24`, `src/server/permissions.ts:34`, `src/server/permissions.ts:42`, `src/server/restore.ts:308`, `src/server/restore.ts:401`.

**Что происходит:** owners() запрещает добавлять отсутствующий объект с createdBy другого пользователя ещё до ветки admin. Restore вызывает обычный archive.write с текущим администратором и сохранёнными авторами.

**Почему это проблема:** восстановление исторического объекта ошибочно обрабатывается как попытка подделать авторство при обычном создании.

**При каких условиях проявится:** relative создал человека/фото/связь, объект попал в backup и затем был удалён; администратор восстанавливает копию.

**Почему это проблема:** ограничение количества вершин не ограничивает глубину стека; валидный ациклический вход может завершиться техническим RangeError.

**При каких условиях проявится:** искусственная очень глубокая цепочка, например импорт с ошибочным смыслом связей. Десять тысяч реальных поколений для этого продукта неправдоподобны — это крайний случай, а не ожидаемая семейная нагрузка.

**Последствия:** отказ импорта/записи с технической ошибкой. Падение всего сервера не подтверждено; handlers перехватывают исключения.

**Как воспроизвести:** обратным порядком задать синтетическую parent-chain на 10 000 людей — Maximum call stack size exceeded.

**Как исправить:** итеративный DFS с собственным стеком и теми же цветами visiting/visited; отдельный осмысленный лимит сложности входа, если нужен.

**Сложность исправления:** S.

### [A30] Shutdown обрывает активные соединения до завершения обработчиков

Категория: SRE / lifecycle / надёжность  
Severity: MEDIUM  
Priority: P1 — до ближайшего релиза  
Confidence: HIGH

Где: `src/server/index.ts:160`, `src/server/index.ts:163`, `src/server/index.ts:185`, `ops/drevo.service:16`.

**Что происходит:** close() вызывает closeAllConnections до ожидания server.close, затем закрывает stores/SQLite. Учёта незавершённых async handlers нет.

**Почему это проблема:** остановка при deployment не даёт активным upload/backup/import/read закончиться; закрытие сокета не означает завершение async операции с хранилищем.

**При каких условиях проявится:** SIGTERM во время запроса, особенно файлового upload/архивирования.

**Последствия:** оборванные ответы, неопределённый результат записи, возможное обращение завершившего await handler к закрытому store. Порча SQLite этим не доказана.

**Как воспроизвести:** на отдельном сервере начать медленную загрузку/backup и вызвать close; порядок принудительного закрытия непосредственно следует из кода. Production не перезапускался.

**Как исправить:** перестать принимать новые запросы, дождаться активных handlers в пределах согласованного drain timeout, отменить оставшиеся работы, только затем закрыть SQLite/таймеры; forced close оставить последним шагом.

**Сложность исправления:** M.

### [A31] Основной production JavaScript передаётся без сжатия

Категория: Performance / HTTP / Mobile UX  
Severity: MEDIUM  
Priority: P2 — ближайшие итерации  
Confidence: HIGH

Где: `ops/nginx.conf:32`, `src/server/static-assets-http.ts:43`, `vite.config.ts:1`.

**Что происходит:** GET /assets/index-CSbGT7Ip.js с Accept-Encoding: gzip, br вернул 192 746 байт и не содержит Content-Encoding. Сборка оценивает gzip этого файла в 61,10 kB. HTML production сжимается.

**Почему это проблема:** на каждой холодной загрузке основного JS передаётся примерно втрое больше bytes, чем необходимо для gzip. Для крупных Workers/моделей эффект может быть больше, но их production-transfer отдельно не измерен.

**При каких условиях проявится:** холодный cache, новый релиз, мобильная сеть.

**Последствия:** больше трафика и времени загрузки/готовности интерфейса.

**Как воспроизвести:** безопасный GET публичного asset; результат сохранён в production-asset.json. Это проверка GET, а не ошибочный вывод по HEAD.

**Как исправить:** настроить gzip_types для JS/CSS/JSON/SVG и соответствующих модельных payload либо precompressed assets с корректными Content-Encoding/Vary; проверить GET и кеширование после изменения. Brotli необязателен для первого исправления.

**Сложность исправления:** XS.

### [A32] Приложение создаёт backup, который само отказывается восстанавливать

Категория: Backup / целостность / ограничения API  
Severity: HIGH  
Priority: P1 — до ближайшего релиза  
Confidence: HIGH

Где: `src/server/restore.ts:34`, `src/server/restore.ts:46`, `src/server/restore.ts:285`, `src/server/database.ts:351`, `src/server/database-backup-http.ts:50`.

**Что происходит:** экспорт SQLite не ограничен 32 MiB, но restore отклоняет SQLite больше 32 MiB. Full backup также может законно превысить пределы restore 128 MiB входящего / 512 MiB распакованного архива.

**Почему это проблема:** ограничения импорта не согласованы с допустимым объёмом данных и создаваемой самим продуктом копией. История из полных snapshots быстро увеличивает SQLite даже без фотографий.

**При каких условиях проявится:** крупное семейное дерево с несколькими версиями либо большой фотоархив. Ошибка не требует миллионов людей.

**Последствия:** кнопка резервирования работает, а штатный путь восстановления собственных данных — нет.

**Как воспроизвести:** создать синтетическую БД с 10 000 людей и биографией 512 ASCII-символов, выполнить шесть правок, writeDatabaseBackup → 63 557 632 байта; POST restore/preview → 400 «База больше 32 МБ». Результат: `work/audit-2026-09-12/backup-size-results.json`; независимый скрипт `backup-size.mjs`.

**Как исправить:** определить поддерживаемую ёмкость архива, согласовать export/restore limits с ней; проверять SQLite потоково/через read-only database с ограниченным рабочим набором. Для превышения интерактивного лимита предоставить проверенный offline restore. Сохранить защиты от decompression bombs и добавить round-trip собственного большого backup.

**Сложность исправления:** M.

API сейчас внутренний, без явной версии; это допустимо для общего релиза client/server. При введении внешних клиентов необходимо зафиксировать версию/схемы DTO. Текущая тесная связь ответов с Family отражена в A10/A11, не предлагается отдельный versioning ради самого versioning.

POST не имеют общего Idempotency-Key. Revision и checks предотвращают многие повторы, но не заменяют идентификатор операции при неизвестном исходе. Семейные даты допускают неполное историческое знание и не должны механически превращаться в UTC timestamp. Служебные даты в UTC/epoch; явная timezone-порча в проверенных путях не найдена. PK/FK включены для соединения, WAL и busy_timeout=5000 заданы. Connection pool для единственного DatabaseSync не используется и сам по себе не нужен.

Общие graph invariants, авторство и недопустимые связи проверяются в domain/server; внешняя запись непосредственно в SQLite может обходить JSON-level правила. Импорт открывает файл отдельно и прогоняет validation, а не просто подключает его как рабочую БД. Полнота восстановления зависимых данных всё равно нарушена A03/A04/A32.

### Запросы и рост объёма

- В проверенном archive read нет ORM N+1 на каждого человека: основные наборы читаются отдельными bulk queries. Полные сканы оправданы для полного экспорта/overview, но не для каждой мелкой правки и страницы tags.
- Pages используют LIMIT/OFFSET. Замер последней страницы 10 000 people показывает удорожание OFFSET; для текущего лимита это вторично относительно A10/A11. При росте фотоальбома нужна keyset/cursor pagination со стабильным порядком.
- Поиск по содержимому JSON/подстроке и полное построение Family не превратятся в индексный lookup автоматически. FTS/нормализованные searchable columns вводить под измеренные запросы, не заменять весь JSON «на всякий случай».
- Долгая BEGIN IMMEDIATE включает вычисления, сериализацию и history. В одном процессе это очередь event loop; с несколькими соединениями — конкуренция writer и ожидание busy_timeout. Deadlock не воспроизведён; нельзя называть обычную блокировку SQLite deadlock.
- Snapshot из нескольких SELECT без явного общего read transaction при нескольких writers требует отдельной проверки согласованности. В единственном синхронном процессе между этими SELECT нет await, поэтому автоматически объявлять torn read текущим багом нельзя.

| Количество записей | Что применимо |
|---|---|
| 10 000 people | Поддерживаемый предел валидации; локально измерен. Запись/первичная загрузка уже чувствительны; backup может не пройти restore |
| 100 000 people | Сейчас отвергается лимитом, нельзя обещать «выдержит»; просто убрать лимит недостаточно |
| 1 000 000 / 10 000 000 people | Неподдерживаемая модель продукта и непроверенная нагрузка. Нужны другой контракт выборок/команд и отдельный benchmark |
| 100 000+ tags/photos/samples/audit rows | Часть коллекций не имеет общего cap. A07/A12: scan/разбор/размер диска; полный Family и история становятся основным пределом |
| 1 000 000 / 10 000 000 таких строк | Ни latency, ни RAM не измерены. По коду полные scans/aggregate materialization делают текущие пути непригодными для заявления о поддержке |

## Performance и масштабирование

### Bottleneck сейчас

A10 — синхронная запись агрегата, A11 — последовательная сеть, A06 — память ожидания превью, A12 — повторный scan tags, A31 — несжатый JS. Для карты отдельный geocoder намеренно ограничен: 1,2 с между внешними запросами, pending≤32, максимум 1000 запросов/день на процесс, persistent cache до 5000 записей/180 дней. Один запрос места может потребовать Photon и Wikidata; нельзя считать лимит равным 1000 успешно определённым местам.

### Frontend: CPU, память, bundles

Из production build, десятичные kB:

| Артефакт | Размер | Gzip оценка сборки | Когда нужен |
|---|---:|---:|---|
| index JS | 192,74 kB | 61,10 kB | Начальная загрузка; фактически передан несжатым |
| App | 50,50 kB | 16,48 kB | Корневая оболочка |
| comparison-panel chunk | 256,14 kB | 83,23 kB | Содержит общие зависимости дерева; название chunk не означает, что всё можно просто отложить |
| domain | 34,09 kB | 10,56 kB | Семейная логика |
| основной CSS | 154,27 kB | 32,03 kB | Глобально импортирован из main |
| ELK Worker | 1 423,88 kB | Не измерено на production | Отдельный Worker раскладки |
| face-api | 1 314,45 kB | 329,63 kB | Lazy, при использовании распознавания |
| Leaflet/places | 163,48 kB | 48,98 kB | Lazy карта |
| memorial-dove PNG | 995,02 kB | Не применимо как JS | Иллюстрация профиля; кандидат на уменьшение/современный формат |

Не нужно суммировать все lazy chunks как «начальный JS». При этом все metadata в итоге материализуются в browser Family; частичная подгрузка не означает ограниченный объём памяти всего сеанса. Раскладка вынесена в Worker, видимость элементов React Flow ограничена; CPU раскладки всё равно зависит от размера графа. Фактическая плавность pan/zoom на 10 000 людей не измерена.

Оригиналы фото передаются потоково; thumbnails/display создаются Sharp, одинаковые pending deduplicated. Кеш готовых preview полезен, но A06 относится к холодному пути. Очистка производных previews не является полным privacy lifecycle оригиналов.

### Уровни одновременной активности — оценено по архитектуре

«Пользователь» не равен непрерывному HTTP-запросу. Результат зависит от размеров дерева, фото, интенсивности записи и попаданий в кеш. Следующая таблица качественная; production latency/RPS/CPU проценты не выдуманы.

| Уровень | Backend / DB | RAM / CPU / соединения | Latency / traffic / первый предел |
|---|---|---|---|
| 1 | Небольшой архив обслуживается обычным одиночным процессом; даже один большой save блокирует loop | Один DB handle, несколько HTTP-запросов браузера; lazy модели нагружают клиент | На большой базе первые ограничения — A10/A11/A32 |
| 10 | Чтение небольшого архива вероятно приемлемо; параллельные авторы конфликтуют по revision | Burst cold previews удерживает buffers; запросы обслуживает один event loop | Локально 10 overview на 10k people заняли ~762 мс как серия; не SLA на пользователя |
| 100 | Read/write contention и частая инвалидизация загрузочных tokens становятся существенными | 100 клиентов не означают 100 DB connections; HTTP sockets и pending work растут | Локально 100 коротких overview на 1k people завершились ~784 мс; активная запись/фото не проверены |
| 1 000 | Готовность не подтверждена; sync scans/write history — узкое место одного процесса | Большие transient buffers, очередь sockets, CPU/GC; диск при upload | Первыми вероятны рост очереди/тайм-ауты, при холодном альбоме — A06. Точное число выдерживаемых сессий неизвестно |
| 10 000 | Заявлять поддержку текущей архитектуры нельзя | Нужны admission control, shared storage и отдельная проверка read capacity; простой cluster ломает A16 | Burst overview/медиа может исчерпать RAM, CPU или канал; какой ресурс раньше — зависит от сценария |

Для ориентира объёма, а не throughput: 10 000 выдач измеренного overview размером 1 815 843 B составляют примерно 18,16 GB тела ответов до HTTP-сжатия. Это арифметическая иллюстрация повторной передачи полного графа, не выполненный benchmark.

### Несколько инстансов

Проверено, что технически два экземпляра могут открыть одну тестовую SQLite и ответить на health. Это не эквивалент горизонтальному масштабированию:

1. OAuth/staging требуют A16.
2. На разных хостах нужен общий media store; файловая SQLite поверх произвольного сетевого FS не является рекомендуемой заменой архитектуры.
3. Несколько процессов не устраняют стоимость aggregate writes и лимит одного SQLite writer.
4. Sticky sessions решают только привязку части последовательностей; restart всё равно обнуляет pending.
5. Миграции при rolling deployment и совместимость версии данных требуют A14.

Сначала достаточно одного управляемого writer и устранения лишней работы. Перенос на PostgreSQL/object storage оправдан после измеренного исчерпания одиночного узла или необходимости нескольких узлов, а не по названию технологии.

### HTTP / Core Web Vitals

На production: immutable cache для hashed assets, no-cache для оболочки, no-store для API, keep-alive в проверенных ответах. gzip HTML подтверждён, gzip JS отсутствует. Brotli/CDN не обнаружены по проверенному ответу; полную инфраструктуру по заголовку Server определить нельзя. **Не удалось проверить:** реально используемые клиентами HTTP/2/HTTP/3, TLS-конфигурацию целиком, CDN topology.

- **LCP:** потенциально задерживается initial JS/CSS, загрузкой данных и крупным портретным/decorative asset; численное значение не измерено.
- **INP:** Worker снижает работу main thread по геометрии; пересборка family/графа и тяжёлая face detection остаются кандидатами. Нет браузерного trace.
- **CLS:** изображения/контейнеры имеют ряд явных размеров, но progressive details и панели надо проверять фактически. Итоговый CLS неизвестен.
- **TTFB:** local HTTP серии приведены выше; реальный production navigation TTFB и распределение под нагрузкой не измерены.

## UX/UI, мобильная версия и accessibility

Основные пути по коду: вход → просмотр дерева → выбор человека/родства → редактирование → сохранение; альбом → upload → отметки/распознавание → портрет; карта → поиск/ручное уточнение; админка → роли/видимость/sharing → export/restore.

| Приоритетная проблема интерфейса | Конкретное изменение |
|---|---|
| A05: после тайм-аута неясно, что стало сохранённым | Показать результат сверки конкретных полей; сохранять base черновика, дать осознанный выбор local/remote |
| A19: Back теряет правки фото | Перехватить history navigation общей защитой draft; предложить остаться/сохранить/отбросить |
| A11: read-only до полной загрузки | Загружать подробности выбранного объекта; отдельно показывать progress альбома, сохранять уже доступный просмотр при ошибке |
| A03/A32: «копия проверена» не означает «можно восстановить» | Preview должен проверять применимость авторства и supported capacity; показывать точный блокер до подтверждения |
| A09: успех загрузки повреждённого файла | Валидация до сообщения об успехе, ошибка рядом с файлом, сохранение остальных полей формы |

Подтверждено по коду: loading/error/status-сообщения, native dialog.showModal для ряда редакторов, aria-label для icon buttons, перевод focus к ошибочному полю с раскрытием details, подтверждения удаления/несохранённых изменений в штатных кнопках. Сохранение имеет busy/saving guard от двойного клика. Эти механизмы не покрывают все пути навигации — A19.

Визуальную иерархию, контраст и clipping нельзя достоверно оценить только чтением отдельных CSS declarations: переменные переопределяются следующими stylesheets и в lightbox. Не объявлены дефектом старые значения --muted без учёта каскада.

**Не удалось проверить:** horizontal overflow на каждом размере, реальные target rectangles, сценарии pinch/long-press, browser zoom/reflow, OS screen reader и контраст итоговых пикселей.

Утверждения о соответствии WCAG в целом этот аудит не даёт.

Семантика/labels/alt проверены в основных компонентах; exhaustive accessible-name computation не выполнялось. CSS reduced-motion присутствует, listeners/ResizeObserver/Leaflet instances/Workers имеют cleanup в просмотренных hooks; подтверждённой обычной утечки event listeners не найдено. Потенциальная память очереди превью — backend A06, её нельзя описывать как React memory leak.

## Надёжность, наблюдаемость и эксплуатация

| Отказ / событие | Поведение и риск |
|---|---|
| SQLite не открывается / повреждена | Startup бросает ошибку, systemd restart-on-failure; нельзя подменять её seed. На синтетической корректной БД restart успешен |
| Медленная SQLite / другой writer | DatabaseSync блокирует loop; busy_timeout=5000 может задержать запросы, A10/A16 |
| Яндекс не отвечает / возвращает ошибку | Внешние fetch имеют 10-секундные сигналы, клиент видит страницу ошибки; причина теряется в серверном журнале, A18 |
| Photon/Wikidata недоступны | Ограниченные очередь/cache, timeout, pause при 429/503, частичные fallback; централизованной устойчивой очереди нет |
| Пользователь оборвал запрос | Media upload pipeline очищает временный файл при ошибке; результат уже выполненной записи может быть неизвестен, A05/A13 |
| Повреждённое фото | Upload может сообщить успех, A09 |
| Некорректный restore tar/SQLite | Есть ограничения размер/путь/тип, staged preview; собственный большой backup также отвергается, A32 |
| Диск заполнен | Атомарность SQLite защищает транзакцию, но storage/backup/upload откажут; предиктивного quota/disk-alert пути нет, A07/A18. Физический disk-full тест не выполнялся |
| Два изменения одного поля | 409 и client conflict selection предусмотрены; сверка после timeout нарушает гарантию A05 |
| Повтор нажатия Save | Клиентский saving ref и busy, серверная revision; это не durable idempotency для произвольного сетевого retry |
| Restart во время preview/OAuth | In-process stage пропадает, A16 |
| SIGTERM во время длинного запроса | Forced close, A30 |
| Ошибка нового релиза | Code rollback предусмотрен, совместимость схемы/повторный health недостаточны, A14 |

Не требуется добавлять circuit breaker ко всем SQLite операциям. Для внешнего geocoder уже есть ограничение/пауза, а для критичных записей опасны автоматические retries без operation ID. Нужны ограничение времени всей операции и явное восстановление неопределённого результата.

### Логи и возможность расследования

- Audit entries фиксируют бизнес-изменения и revision отдельно от последних 50 snapshots; это полезно для «кто изменил человека».
- Это не журнал входов/отказов авторизации/размеров запросов. Нельзя по нему установить всю последовательность security incident.
- Nginx access/error и stdout/stderr есть; request/correlation ID, стабильные error codes и общий structured log отсутствуют в текущей композиции, A18.
- URL secrets могут попасть в стандартный access log, A17. Токены провайдера в приложении не сохраняются, passwords отсутствуют.
- **Не удалось проверить:** реальный journald/nginx retention/rotation, права операторов к логам и backup, внешние alerting/metrics/tracing.
- Нужные эксплуатационные показатели конкретны: event-loop lag и длительность archive.write, pending/bytes preview queue, свободные bytes/inodes, age последнего полного внешнего backup, restore drill status, рост WAL/SQLite, OAuth/geocoder error rates. Они обслуживают A06/A10/A15/A18, а не декоративный dashboard.

### Deployment / CI/CD

Dockerfile и Compose отсутствуют; production использует systemd. Это не недостаток само по себе. Unit запускает процесс непривилегированным пользователем, ограничивает запись shared-каталогом, задаёт NoNewPrivileges/PrivateTmp/ProtectSystem/ProtectHome, restart policy и production env. Backend слушает loopback, TLS завершается на nginx.

GitHub CI проверяет PR, deploy повторяет проверки для push main; Actions закреплены SHA, SSH host key закреплён, secrets передаются через environment, release собирается отдельно, runtime dependencies урезаны до нужных серверу. Bash syntax deploy.sh дополнительно проверен локально: PASS.

Недостатки конкретны: A14/A15/A30, отсутствие browser coverage и dependency scan как pipeline gate — A24. Зависимости runtime устанавливаются отдельным npm ci; lock воспроизводим, но проверка advisory сейчас была ручной в рамках аудита. Ручной workflow_dispatch и защита main зависят от GitHub settings: **не удалось проверить**.

**Может ли плохой commit попасть в production?** Да: проходящий проверки семантический дефект вроде A04/A05 попадёт автоматически. Commit с ошибкой типов/lint/существующего теста штатный pipeline должен остановить. Утверждать возможность обхода branch protection без доступа к настройкам нельзя.

## Privacy, backup и disaster recovery

| Данные | Где | Удаление / экспорт / ограничения |
|---|---|---|
| Provider ID, display name, role | SQLite users | Паролей/Яндекс access tokens нет; удаления аккаунта через UI/API нет, процедура владельцем не определена |
| Сессии | auth_sessions, token hashes | Logout текущей сессии и expiry есть; также попадают в техническую SQLite-копию |
| Биографии, даты, родство, места, источники, фотоописания | Family JSON/relations/tags | JSON/GEDCOM export; удаление текущих данных не удаляет историю/audit |
| Фото и портреты | uploads, previews | Согласованная политика retention отсутствует, A02/A27 |
| 128-мерные samples | face_descriptors | Отправляются с браузера серверу; provenance/адресное удаление отсутствует, A08 |
| Журнал изменений | audit tables | Данные автора и diff сохраняются независимо от current Family; срок удаления в продукте не задан |
| Shared links | token hash + person IDs + expiry | Отзыв/истечение предусмотрены; raw URL может сохраняться в proxy logs, A17 |
| Географические запросы | SQLite cache, Photon/Wikidata | Во внешний сервис уходит текст места; OSM tiles запрашиваются браузером, провайдер видит сетевой адрес клиента и область карты |

Локальный face detection не означает, что вся биометрия остаётся на устройстве: descriptors передаются backend. Это существенное описание потока данных для интерфейса/политики продукта. Юридическое соответствие конкретной юрисдикции не оценивалось.

Для удаления пользовательских данных необходима явная политика владельца: какие записи удаляются сразу, какие остаются в business audit, сколько хранятся backup, как обрабатываются запросы на удаление биометрии. Наличие законного/договорного основания и реальное информирование людей **не удалось проверить**; репозиторий не позволяет сделать правовой вывод.

### Что необходимо резервировать и как восстанавливать

1. Согласованная SQLite (включая служебные таблицы) и оригиналы uploads одной точки восстановления; previews можно построить заново.
2. Production configuration, доступ к OAuth secrets, параметры DNS/TLS/SSH и идентификатор проверенного релиза — отдельно от публичных артефактов.
3. Внешняя копия и каталог retention. Только `shared/backups` на том же сервере не переживает его потерю.
4. Проверка: восстановить в новый отдельный каталог, запустить совместимую версию схемы, integrity_check + foreign_key_check, проверить counts/авторство/descriptors/выборочные хеши и открытие фотографий, вход и настройки приватности.
5. Только после успешной проверки выбирать cutover; не накатывать тестовую копию поверх production.

Административный restore семейных данных намеренно сохраняет текущие accounts/settings/audit/shares. Это не полный DR-restore сервера. Offline восстановление всей базы должно учитывать, что старые session hashes и access settings тоже возвращаются.

**RPO: не удалось определить. RTO: не удалось определить.** Частота deployment не равна расписанию резервирования, успешный restore drill не предоставлен. При потере единственного сервера восстановление возможно только из реально сохранённой внешней копии плюс конфигурация. A02/A03/A04/A32 означают, что даже наличие файла «backup» ещё не доказывает восстановимость.

## Целевая архитектура — только необходимые изменения

Сохранить React + native HTTP + чистый domain. Нужны более чёткие контракты внутри монолита:

- **AccessPolicy:** аутентификация, допуск к архиву и право на объект — отдельные решения; один policy используется API и media.
- **Archive commands:** операции над IDs и изменёнными полями, транзакция/author/revision/audit; persistence не удаляет сущность из-за порядка отображения.
- **Read models:** overview графа, person details, photo pages/search; UI не обязан получать полный Family для любой правки.
- **Draft session:** base revision + original object + локальные изменения, одинаковые правила navigation/conflict/reconcile.
- **Media registry:** immutable оригиналы, refs/tombstones/retention, очередь обработки с ограничением bytes, backup manifest.
- **Recovery/observability:** воспроизводимый restore совместимой версии и безопасный request lifecycle.

Замену SQLite выполнять только после исправления корректности и benchmark с реальным набором данных. Внешний object storage нужен при независимом масштабировании файлов/узлов или DR-требованиях; не решит сам по себе неправильный media lifecycle. Redis не обязателен для одного сервера.

## SEO и публичная веб-оболочка

Сайт доступен публично; семейные сведения при этом не обязаны индексироваться. Цель SEO зависит от выбранной политики publicTree/publicAlbums, а не от того, что оболочка отвечает 200.

- `index.html` содержит lang=ru, viewport, title, description, Open Graph/Twitter metadata и favicon. Содержание приложения CSR; индивидуальные карточки не имеют самостоятельного SSR/document metadata.
- Канонический URL, sitemap, robots.txt, structured data и web app manifest в tracked public-дереве не найдены. Для закрытого архива sitemap людей и SEO-разметка персональных карточек не нужны; это не production blocker.
- / и /tree открывают один раздел без canonical. Если требуется индексируемая публичная витрина, определить один канонический URL и отдельную безопасную landing page; не индексировать закрытые данные ради SEO.
- Shared pages/API явно отправляют noindex/nofollow/noarchive и no-referrer. Это полезно, но robots-заголовок не заменяет секретность token.
- Неизвестные маршруты и отсутствующие файлы возвращают 404, а не общую SPA-страницу 200. HTTP→HTTPS redirect предусмотрен nginx.
- `public/archive/family-notes.html` явно помечен вымышленным демонстрационным материалом; найденные в нём имена не объявлены утечкой реальных семейных данных.
- **Не удалось проверить:** реальную индексацию, Search Console, crawler rendering, social preview и метаданные публичной витрины в браузере.

К отчёту прилагается [архив диагностических скриптов и результатов](audit-2026-09-12-evidence.zip). Он содержит логи проверок, JSON результатов и использованные скрипты с manifest/SHA-256; рабочие/синтетические SQLite и бинарные фотографии в него не включены. После распаковки с сохранением путей скрипты располагаются в `work/audit-2026-09-12/` и запускаются из корня соответствующего commit с установленными dependencies.

Подтверждённые дефекты можно повторять на новых синтетических каталогах без обращения к рабочей БД. Скрипты benchmark/reproduce не выполняют нагрузку на production; extra-checks и asset-check читают только публичную оболочку/asset. Загружать полученные synthetic backups в реальную админку для воспроизведения не нужно.

В реестре **32 отдельные проблемы: 11 HIGH, 17 MEDIUM, 4 LOW, 0 CRITICAL**. Эти числа не являются оценкой покрытия: существенная часть браузерной и инфраструктурной проверки прямо оставлена непроверенной.

## Что сделано хорошо

Только подтверждённые решения:

1. `src/domain/` отделён от React/HTTP/SQLite; типизация и architecture-boundary tests поддерживают границу.
2. `src/domain/changes.ts` сравнивает отдельные поля и хранит inverse changes; обычный conflict flow не сводится к слепому overwrite полного snapshot.
3. `src/server/permissions.ts` независимо от UI проверяет роли/авторство; клиентские createdBy нельзя свободно подменить при обычной записи.
4. `src/server/yandex-oauth.ts` реализует state/PKCE, ограничение начала входа, одноразовый verifier и timeout провайдера; provider access token не выдаётся клиенту.
5. `src/server/auth.ts` хранит session hashes, использует random tokens и безопасные cookie-флаги для HTTPS; renewal не пишет в БД на каждый обычный запрос.
6. `src/server/schema.ts` использует STRICT, FK, CHECK/UNIQUE, WAL и транзакционные миграции; неизвестная будущая схема не модифицируется молча.
7. `src/server/restore.ts` отделяет preview от применения, ограничивает распаковку, проверяет пути/actor/revision и делает backup перед импортом.
8. `src/server/public-sharing-http.ts` ограничивает person IDs, проверяет expiry/revocation и повторяет проверку после async media; no-store/no-referrer/noindex заданы.
9. `src/components/tree/layout.worker.ts` и Worker-тест проверяют реальную собранную раскладку, а не только исходный алгоритм; main thread не считает ELK напрямую.
10. `src/server/media.ts` сохраняет потоково через временный UUID-файл и rename, ограничивает размер и очищает временный файл при ошибке.
11. `src/server/geocoding.ts` имеет deduplication, bounded queue, постоянный ограниченный cache и паузу при отказах внешнего провайдера.
12. `ops/` и workflow используют отдельные релизы, ограниченного пользователя, pinned Actions/SSH host key, согласованный SQLite backup перед сменой кода и минимальный runtime manifest.

Эти решения стоит сохранить при исправлении найденных дефектов. Критерий готовности следующего релиза — проверенное закрытие data-loss/privacy blockers и успешное восстановление поддерживаемого архива, а не рост оценки или количества тестов.
