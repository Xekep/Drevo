# Параллельная работа PostgreSQL

## Воспроизводимый прогон

`ops/postgres/benchmark-runtime.ts` создаёт синтетический архив в **новой пустой**
БД `drevo_migration_bench_*`. Имя, фактическая БД, отсутствие таблиц и роль без
superuser/BYPASSRLS проверяются до импорта. Рабочий архив и пользовательские файлы
не используются. Скрипт не создаёт и не удаляет PostgreSQL-базы; временная SQLite
для подготовки данных удаляется в `finally`.

Пример для уже созданной пустой БД, принадлежащей тестовой роли:

```sh
PGDATABASE=drevo_migration_bench_local PGUSER=drevo_runtime \
  node --experimental-strip-types ops/postgres/benchmark-runtime.ts 1000
```

Остальные параметры подключения задаются обычными переменными `PGHOST`, `PGPORT`,
`PGPASSWORD`. Пароли не передаются через аргументы команды и не печатаются.
Для повторения требуется новая пустая БД. Допустимы 1 000–10 000 человек.
CI создаёт отдельные PostgreSQL 18 базы для 1 000 и 10 000 человек и сохраняет
JSON-результат в журнале и сводке задания `postgres`.

`ops/postgres/benchmark-http.ts` использует ещё одну новую пустую БД с теми же
проверками имени и роли. Он запускает **два отдельных backend-процесса** с общими
PostgreSQL и каталогом медиа. Перед измерением загружает синтетическую фотографию
с несжимаемыми пикселями через HTTP и проверяет, что оба процесса отдают оригинал
и превью. Затем 45 секунд
смешивает полное чтение архива, проекцию дерева, поиск людей, список документов,
статус ИИ, выдачу оригинала и превью, две записи в ИИ-диалоги и последовательные
правки разных карточек через оба процесса. Перед измерением оба процесса одновременно
запрашивают холодное превью из общего каталога и декодируют полученный WebP.
Во время HTTP-нагрузки оба процесса одновременно запрашивают фоновую управляемую
копию: ровно один должен её создать, второй — получить отказ занятого lease,
не приписав себе чужую работу. Второй процесс подтверждает, что видит
единственную копию в общем каталоге. Отдельно выводятся длительность создания
и время до отказа второго процесса (по одному наблюдению за прогон, без
процентилей распределения). Ответы диалогов проверяются через
противоположный процесс. После прогона второй процесс должен увидеть последнюю правку. Измеряет
p50/p95/p99 и ошибки для каждого маршрута,
объём полученных данных, CPU и RSS каждого процесса. Сбой любого HTTP-запроса
завершает CI ошибкой. Пример для отдельно созданной пустой БД:

```sh
PGDATABASE=drevo_migration_bench_local PGUSER=drevo_runtime \
  node --experimental-strip-types ops/postgres/benchmark-http.ts 1000 45
```

Для отдельного более долгого прогона есть ручной workflow
`PostgreSQL mixed HTTP soak`: он создаёт новую тестовую БД на GitHub runner,
использует 10 000 синтетических людей и выполняет тот же HTTP-профиль пять
минут. Его результаты сохраняются в сводке запуска; workflow не запускается
при каждом коммите и не подключается к рабочей БД. Сравнивать такой прогон с
коротким CI-профилем нужно с учётом разного размера архива и нагрузки runner.
Перед смешанной нагрузкой скрипт также проходит обычный клиентский путь:
начальная проекция, затем все страницы деталей через оба backend-процесса.
Отдельно выводятся число запросов и время `initial_hydration` без отрисовки
браузером и сети пользователя.

Это **частичное** покрытие смешанной нагрузки. `ai_mock_turn` проходит полный
HTTP-путь ИИ-диалога и сохранение ответа, но использует внедрённый в backend
подставной Responses API с фиксированной задержкой 150 мс. Тестовые ключ,
модель и адрес подставляются независимо от окружения оператора; подставной
провайдер отклоняет любой неожиданный адрес и не обращается во внешнюю сеть.
Из фоновых заданий активируется только одно создание копии при двух попытках.
Межпроцессное исключение обеспечивается транзакцией PostgreSQL с блокировкой
строки архива до чтения lease. Профиль не моделирует несколько одновременных писателей,
внешний AI API и скорость модели, сеть пользователя,
ресурсы PostgreSQL, CDN и 10 000 одновременных сессий. Поэтому пункт полного
длительного профиля в дорожной карте остаётся открытым, а числа CI не являются
оценкой ёмкости production.

Первый прогон расширенного профиля в CI 2 октября 2026 года: 1 000 синтетических
людей, два backend-процесса, 12 параллельных HTTP-читателей и 45 секунд нагрузки.
Один фоновый backup завершился за 1056,1 мс, второй процесс получил отказ
занятого lease за 44,3 мс; каталог содержал ровно одну копию. Одновременно
выдано 3689 оригиналов (p95 42,8 мс) и 3689 превью (p95 36,2 мс), ошибок не
было. Времена backup и отказа — по одному наблюдению на общем CI runner,
поэтому они не задают предел производительности или задержки production.

Ручной [пятиминутный прогон](https://github.com/Xekep/Drevo/actions/runs/36994402500)
2 октября 2026 года на GitHub runner с PostgreSQL 18.6: 10 000 синтетических
людей, два backend-процесса, 12 параллельных читателей, 19 174 успешных
HTTP-чтения и 347 успешных правок без ошибок. p95 полного архива — 682,7 мс,
начальной проекции — 635,1 мс, поиска — 446,3 мс, правки — 649,3 мс.
Средний ответ полного архива составил около 7,12 МБ, проекции — 2,26 МБ;
за прогон эти два маршрута вернули соответственно 19,5 и 6,2 ГБ данных.
RSS backend-процессов **в конце** — 638 и 606 МБ, пользовательское CPU-время —
292 и 288 секунд. Два тестовых AI-ответа и одно фоновое резервирование прошли;
по 1–2 наблюдениям нельзя оценивать задержку этих операций. CPU/RAM самой БД,
пиковая память процессов, внешний AI, пользовательская сеть и реальные данные
не измерялись. Объём полного ответа уже делает массовое чтение всего архива
важным кандидатом на оптимизацию; эти цифры не определяют ёмкость production.

Измеряются полное чтение архива, начальная проекция древа и независимые правки
карточек при 1, 10 и 100 параллельных операциях. Два независимых экземпляра
хранилища используют два пула по 10 соединений. Отдельно измеряются десять
пакетных правок по 500 карточек с проверкой 500 связанных людей. Метрики:
p50/p95/p99, успешные операции в секунду, ошибки, CPU Node и пиковый RSS процесса.
CPU PostgreSQL и сеть браузера в эти показатели не входят. RSS — максимум за
время жизни процесса, а не отдельного сценария.

Задержки включают все попытки, в том числе неуспешные. Для стресс-сценария
100 одновременных чтений исчерпание 5-секундного ожидания соединения записывается
как `connection_queue_timeout` и `overloaded: true`: это измеренная граница, а
не успешная обработка всей нагрузки. После оптимизации снимков этот профиль
проходит без таймаутов; теперь **любая** ошибка, включая возврат перегрузки,
или нарушение целостности завершают прогон ошибкой. CI использует `pipefail`,
чтобы сохранение журнала через `tee` не скрывало неуспех скрипта.

После записи проверяются все значения и точное увеличение ревизии. Две правки
одного поля из разных пулов дают один успех и один конфликт; повтор применённой
правки не создаёт дополнительную ревизию. Уже существующие PostgreSQL-тесты
отдельно проверяют отзыв прав во время ожидания, изоляцию архивов и откат.

**Границы:** короткие закрытые серии после прогрева, без пользовательской сети,
HTTP, медиазагрузок и ИИ; граф состоит из пар родитель–ребёнок и биографий.
Это не число поддерживаемых пользователей и не проверка нескольких полноценных
backend-процессов. Метрики CI нельзя переносить на production-сервер. Для оценки
ёмкости нужны длительный смешанный HTTP-профиль, сеть, CPU/RAM БД и отдельная
проверка фоновых задач, лимитов и файлов между экземплярами.

## Исправленное узкое место

Обычные чтения списка, карточки, PDF и аннотаций документа для пользователя с
полным доступом больше не гидратируют весь семейный граф. Для имён на странице
сервер читает только связанные карточки. Поиск по ФИО и ограниченная область
доступа по-прежнему требуют проверки видимого графа. Регрессия HTTP проверяет
эти чтения и сохранение имён без полной загрузки архива.

`src/server/person-patches.ts` раньше читал каждую изменяемую или связанную карточку
отдельно. `Promise.all` не распараллеливал SQL: внутри транзакции запросы идут по
одному PostgreSQL-соединению. При правке 500 родителей и проверке 500 детей это
1 000 обращений к БД под блокировкой архива.

Теперь одна параметризованная выборка получает весь набор. Идентификаторы
передаются JSON-массивом, без растущего числа placeholders. PostgreSQL использует
[`jsonb_array_elements_text`](https://www.postgresql.org/docs/18/functions-json.html),
SQLite — `json_each`. Порядок карточек восстанавливается по исходному списку ID;
отсутствующая карточка по-прежнему даёт конфликт. Проверки прав, дат связанных
людей, истории, аудита и ревизии остаются в той же транзакции.

Регрессия `tests/person-patch-batch.test.ts` проверяет границу 500 правок,
количество чтений, неизменность связей, дату последнего неотредактированного
ребёнка, удалённую карточку и восстановление предыдущей ревизии.

Записи одного архива всё ещё последовательно берут блокировку строки `archives`:
это обеспечивает согласованность общего графа и ревизии. Убирать блокировку без
нового протокола конфликтов нельзя. Обновление нескольких сотен строк, аудит и
валидация также имеют стоимость; оптимизация чтения не делает их бесплатными.

## Повторное чтение согласованных снимков

`src/server/archive-read-cache.ts` объединяет одновременные чтения одной ревизии
и сохраняет последний снимок отдельно для полного архива, проекции с портретами
и проекции без портретов. Перед каждой выдачей выполняется короткий запрос
текущей ревизии в БД. Запись другим процессом видна при следующей проверке;
TTL и широковещательный сброс между процессами для корректности не требуются.
Чтение, уже начавшееся до чужого commit, может вернуть прежний согласованный
снимок со своим прежним номером ревизии.

Каждый экземпляр хранилища владеет своими тремя кешами. Сохраняется не более
16 МиБ сериализованных данных на вид (до 48 МиБ на экземпляр); больший снимок
разделяется только между ожидающими его запросами. Дополнительная память нужна
для загрузки и копий, выдаваемых запросам, поэтому это не лимит RSS приложения.
Снимок хранится JSON-строкой: гидратация архива возвращает JSON-данные из БД и
массивы связей. Размер строки считается с запасом по два байта на UTF-16 символ.
Каждый вызывающий получает отдельный объект через `JSON.parse`, без общих
изменяемых ссылок. Изменение возвращённого объекта не загрязняет кеш. Тест
сравнивает его с непосредственным чтением БД, а не только с предыдущей копией.
Копии выдаются с уступкой event loop через `setImmediate`: ожидающие один снимок
запросы не создают сразу все большие объекты в одной цепочке microtasks до того,
как первый потребитель сможет освободить свою копию. Это уменьшает временный
пик памяти при всплеске и позволяет обслуживать другие события между копиями.

Внутри существующей транзакции кеш обходится: редактор видит собственные
незавершённые изменения, а читающая транзакция — свой снимок `REPEATABLE READ`.
Откат не публикует незавершённые данные. Неудачная загрузка допускает повтор,
старый медленный ответ не вытесняет новый. История и изменения данных продолжают
читаться/записываться по прежним правилам конфликтов.

Кеш не содержит HTTP-ответы, сессии или пользовательские разрешения. Проекция
`common_ancestors` применяется после чтения по текущему пользователю. Из
`archive-query-http.ts` удалён отдельный кеш этой проекции: он мог присоединить
новый номер ревизии к ранее прочитанному графу. Номер теперь всегда берётся из
самого снимка. Проверка page token, подсчёты и чтение страницы выполняются в
одной read-only транзакции. Запись между запросами страниц даёт 409 и повторную
загрузку; запись во время уже начатой страницы не смешивает две версии.

`tests/archive-read-cache.test.ts` проверяет объединение чтений, независимость
объектов и видов, чужую запись, откат, старый запоздавший ответ, отказ БД и лимит
кеша. PostgreSQL runtime-тест дополнительно сохраняет данные через другой пул
между проверкой page token и выборкой карточек: текущая страница остаётся
согласованной, следующий запрос со старым токеном отклоняется.

Нагрузочный прогон дополнен холодным всплеском 100 чтений и 100 чтениями
параллельно десяти последовательным правкам. Каждая правка записывает в поле
контрольную метку своего номера ревизии; все ответы проверяются на совпадение
метки и версии снимка. Профиль повторных чтений измеряется после прогрева кеша.

[Предыдущий прогон без кеша](https://github.com/Xekep/Drevo/actions/runs/36487369809/job/109147868468)

различаются: это свидетельство устранения очереди повторных запросов, не точный
коэффициент ускорения для production. Полный смешанный HTTP-профиль остаётся
следующим этапом.
