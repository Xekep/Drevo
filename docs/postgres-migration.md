# Миграция серверного архива в PostgreSQL

Первый этап запущен 27 сентября 2026 года. На рабочем хосте установлен PostgreSQL 18 из репозитория Ubuntu. Он принимает соединения только через локальный Unix-сокет; для изолированной проверки создана база `drevo_migration` с ролью `site_drevo`. Приложение **продолжает работать на SQLite**. Ни одна запись рабочего архива пока не направляется в PostgreSQL.

## Проверенный перенос первой группы данных

`ops/postgres/import-sqlite.ts` принимает согласованную **копию** SQLite, каталог оригиналов `uploads/` и новый `archive_id`. Рабочий файл с именем `drevo.sqlite` он отклоняет. Скрипт проверяет `integrity_check`, точную версию схемы, локальные ссылки на оригиналы, затем одной транзакцией создаёт таблицы и переносит людей, связи, метаданные фото, отметки на снимках, документы с привязками, историю ревизий и сообщения обсуждений (если таблица уже есть в SQLite). Каждая таблица перечитывается из PostgreSQL и сравнивается с источником по всем перенесённым полям. Повторный импорт в непустую базу запрещён; ошибка откатывает транзакцию.

Для пробного импорта использована новая согласованная копия рабочей SQLite. Сверка прошла: 116 человек, 174 связи, 89 фотографий, 155 отметок, один документ с привязкой и 50 ревизий истории; 140 локальных оригиналов найдены. Тестовая база заняла около 10 МБ. Эти числа описывают **снимок на момент проверки**, а не постоянное состояние архива. Бинарные файлы не копировались в PostgreSQL и остаются на прежнем диске.

Пример запуска на изолированной установке, от имени пользователя приложения:

```sh
PGHOST=/var/run/postgresql PGUSER=site_drevo PGDATABASE=drevo_migration \
  node --experimental-strip-types ops/postgres/import-sqlite.ts \
  /path/to/consistent-copy.sqlite /path/to/uploads legacy-primary
```

Перед повторным опытом создавайте новую пустую тестовую базу, а не очищайте существующую автоматически. Исходную копию и исходные медиа храните отдельно до завершения сверки.

## Полная сверка актуального снимка

После обновления рабочего древа создан **новый согласованный снимок** SQLite с ревизией 818. Импортёр теперь сверяет полный перечень таблиц со схемой: неизвестная новая таблица или изменённый столбец семейной таблицы останавливают импорт. Все 27 служебных таблиц, включая пользователей, сессии, настройки, аудит, AI-диалоги, каталог исследований и данные распознавания лиц, сохраняются в `service_snapshot_tables` и `service_snapshot_rows` вместе с исходными именами столбцов и порядком строк. Каждая строка перечитывается и сравнивается в той же транзакции. Эти таблицы — **теневая копия для проверки полноты**, не работающие PostgreSQL-репозитории приложения. Они содержат чувствительные данные; доступ к отдельной тестовой базе ограничен локальным Unix-сокетом и ролью приложения.

Проверка на сервере прошла для 127 человек, 201 связи, 89 фотографий, 155 отметок, одного документа, 50 ревизий истории и 2765 строк служебных таблиц. Найден 141 локальный оригинал. Ревизия живой SQLite после переноса оставалась 818. Это состояние на момент снимка; при новых изменениях древа требуется **новая согласованная копия и новая пустая тестовая база**, а не использование старого PostgreSQL-снимка.

## Что ещё блокирует переключение

- Аккаунты, участники архива, права, сессии, настройки, аудит, публичные ссылки, AI/MCP-данные, фоновые задания и служебные кэши уже сохранены и сверены в теневой копии, но работающие операции над ними **по-прежнему только в SQLite**. Нельзя включать регистрацию или объявлять PostgreSQL основным хранилищем до введения `archive_id` на **каждом** маршруте чтения и записи.
- Для Node.js нужен асинхронный слой операций над конкретными сущностями и транзакциями. Текущий `DatabaseSync` и синхронные SQL-запросы нельзя механически заменить `pg`: каждая операция должна сохранять проверки прав, ревизий и конфликтов. Переписать только `database.ts` недостаточно.
- Хранилище фотографий и документов локально для одного экземпляра. Для нескольких серверов приложения понадобятся общее файловое хранилище, общий контроль квот/очередей и отдельные ограничения доступа к медиа.
- Действующие SQLite-бэкапы не являются бэкапами PostgreSQL. До переключения нужны base backup + архивирование WAL для PITR, резервирование оригиналов файлов, мониторинг, регулярная проба восстановления и согласованные RPO/RTO.
- Во время проверки доступный системе объём RAM вырос с 1,6 до 3,3 ГиБ. Перед рабочим переключением измерить пиковое потребление Node, PostgreSQL и обработки медиа, подтвердить конфигурацию хоста и запас памяти; текущий пробный перенос не является нагрузочным тестом.

Следующий этап: привязать текущих участников к явному владельцу и членству **одного** архива без изменения их прав; провести одинаковые сценарии чтения, записи, конфликтов, импорта и экспорта на SQLite и PostgreSQL. Только после тестов на копии выполнить финальный перенос в окно обслуживания с остановкой записи, повторной сверкой и планом отката. Отдельный личный кабинет и регистрацию открывать после серверной изоляции архивов.
