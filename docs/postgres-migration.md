# Миграция серверного архива в PostgreSQL

Первый этап запущен 27 сентября 2026 года. На рабочем хосте установлен PostgreSQL 18 из репозитория Ubuntu. Он принимает соединения только через локальный Unix-сокет; для изолированной проверки создана база `drevo_migration` с ролью `site_drevo`. Приложение **продолжает работать на SQLite**. Ни одна запись рабочего архива пока не направляется в PostgreSQL.

## Проверенный перенос первой группы данных

`ops/postgres/import-sqlite.ts` принимает согласованную **копию** SQLite, каталог оригиналов `uploads/` и новый `archive_id`. Рабочий файл с именем `drevo.sqlite` он отклоняет. Скрипт проверяет `integrity_check`, точную версию схемы, локальные ссылки на оригиналы, затем одной транзакцией создаёт таблицы и переносит людей, связи, метаданные фото, отметки на снимках, документы с привязками, историю ревизий и сообщения обсуждений (если таблица уже есть в SQLite). Каждая таблица перечитывается из PostgreSQL и сравнивается с источником по всем перенесённым полям. Повторный импорт в непустую базу запрещён; ошибка откатывает транзакцию.

Для пробного импорта использована новая согласованная копия рабочей SQLite. Сверка прошла: 116 человек, 174 связи, 89 фотографий, 155 отметок, один документ с привязкой и 50 ревизий истории; 140 локальных оригиналов найдены. Тестовая база заняла около 10 МБ. Эти числа описывают **снимок на момент проверки**, а не постоянное состояние архива. Бинарные файлы не копировались в PostgreSQL и остаются на прежнем диске.

Пример запуска на изолированной установке, от имени пользователя приложения:

```sh
PGHOST=/var/run/postgresql PGUSER=site_drevo PGDATABASE=drevo_migration \
  node --experimental-strip-types ops/postgres/import-sqlite.ts \
  /path/to/consistent-copy.sqlite /path/to/uploads legacy-primary
```

Перед повторным опытом создавайте новую пустую тестовую базу, а не очищайте существующую автоматически. Исходную копию и исходные медиа храните отдельно до завершения сверки.

## Полная сверка актуального снимка

После обновления рабочего древа создан **новый согласованный снимок** SQLite с ревизией 818. Импортёр теперь сверяет полный перечень таблиц со схемой: неизвестная новая таблица или изменённый столбец семейной таблицы останавливают импорт. Все 27 служебных таблиц, включая пользователей, сессии, настройки, аудит, AI-диалоги, каталог исследований и данные распознавания лиц, сохраняются в `service_snapshot_tables` и `service_snapshot_rows` вместе с исходными именами столбцов и порядком строк. Каждая строка перечитывается и сравнивается в той же транзакции. Эти таблицы — **теневая копия для проверки полноты**, не работающие PostgreSQL-репозитории приложения. Они содержат чувствительные данные; доступ к отдельной тестовой базе ограничен локальным Unix-сокетом и ролью приложения.

Проверка на сервере прошла для 127 человек, 201 связи, 89 фотографий, 155 отметок, одного документа, 50 ревизий истории и 2765 строк служебных таблиц. Найден 141 локальный оригинал. Ревизия живой SQLite после переноса оставалась 818. Это состояние на момент снимка; при новых изменениях древа требуется **новая согласованная копия и новая пустая тестовая база**, а не использование старого PostgreSQL-снимка.

Отдельная проверка `ops/postgres/verify-archive-read.ts` читает **именно семейный объект, используемый интерфейсом**, через общий код сборки графа. Для того же снимка результат PostgreSQL совпал с SQLite целиком: ревизия 818, 127 человек, 201 связь и 89 фотографий с отметками. Чтение происходит в PostgreSQL-транзакции `REPEATABLE READ READ ONLY`; рабочий HTTP-сервер по-прежнему читает SQLite.

## Аккаунты и права в типизированной схеме

На новом снимке ревизии **819** одной транзакцией перенесены семейные данные и полная теневая копия, затем созданы PostgreSQL-таблицы `accounts`, `archive_memberships`, `archive_owners`, `account_sessions`, `archive_access_settings` и `archive_tree_settings`. Проверены 7 аккаунтов, 7 членств, 14 сессий, настройки доступа и древа; исходные роли, допуск, привязка к человеку и режим видимости сверены построчно. Один действующий администратор текущего архива стал его владельцем. Если действующих администраторов несколько, импорт требует явно передать `owner_user_id` четвёртым аргументом CLI; он должен быть одним из них. Полное дерево снимка: 127 человек, 201 связь, 89 фото, 141 локальный файл. Живая SQLite при проверке не менялась.

Это **подготовленная схема**, не переключение аутентификации: вход, сессии и API участников по-прежнему обслуживает SQLite. Нельзя использовать перенесённые хэши сессий в приложении до проверки всех путей авторизации и отзыва доступа на PostgreSQL. После очередных правок архива нужен новый согласованный снимок и новая пустая тестовая база.

```sh
PGHOST=/var/run/postgresql PGUSER=site_drevo PGDATABASE=drevo_migration_YYYYMMDD_HHMMSS \
  node --experimental-strip-types ops/postgres/verify-archive-read.ts \
  /path/to/consistent-copy.sqlite legacy-primary
```

## Что ещё блокирует переключение

- Аккаунты, членство, права, сессии, базовые настройки и аудит уже имеют типизированные PostgreSQL-таблицы. Публичные ссылки, AI/MCP-данные, фоновые задания и служебные кэши пока только в теневой копии. Работающие операции над всем этим **по-прежнему только в SQLite**. Нельзя включать регистрацию или объявлять PostgreSQL основным хранилищем до введения `archive_id` на **каждом** маршруте чтения и записи.
- Для Node.js нужен асинхронный слой операций над конкретными сущностями и транзакциями. Текущий `DatabaseSync` и синхронные SQL-запросы нельзя механически заменить `pg`: каждая операция должна сохранять проверки прав, ревизий и конфликтов. Переписать только `database.ts` недостаточно.
- Хранилище фотографий и документов локально для одного экземпляра. Для нескольких серверов приложения понадобятся общее файловое хранилище, общий контроль квот/очередей и отдельные ограничения доступа к медиа.
- Действующие SQLite-бэкапы не являются бэкапами PostgreSQL. До переключения нужны base backup + архивирование WAL для PITR, резервирование оригиналов файлов, мониторинг, регулярная проба восстановления и согласованные RPO/RTO.
- Во время проверки доступный системе объём RAM вырос с 1,6 до 3,3 ГиБ. Перед рабочим переключением измерить пиковое потребление Node, PostgreSQL и обработки медиа, подтвердить конфигурацию хоста и запас памяти; текущий пробный перенос не является нагрузочным тестом.

Права участников теперь читаются из PostgreSQL через `postgresAccessReader`: каждый запрос к учётной записи или сессии требует `archive_id` и членства в этом архиве. `ops/postgres/verify-access-read.ts` сравнивает участников, действующие и просроченные сессии и настройки видимости с согласованной копией SQLite. На изолированной базе сверены 7 участников и 14 сессий. Проверка дополнительно создаёт внутри откатываемой транзакции второй архив с совпадающим ID человека, отдельным участником, сессией и настройками: оба архива видят только свои данные. Одна существующая учётная запись получает в двух архивах разные роли и допуск; общая сессия должна вернуть права именно выбранного архива. Скрипт отказывается работать вне базы `drevo_migration*`; после проверки второй архив откатывается. Этот слой пока не подключён к HTTP-серверу и не является переключением аутентификации.

`postgresSessionArchives` получает доступные деревья по действительному хэшу сессии, а не по переданному клиентом ID аккаунта. Каждая строка содержит права именно этого членства; явный выбор отсутствующего или неодобренного дерева возвращает отказ и не подменяется другим деревом. Без явного выбора берётся первое одобренное дерево, собственное имеет приоритет. На изолированном снимке проверены общий аккаунт с двумя разными ролями, недопущенное членство и просроченная сессия. Это подготовка для будущего переключателя архивов, а не новый публичный маршрут.

Жизненный цикл PostgreSQL-сессии также подготовлен отдельно: создание и ротация старого токена участвуют в транзакции вызывающего кода, в таблицу попадает только SHA-256, продление требует действующей сессии, отзыв удаляет её, визит обновляется не чаще раза в минуту по самой сессии. Общий формат токена используется и действующим SQLite-входом. На тестовой БД проверены ротация, продление ровно через сутки, отказ после истечения срока, отзыв и отсутствие открытого токена в таблице. OAuth callback теперь дожидается завершения операции выдачи сессии и возвращает ошибку, если она не удалась; его фактическое хранилище и HTTP-куки по-прежнему работают через SQLite до сквозного переключения.

В схему нового импорта добавлена глобальная таблица `oauth_transactions`: OAuth state возникает до определения аккаунта и архива. PostgreSQL-адаптер создаёт запись с хэшем state и PKCE verifier, а callback забирает её атомарным `DELETE ... RETURNING`, исключая повторное использование. Действующий SQLite-адаптер использует тот же контракт; сквозной тест проверяет оба варианта подключения и одноразовость. На изолированной PostgreSQL-базе проверены создание, истечение срока, очистка и повторный вызов с откатом. При будущем переключении начатый до окна обслуживания вход придётся начать заново; переносить незавершённые OAuth-транзакции из теневой копии в рабочую таблицу не нужно. Рабочий callback сейчас остаётся на SQLite.

Импорт теперь создаёт `account_identities` и связывает старые ID пользователей с субъектами Yandex. Новые аккаунты получают собственный непрозрачный UUID: ID провайдера больше не служит ID аккаунта. `completePostgresYandexLoginInTransaction` в одной транзакции разрешает личность, создаёт приватный архив при первом входе и ротирует сессию; повторный callback не создаёт второе дерево. Существующий одобренный участник остаётся в доступном ему архиве без автоматического создания пустого личного дерева; старые роли сохраняются. Проверка `ops/postgres/verify-yandex-login.ts` выполняется только на изолированной migration-базе и откатывает все изменения. Отдельная проверка `verify-yandex-concurrency.ts` на удалённой после опыта временной БД запустила два одновременных callback: второй дождался коммита первого, получился один аккаунт и один собственный архив. Этот координатор ещё не подключён к рабочему HTTP-входу и не открывает регистрацию.

Схема `account_tiers` отделяет уровень аккаунта от роли в архиве: перенесённые участники получают `full_access=true`, новый аккаунт — `false`. Это только сохранение исходной политики для будущей регистрации. Лимиты 150 человек и 500 000 000 байт, запрет ИИ и проверка квот при параллельных операциях пока не подключены к HTTP; до их реализации базовый уровень нельзя считать действующим.

Для будущей регистрации `provisionPrivateArchiveInTransaction` создаёт пустой архив, утверждённое членство владельца и закрытые настройки в транзакции вызывающего кода. Повторный callback возвращает уже созданный собственный архив; блокировка владельца и уникальность `archive_owners.user_id` не допускают два собственных дерева при конкуренции. Проверка изоляции использует этот же код и удостоверяется, что новое дерево пустое и непубличное. Создание аккаунта, подтверждение email, квоты и HTTP-переключение ещё не реализованы; вызывать функцию следует только после подтверждённой идентификации аккаунта. Уникальное ограничение входит в схему нового импорта; существующую тестовую БД нужно пересоздать из свежего снимка перед будущим переключением.

На изолированном снимке ревизии 818 проверка с новой операцией прошла дважды подряд: каждый раз 7 исходных участников и 14 сессий; временный архив, владелец и индекс уникальности откатились вместе с транзакцией. Отдельная проверка двух **одновременных** регистрационных HTTP-запросов потребуется после подключения операции к реальному входу.

Полный повторный импорт того же снимка в новую временную базу также прошёл: 127 людей, 201 связь, 89 фото, 7 аккаунтов; индекс `archive_owners_one_tree_per_user` реально создан. Проверка второго дерева на этой базе прошла, после чего временная база удалена. Это репетиция схемы, не перенос изменившихся с момента снимка рабочих данных.

```sh
PGHOST=/var/run/postgresql PGUSER=site_drevo PGDATABASE=drevo_migration_YYYYMMDD_HHMMSS \
  node --experimental-strip-types ops/postgres/verify-access-read.ts \
  /path/to/consistent-copy.sqlite legacy-primary
```

Аудит также перенесён в отдельные таблицы `archive_audit_entries` и `archive_audit_people`. Их исторические ID и ссылки на удалённых людей или участников сохраняются. Полный импорт снимка ревизии 819 в новую пустую базу одной транзакцией сверил 695 записей аудита и 1170 привязок; затем `ops/postgres/verify-audit-read.ts` сравнил с SQLite 164 страницы выдачи, включая фильтры по 2 авторам и 125 людям. Чтение аудита из PostgreSQL пока не подключено к HTTP.

```sh
PGHOST=/var/run/postgresql PGUSER=site_drevo PGDATABASE=drevo_migration_YYYYMMDD_HHMMSS \
  node --experimental-strip-types ops/postgres/verify-audit-read.ts \
  /path/to/consistent-copy.sqlite legacy-primary
```

Следующий этап: провести одинаковые сценарии записи, конфликтов, импорта и экспорта на SQLite и PostgreSQL; затем перевести HTTP-авторизацию и все операции доступа на асинхронный слой с обязательным `archive_id`. Только после тестов на копии выполнить финальный перенос в окно обслуживания с остановкой записи, повторной сверкой и планом отката. Отдельный личный кабинет и регистрацию открывать после серверной изоляции архивов.

## Репетиция записи семейного графа

`ops/postgres/verify-archive-write.ts` использует согласованную **копию** SQLite и уже импортированную из неё изолированную PostgreSQL-базу; имя базы должно начинаться с `drevo_migration`. Сначала сверяет исходный граф, затем применяет к обоим хранилищам одинаковые изменения: порядок людей и фотографий, название архива, добавление и удаление человека, дополнительную связь, подпись фото и отметку человека на снимке. Создаёт документ и комментарий для нового человека и проверяет одинаковое каскадное удаление привязки и комментария при сохранении самого документа. Третий шаг импортирует человека из GEDCOM и сравнивает результат экспорта. После каждого шага сравнивает семейный объект целиком; отдельно проверяет устаревшую ревизию, чужой `archive_id` и блокировку конкурентной записи вторым соединением. Все изменения PostgreSQL находятся в одной транзакции, которая в конце всегда откатывается. Скрипт не подключён к HTTP и не является способом редактировать рабочий архив.

На изолированной базе `drevo_migration_20260927_143340` и соответствующей копии SQLite ревизии 818 проверены три последовательные записи для 127 людей и 89 фото, документ и комментарий, а также блокировка второго писателя. После отката повторное чтение подтвердило исходную ревизию 818 и совпадение семейного графа. Запуск от имени роли приложения:

```sh
PGHOST=/var/run/postgresql PGUSER=site_drevo PGDATABASE=drevo_migration_20260927_143340 \
  node --experimental-strip-types ops/postgres/verify-archive-write.ts \
  /path/to/consistent-copy.sqlite legacy-primary
```

Это проверяет сериализацию, конкурентную ревизию и целостность связанных строк, но **не завершает миграцию**. Проверка GEDCOM касается доменного импорта и экспорта, не HTTP-предпросмотра, резервной копии перед импортом и прав администратора. Репетиционный writer также не содержит аудита, разрешения ссылок на медиа и бинарного хранилища. Ещё нужны сквозные HTTP-проверки прав и параллельных запросов, затем перенос остальных служебных операций на архивно-изолированные репозитории. До этого рабочая SQLite остаётся единственным источником изменений.

## Сохранение полей карточек по сессии

28 сентября 2026 года добавлена `patchPostgresPeopleForSession` в `src/server/postgres-person-patches.ts`. Операция принимает сессию, конкретный архив, исходную ревизию и изменения полей с предыдущими значениями. Доступ проверяется до блокировки архива и повторно после ожидания; до конца транзакции удерживаются блокировки сессии и членства. Подтверждённый администратор редактирует карточки выбранного архива, родственник — только собственные, читатель не может записывать. Для `common_ancestors` применяется общая проверка видимости и прав.

Независимые поля объединяются даже при устаревшей общей ревизии; изменение уже обновлённого поля возвращает конфликт. Повтор запроса с уже сохранёнными значениями не создаёт новую ревизию или аудит. Сведения людей, обратные изменения для истории, аудит и ревизия сохраняются одной транзакцией. При ошибке откатывается всё. Для обычного доступа читаются только изменяемые люди и соседи по связям, обновляются только изменённые строки. Ограниченный доступ пока требует полного графа для общей авторизации.

Порядок блокировок: строка архива → сессия → членство. `READ COMMITTED` позволяет перечитать данные и права после ожидания; `lock_timeout=5s` и `statement_timeout=15s` ограничивают ожидание запросов. Записи внутри одного архива сериализуются по его ревизии, разные архивы независимы. Все будущие операции записи графа и добавления аудита должны брать тот же замок архива. Это сохраняет текущую модель ревизий, но не является обещанием неограниченного параллелизма. Основание: [PostgreSQL 18 — Row-Level Locks](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS).

На отдельной временной базе PostgreSQL 18 прошли **14 интеграционных проверок**: соответствие SQLite по сохранённому графу и аудиту, повтор запроса, права/видимость, неизвестные поля и невалидные даты, атомарность пакета, два одновременных редактора, отзыв членства/сессии и истечение сессии во время ожидания, независимость двух архивов с одинаковыми ID людей, сбой аудита, отмена своей правки и хранение последних 50 ревизий. База содержала только синтетические данные и удалена после проверки. Эти сценарии запускаются в отдельной задаче `postgres` в CI, без подмены SQL заглушками.

Для повторения на отдельной тестовой установке создайте пустую базу с именем `drevo_migration_person_patches` и задайте обычные `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`, затем `npm run test:postgres`. Тест отказывается работать с другим именем базы, создаёт для каждого сценария отдельную схему и удаляет её после проверки. Не передавайте реквизиты рабочего хранилища.

**Граница этапа:** операция ещё не подключена к HTTP. Портреты, создание/удаление людей, родственные связи, медиа и квоты в неё не входят и отклоняются; их нельзя незаметно отправить через универсальный patch. Рабочее приложение продолжает сохранять изменения в SQLite. Следующий шаг — такие же архивно-изолированные операции для связей и создания людей, затем медиа/квоты и сквозное подключение HTTP.

## Репетиция восстановления PostgreSQL

`ops/postgres/verify-restore.sh` принимает **только** базу с именем `drevo_migration*`, создаёт логический `pg_dump -Fc`, восстанавливает его в новую временную базу и сравнивает список таблиц, число строк и хеш содержимого каждой строки каждой таблицы. Временная база и дамп удаляются после проверки. На сервере восстановление базы ревизии 818 прошло: 17 таблиц, 3448 строк; временная база удалена. Запускать от роли PostgreSQL, способной создавать временную базу:

```sh
PGHOST=/var/run/postgresql PGUSER=postgres \
  bash ops/postgres/verify-restore.sh drevo_migration_20260927_143340
```

Это проверка **логического** восстановления тестовой базы. Она сама по себе не является расписанием бэкапов и не защищает от потери всего сервера. Локальное резервирование PostgreSQL и оригиналов медиа настроено отдельно, ниже.

## Локальный этап резервирования PostgreSQL

После этой репетиции на сервере настроен **локальный** pgBackRest 2.58.0 для кластера PostgreSQL 18/main. Архивирование WAL включено; полная копия создаётся по воскресеньям, дифференциальная — в остальные дни в 03:40 UTC. Хранятся две цепочки полных копий с необходимыми WAL; устаревшие цепочки удаляет сам pgBackRest. Ежечасная проверка сообщает в systemd journal об ошибке архивирования, отсутствии свежей копии (старше 36 часов) или остатке менее 8 ГиБ на диске. Настройка зафиксирована в `ops/postgres/local-backup.conf.example`, `ops/postgres/local-backup.sh` и соответствующих systemd units. `ops/postgres/setup-local-backup.sh --apply` предназначен **только для начальной установки на пустой конфигурации pgBackRest** и перезапускает кластер; повторно на работающем production-кластере его не запускать.

На тестовом кластере выполнены две полные копии, `pgbackrest check` и запуск ежедневного и контрольного systemd-сервисов. `ops/postgres/verify-physical-restore.sh` разворачивает последнюю копию в отдельный временный каталог, запускает вторую копию PostgreSQL на приватном Unix-сокете, ждёт завершения recovery, проверяет наличие миграционных баз и удаляет временный экземпляр. Репетиция прошла; рабочий кластер не останавливался. Предыдущая логическая проверка `verify-restore.sh` сверила 17 таблиц и 3448 строк тестовой БД.

Оригиналы фото и PDF из `shared/uploads` копируются отдельным сервисом `drevo-media-backup.service` ежедневно в 04:20 UTC. `ops/postgres/local-media-backup.sh` проверяет запас 8 ГиБ и место для архива, создаёт tar.gz и SHA-256, проверяет читаемость архива и только после успеха оставляет три последние копии. Ежечасный `drevo-media-backup-health.timer` сообщает в journal об отсутствии свежей копии или нехватке места. На сервере создана и распакована тестовая копия: 143 файла совпали с исходными. `ops/postgres/setup-local-media-backup.sh --apply` устанавливает только эти сервисы/таймеры и не перезапускает PostgreSQL. Копия медиа и pgBackRest пока **не образуют атомарный снимок**: при изменении файлов между запусками согласованность связей нужно проверять отдельно. До переключения хранить текущий SQLite-архив как источник истины.

Проверка локального состояния:

```sh
sudo -u postgres pgbackrest --stanza=drevo check
sudo -u postgres pgbackrest --stanza=drevo info
systemctl status drevo-pgbackrest-backup.timer drevo-pgbackrest-health.timer
systemctl status drevo-media-backup.timer drevo-media-backup-health.timer
journalctl -u drevo-pgbackrest-backup.service -u drevo-pgbackrest-health.service --since today
journalctl -u drevo-media-backup.service --since today
journalctl -u drevo-media-backup-health.service --since today
sudo -u postgres bash ops/postgres/verify-physical-restore.sh
sudo -u site_drevo bash ops/postgres/verify-local-media-backup.sh
```

Репозитории PostgreSQL и медиа находятся **на том же системном диске**, что и рабочие данные. Это даёт локальный PITR PostgreSQL в пределах сохранённых WAL и локальные копии файлов, но не защищает от потери диска/сервера или компрометации хоста. Уведомления вне сервера пока нет: ошибки видны только в journal. Перед production-переключением нужны вынесенная копия pgBackRest и медиа, проверка восстановления из неё, внешнее оповещение, согласование снимка БД и файлов и измерение роста WAL/диска под реальной нагрузкой. Продолжительность восстановления production-архива не измерена.

Основание для настройки и предостережения о заполнении `pg_wal` при ошибке архивирования: [PostgreSQL 18 — Continuous Archiving](https://www.postgresql.org/docs/18/continuous-archiving.html) и [pgBackRest User Guide](https://pgbackrest.org/user-guide.html).

## Чтение архива по сессии

`src/server/postgres-authorized-archive-read.ts` добавляет серверную границу для будущего PostgreSQL HTTP-контура. Вызывающий передаёт токен сессии и выбранный `archive_id`; одна `REPEATABLE READ READ ONLY` транзакция проверяет действующую сессию, подтверждённое членство именно в этом архиве и читает его данные. Для роли с доступом `common_ancestors` применяется существующая проекция видимой семьи. Неверный токен, чужой архив и неподтверждённое членство возвращают `null` до чтения данных архива. Токен хешируется перед запросом к базе.

Через ту же границу читаются журнал изменений, список участников и настройки доступа. Эти данные выдаются владельцу или подтверждённому администратору выбранного архива; обычное членство в нём не даёт административного доступа. Статус администратора платформы сам по себе не даёт доступ к чужому приватному архиву.

Этот модуль пока не подключён к production HTTP: он не завершает перенос архива, медиа, истории и остальных маршрутов с SQLite. Регистрация новых пользователей остаётся закрытой до сквозной изоляции.
