# Резервные копии и восстановление

SQLite-копия также включает события людей, отдельный журнал правок и каталог временных ссылок. Импорт семейных данных из бэкапа через админку сохраняет текущие аккаунты, журнал и выданные ссылки, а само восстановление фиксируется в аудите. Обмен GEDCOM описан отдельно: [перенос между программами](gedcom.md).

## Разделы админки

**Экспорт и импорт** — JSON для анализа, GEDCOM для других генеалогических программ и импорт данных. **Резервные копии** — восстановление, расписание и хранение полных копий.

По умолчанию автоматические копии включены: каждые 24 часа, последние 30 копий на сервере архива. Период задаётся в часах (1–720), количество — 1–365. Следующий запуск показан в местном времени браузера. Расписание отсчитывается от начала последнего запуска; изменение периода или включение автоматического копирования назначает следующий запуск через выбранный интервал. После ошибки повторная попытка — через час. Выключатель отключает расписание, но оставляет ручное создание.

Кнопка **Создать копию** работает в фоне: раздел можно закрыть. В список попадают только завершённые копии с контрольной суммой SHA-256. Проверка SQLite и упаковка выполняются в отдельных процессах. Сроки и блокировка параллельных операций сохраняются в SQLite; после аварийного завершения блокировка истекает через 90 секунд. Старые завершённые копии удаляются только после успешной новой копии и только в том же хранилище. Копии перед деплоем и восстановлением в эту ротацию не входят. Уменьшение количества вступает в силу после следующей успешной копии. При смене хранилища старые копии остаются доступны; для удалённых нужно сохранить прежнее SSH-подключение.

Полная копия содержит SQLite, фотографии, документы из `uploads/` и ключ шифрования настроек, если он существует. Архивы содержат персональные данные и секреты; скачивать их может только одобренный администратор. Нельзя оценивать сохранность только по статусу задания: периодически проверяйте восстановление на отдельной тестовой установке.

## Отдельная SQLite-копия

Администратор может скачать SQLite через `GET /api/backup`. Локально вход не требуется. Сервер выполняет `VACUUM INTO`, поэтому скачанный файл `.sqlite` включает подтверждённые изменения из WAL и пригоден для самостоятельного открытия. Копирование только рабочего файла SQLite во время записи не даёт такой гарантии.

В бэкапе есть люди, связи, источники, метаданные снимков, отметки, пользователи, роли, настройки доступа и история последних 50 версий. **Бинарные файлы фотографий в SQLite не хранятся.** Для них используйте полный бэкап.

## Где лежат данные

| Среда     | База                                          | Фотографии                                |
| --------- | --------------------------------------------- | ----------------------------------------- |
| Компьютер | `data/drevo.sqlite`                           | `data/uploads/`                           |
| Сервер    | `/var/www/drevo.kiiko.ru/shared/drevo.sqlite` | `/var/www/drevo.kiiko.ru/shared/uploads/` |

Перед каждым деплоем создаётся дополнительный согласованный SQLite-бэкап в `shared/backups/<релиз>.sqlite`. Полные копии создаёт общий менеджер приложения и `ops/backup.sh`; расписание и количество берутся из админки. Старые локальные `full-*.tar.gz` с checksum автоматически подхватываются в список. `BACKUP_REMOTE` больше не используется. Копия на том же сервере не защищает от потери сервера.

Управляемый бэкап включает `drevo.sqlite.secrets.key`, если он существует: этот 32-байтовый ключ нужен для расшифровки настроек AI Studio после потери сервера. Копии доступны только владельцу. Перед созданием проверяется свободное место; параллельные задания блокируются общей SQLite-арендой с продлением. Незавершённый файл не считается готовой копией. Скрытые временные файлы незавершённых загрузок из `uploads/` исключаются. Конфигурацию OAuth `/etc/drevo.env`, SSH-ключи и конфигурацию веб-сервера резервируют отдельно.

## Полный бэкап

В разделе **Резервные копии** создайте и скачайте `.tar.gz` с согласованной копией `drevo.sqlite` и каталогом `uploads/`, без остановки сайта. Требуется системная команда `tar`. Секреты OAuth из `/etc/drevo.env` в этот архив не входят — сохраните их отдельно. В архив попадут и оставленные для восстановления файлы удалённых снимков. Прежний `GET /api/backup/full` оставлен для совместимости и не включает ключ шифрования; управляемые копии в новом разделе включают его.

Самый простой вариант: остановить процесс и скопировать весь каталог `data` на компьютере либо `shared` на сервере, затем снова запустить процесс. Так база, WAL при его наличии и снимки сохраняются вместе. Для сервера команды остановки и запуска: `sudo systemctl stop drevo` и `sudo systemctl start drevo`.

Экспорт JSON удобен для обмена и ручного редактирования. Он содержит текущий архив, но не историю SQLite, настройки входа и файлы фотографий. Импорт JSON доступен в «Экспорт и импорт → Импорт» и полностью заменяет текущие данные после явного нажатия кнопки подтверждения.

## Импорт через админку

Откройте **Админка → Резервные копии**, нажмите **Восстановить** у нужной копии. Сервер проверит размер, SHA-256, SQLite и содержимое архива. После проверки сравните количество людей, фотографий и документов, поставьте подтверждение и нажмите **Восстановить архив**. Отдельно доступна загрузка `.sqlite` или `.tar.gz` с компьютера. Проверка не изменяет действующее древо. Если после проверки кто-то изменил архив, потребуется повторная проверка: устаревший снимок не применяется автоматически.

Импорт заменяет текущих людей, связи, источники, координаты, фотографии, отметки и документы. **Аккаунты, роли, настройки доступа, AI и резервирования остаются действующими.** Старую историю изменений из импортируемой базы интерфейс не переносит. Для полного восстановления всей SQLite, включая пользователей, используйте ручной сценарий ниже.

Перед применением создаётся `shared/backups/before-import-<время>-<uuid>.sqlite`. Новые файлы фотографий получают новые имена, ссылки в импортируемом древе меняются вместе с данными. Прежние файлы не перезаписываются и не удаляются. Для возврата к состоянию до импорта пригодны созданная резервная база и сохранённые прежние фотографии. Импорт одной SQLite сообщает о недостающих файлах — бинарные фотографии следует восстанавливать из полного архива.

Ограничения: загружаемый и распакованный архив до 12 ГиБ, SQLite до 512 МиБ, отдельное фото до 20 МиБ. Допускаются `drevo.sqlite` и `uploads/`; ссылки, пути вне архива, повреждённые базы и неожиданные файлы отклоняются. Проверенный файл хранится временно до 15 минут и привязан к администратору. Лимит рассчитан на действующую квоту медиа 10 ГиБ. Ограничение Nginx для `/api/restore/preview` задано отдельно в `ops/nginx.conf`.

Импорт принимает также необязательный `drevo.sqlite.secrets.key` ровно 32 байта, но не применяет его: действующие настройки и ключ сохраняются. Для полного восстановления сервера ключ возвращают вручную вместе с базой.

## Автоматический off-host backup

Приложение проверяет расписание каждые 30 секунд. Дополнительный systemd timer проверяет то же расписание раз в пять минут и позволяет создавать копии, когда процесс сайта остановлен: установите актуальные `ops/drevo-backup.service` и `ops/drevo-backup.timer` в `/etc/systemd/system/`, выполните `systemctl daemon-reload && systemctl enable --now drevo-backup.timer`. Старые установленные units нужно обновить вручную при переходе на этот релиз. Два планировщика используют одну блокировку и не создают дубли. `bash ops/backup.sh` проверяет срок; `bash ops/backup.sh --now` запускает копию немедленно.

Для отдельного сервера один раз создайте SSH-профиль, доступный сервисному пользователю, в `shared/backup-ssh/config` (каталог 700, config и приватный ключ 600). Файл и ключи находятся вне релизов и сохраняются при деплое. Пример:

```sshconfig
Host backup-vault
  HostName backup.example.org
  Port 22
  User drevo-backup
  IdentityFile /var/www/drevo.kiiko.ru/shared/backup-ssh/id_ed25519
  IdentitiesOnly yes
  UserKnownHostsFile /var/www/drevo.kiiko.ru/shared/backup-ssh/known_hosts
  StrictHostKeyChecking yes
```

На удалённом сервере нужны OpenSSH с SFTP, Python 3.8+ и отдельный пользователь с правами на каталог копий. Закрепите публичный ключ сервера в `known_hosts` после независимой проверки fingerprint; не отключайте проверку. Публичный ключ клиента добавьте в `authorized_keys` удалённого пользователя. В админке выберите **Отдельный сервер по SSH**, введите `backup-vault` и `/srv/backups/drevo`, нажмите **Проверить подключение**, затем сохраните. Пароли/приватные ключи браузер не принимает. Для другого порта измените SSH-профиль. При ошибке SSH проверьте профиль от имени пользователя сервиса; подробности SSH намеренно не выдаются браузеру.

Удалённая копия сначала передаётся как `.partial`, сервер пересчитывает SHA-256 и только затем атомарно переименовывает файл. После успешной записи удаляются лишние копии из каталога этого архива. Ротация не удаляет посторонние файлы и каталоги. Если отдельный сервер недоступен, предыдущие копии сохраняются, в админке появляется ошибка, затем повтор через час. Локальное место нужно и при удалённом хранении — для упаковки и временного скачивания на восстановление.

Не реже одного раза в квартал разверните последнюю удалённую копию в изолированном каталоге, проверьте `sha256sum -c`, `PRAGMA integrity_check`, запуск приложения и открытие нескольких оригиналов фотографий. RPO зависит от выбранного периода и успешности запусков; RTO подтверждается только практическим восстановлением.

### Копия на компьютере владельца

На 25 сентября 2026 года серверный таймер включён. Дополнительно на Windows настроена задача `DrevoOffsiteBackup`: ежедневно в 07:00 и при входе пользователя она запускает копию `ops/pull-backup.ps1` из `C:\Users\Xekep\Desktop\web\pull-drevo-backup.ps1`. Архивы сохраняются в `C:\Users\Xekep\Desktop\web\backups`; SSH использует существующий `ssh_config` с закреплённым ключом сервера. Перед завершением скачивания проверяется SHA-256, локально сохраняются копии за 30 дней и `last-success.json`.

Задача работает в сеансе владельца при доступной сети; выключенный компьютер увеличивает фактический RPO. Это дополнительная копия **локальных** серверных бэкапов. Если в админке выбран отдельный сервер, новые архивы туда отправляются напрямую; Windows-задача не скачивает их с нового хранилища автоматически. Следите за возрастом `last-success.json` и `LastTaskResult`. После изменения скрипта в репозитории обновляйте установленную копию.

## Ручное восстановление SQLite

1. Остановите процесс приложения.
2. Сохраните существующий каталог данных под другим именем, включая `drevo.sqlite-wal` и `drevo.sqlite-shm`, если они есть. Не оставляйте старые WAL/SHM рядом с восстановленной базой.
3. Поместите скачанный бэкап в каталог данных под именем `drevo.sqlite`.
4. Восстановите соответствующий `uploads/` и `drevo.sqlite.secrets.key` из той же системной копии. Имена файлов должны остаться прежними. Ключ храните с правами `600` и владельцем сервиса.
5. На сервере проверьте владельца `site_drevo:site_drevo_grp` и разрешение записи в `shared` для этого пользователя.
6. Запустите приложение, проверьте карточки и несколько фотографий.

Смена кода при неудачном деплое не откатывает пользовательские данные автоматически. Если будущая миграция схемы окажется несовместимой, остановите приложение и восстановите согласованный бэкап вручную, чтобы не потерять изменения, поступившие после деплоя.
