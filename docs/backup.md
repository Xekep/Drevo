# Резервные копии и восстановление

SQLite-копия также включает события людей, отдельный журнал правок и каталог временных ссылок. Импорт семейных данных из бэкапа через админку сохраняет текущие аккаунты, журнал и выданные ссылки, а само восстановление фиксируется в аудите. Обмен GEDCOM описан отдельно: [перенос между программами](gedcom.md).

## Кнопка «Бэкап базы»

Администратор может скачать SQLite в **«Управлении архивом»**. Локально вход не требуется. Сервер выполняет `VACUUM INTO`, поэтому скачанный файл `.sqlite` включает подтверждённые изменения из WAL и пригоден для самостоятельного открытия. Копирование только рабочего файла SQLite во время записи не даёт такой гарантии.

В бэкапе есть люди, связи, источники, метаданные снимков, отметки, пользователи, роли, настройки доступа и история последних 50 версий. **Бинарные файлы фотографий в SQLite не хранятся.** Для них используйте полный бэкап.

## Где лежат данные

| Среда     | База                                          | Фотографии                                |
| --------- | --------------------------------------------- | ----------------------------------------- |
| Компьютер | `data/drevo.sqlite`                           | `data/uploads/`                           |
| Сервер    | `/var/www/drevo.kiiko.ru/shared/drevo.sqlite` | `/var/www/drevo.kiiko.ru/shared/uploads/` |

Перед каждым деплоем создаётся дополнительный согласованный бэкап в `shared/backups/<релиз>.sqlite`. Бэкапы и старые релизы не удаляются автоматически; периодически контролируйте место. Для надёжного хранения копируйте резервные данные с сервера на другой носитель.

## Полный бэкап

В «Управлении архивом» скачайте **базу и фотографии**: сервер создаст `.tar.gz` с согласованной копией `drevo.sqlite` и каталогом `uploads/`, без остановки сайта. Требуется системная команда `tar`. Секреты OAuth из `/etc/drevo.env` в этот архив не входят — сохраните их отдельно. В архив попадут и оставленные для восстановления файлы удалённых снимков. Для восстановления распакуйте архив в отдельный каталог и выполните шаги ниже.

Самый простой вариант: остановить процесс и скопировать весь каталог `data` на компьютере либо `shared` на сервере, затем снова запустить процесс. Так база, WAL при его наличии и снимки сохраняются вместе. Для сервера команды остановки и запуска: `sudo systemctl stop drevo` и `sudo systemctl start drevo`.

Экспорт JSON удобен для обмена и ручного редактирования. Он содержит текущий архив, но не историю SQLite, настройки входа и файлы фотографий. Импорт JSON доступен через «Настройки» и полностью заменяет текущие данные после явного нажатия кнопки подтверждения.

## Импорт через админку

На компьютере откройте **Админка → Данные и копии → Восстановить из бэкапа**. Выберите `.sqlite` либо полный `.tar.gz`, нажмите «Проверить бэкап», сравните количество людей и фотографий, затем подтвердите замену. Проверка файла не изменяет действующее древо. Если после проверки кто-то изменил архив, потребуется повторная проверка: устаревший снимок не применяется автоматически.

Импорт заменяет текущих людей, связи, источники, координаты, фотографии и отметки. **Аккаунты, роли, настройки доступа и направления эпох остаются действующими.** Старую историю изменений из импортируемой базы интерфейс не переносит. Для полного восстановления всей SQLite, включая пользователей, используйте ручной сценарий ниже.

Перед применением создаётся `shared/backups/before-import-<время>-<uuid>.sqlite`. Новые файлы фотографий получают новые имена, ссылки в импортируемом древе меняются вместе с данными. Прежние файлы не перезаписываются и не удаляются. Для возврата к состоянию до импорта пригодны созданная резервная база и сохранённые прежние фотографии. Импорт одной SQLite сообщает о недостающих файлах — бинарные фотографии следует восстанавливать из полного архива.

Ограничения: загружаемый файл до 128 МБ, SQLite до 32 МБ, распакованный архив до 512 МБ, отдельное фото до 20 МБ. Допускаются `drevo.sqlite` и `uploads/`; ссылки, пути вне архива, повреждённые базы и неожиданные файлы отклоняются. Проверенный файл хранится временно до 15 минут и привязан к администратору. Для более крупных архивов используйте ручное восстановление. Ограничение Nginx для `/api/restore/preview` задано отдельно в `ops/nginx.conf`.

## Ручное восстановление SQLite

1. Остановите процесс приложения.
2. Сохраните существующий каталог данных под другим именем, включая `drevo.sqlite-wal` и `drevo.sqlite-shm`, если они есть. Не оставляйте старые WAL/SHM рядом с восстановленной базой.
3. Поместите скачанный бэкап в каталог данных под именем `drevo.sqlite`.
4. Восстановите соответствующий `uploads/`. Имена файлов должны остаться прежними.
5. На сервере проверьте владельца `site_drevo:site_drevo_grp` и разрешение записи в `shared` для этого пользователя.
6. Запустите приложение, проверьте карточки и несколько фотографий.

Смена кода при неудачном деплое не откатывает пользовательские данные автоматически. Если будущая миграция схемы окажется несовместимой, остановите приложение и восстановите согласованный бэкап вручную, чтобы не потерять изменения, поступившие после деплоя.
